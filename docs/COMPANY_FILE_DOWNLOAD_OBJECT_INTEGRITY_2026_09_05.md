# 기업자료 다운로드 원본 크기 무결성 경계

기준일: 2026-09-05

## 확인한 문제

기업자료 다운로드 API는 D1 파일 원장, 현재 계정 권한, 삭제 원장과 R2 객체 존재를 확인한 뒤 권한을 다시 확인했다. 그러나 D1의 `size_bytes`와 실제 R2 객체 크기를 대조하지 않아 같은 저장 키의 객체가 손상되거나 다른 크기로 교체되면 정상 원본처럼 HTTP 200으로 제공했다.

R2 조회 중 D1 크기 메타데이터가 달라지는 경쟁에서도 기존 구현은 저장 키만 같으면 미리 가져온 본문을 반환했다.

## 적용한 경계

- R2 본문을 가져온 직후 실제 객체 크기와 최초 D1 `size_bytes`가 정확히 같은지 확인한다.
- R2 조회 뒤 현재 D1 파일 원장과 계정·포털 접근 상태를 다시 읽고 저장 키와 크기가 모두 최초 값에서 바뀌지 않았는지 확인한다.
- 응답 직전 D1 조건문에도 파일 ID·저장 키·크기·담당 계정·담당 이름, 삭제 원장 부재와 동일 포털 상태를 함께 넣어 마지막 경쟁을 차단한다.
- 크기가 다르거나 조회 중 바뀌면 미리 가져온 R2 본문 스트림을 폐기하고 비공개 보안 헤더가 적용된 HTTP 409로 거절한다.
- D1 메타데이터와 R2 객체를 자동 수정·삭제하지 않는다. 본문 해시 저장, 스키마·보관 정책·다운로드 권한·파일명·MIME 정책도 변경하지 않았다.

## 검증

- 수정 전 재현: D1 크기와 다른 R2 객체 및 R2 조회 중 바뀐 D1 크기가 모두 HTTP 200 본문으로 제공됐다.
- 수정 후: 두 경우 모두 HTTP 409로 실패하고 미리 읽은 본문은 반환하지 않는다.
- 거절 뒤 D1 파일 원장과 R2 객체가 자동 변경되지 않는다.
- 격리 Worker에서 잘못된 R2 크기를 거절하고 D1 크기를 보존한 뒤 정상 크기 복구 시 같은 원본 다운로드가 다시 HTTP 200으로 성공한다.
- 기존 정지·권한 변경·삭제 경쟁, 연결 원본 삭제 차단과 정상 다운로드 검사가 계속 통과한다.
- Node 자동 테스트 560/560 통과.
- 격리 workerd+D1+R2 검사 350/350 통과.
- 타입검사, 전체 lint, 프로덕션 빌드 통과.
- 로컬 프로덕션 `/`, `/account`, `/account/setup` HTTP 200과 CSP·`nosniff`·`no-referrer` 확인.
- 실제 운영 쓰기, 메일 발송, 유료 AI 요청, 외부 요청 0건.
