# 독립 Next.js 운영 연결 후보

> 이전 Cloudflare HTTP 설계 기록입니다. 2026-09-09 이후 새 Vercel 배포는 [Turso + 비공개 Vercel Blob 연결 안내](VERCEL_STORAGE.md)를 따릅니다. 별도 Cloudflare 계정·Worker 배포는 요구하지 않습니다.

2026-09-08 기준입니다. **코드와 격리 검증을 완료한 연결 후보이며, 실제 Vercel 배포나 데이터 이관 완료가 아닙니다.** 기존 Sites 서비스, 호스팅 식별자와 원본 SQL 99개는 변경하지 않았습니다. Duet/Claude는 사용하지 않았습니다.

## 연결 구조와 활성화 경계

브라우저는 Next에서 로그인하고 작은 JSON으로 파일 전송 권한을 요청합니다. 파일 바이트는 별도 파일 Worker에 직접 전송합니다. Next의 일반 업무 처리기는 서버 전용 D1/R2 HTTPS 연결을 사용합니다. 파일 Worker는 동일 대상 DB·버킷의 네이티브 바인딩을 사용하며 기존 업무 권한·원장·멱등성 검사를 재사용합니다.

| 설정 | 역할 |
| --- | --- |
| `PARTNER_HUB_NEXT_BACKEND=cloudflare-http-v1` | 빌드 시 독립 원격 런타임·인증·파일 전송 별칭 선택. 런타임에서도 유지 |
| `PARTNER_HUB_BACKEND_ENABLED=1` | 별도의 런타임 활성화. 기본값은 `0` |
| `PARTNER_HUB_APP_ORIGIN` | 고정된 Next 서비스의 정확한 HTTPS origin |
| `PARTNER_HUB_D1_ORIGIN`, `PARTNER_HUB_D1_SECRET` | D1 Worker와 서버 전용 인증값 |
| `PARTNER_HUB_R2_ORIGIN`, `PARTNER_HUB_R2_SECRET` | R2 Worker와 서버 전용 인증값 |
| `PARTNER_HUB_FILE_ORIGIN`, `PARTNER_HUB_FILE_SECRET` | 브라우저 파일 Worker와 암호화 전송 권한의 비밀값 |

origin 네 개는 서로 달라야 하며 경로·끝 슬래시·쿼리·인증정보를 포함할 수 없습니다. 비밀값 세 개는 각각 독립된 무작위 32바이트의 소문자 64자리 hex이며 재사용을 거절합니다. `NEXT_PUBLIC_*`나 `next.config.env`에 넣지 않습니다. 비밀값 변경 후에는 프로세스 재시작/재배포가 필요합니다.

기본 빌드는 계속 미연결 상태입니다. 런타임 플래그만 바꿔 기본 빌드를 원격 모드로 전환할 수 없습니다. 원격 모드에서 설정이 누락되거나 잘못되면 API가 `503 / MIGRATION_BACKEND_NOT_CONFIGURED`로 닫힙니다. 로컬 에뮬레이터로 돌아가거나 DB·관리자를 자동 생성하지 않습니다. 로컬 저장소 opt-in과 원격 선택의 혼용도 거절합니다.

실제 요청 URL과 고정 origin을 대조합니다. 변경 요청은 동일한 `Origin`이 필요하고 `Sec-Fetch-Site: cross-site`는 거절합니다. 이 검사 자체는 사용자 인증이 아니며, 각 업무 라우트가 기존 세션·역할·대상 권한을 다시 확인합니다. Sites 신원 헤더와 임의 전달 IP 헤더는 독립 인증 근거로 사용하지 않습니다. Vercel 실제 프록시 환경 검증은 남아 있습니다.

로그인 요청 제한은 D1의 원자적 카운터를 사용합니다. 명시적으로 활성화된 원격 모드, 유효한 전체 서버 설정과 origin, 서버의 `VERCEL=1` 및 `VERCEL_ENV=preview|production`이 모두 확인될 때만 `x-vercel-forwarded-for`의 단일 IP를 제한 키로 사용합니다. 임의 `x-forwarded-for`, `x-real-ip`, `cf-connecting-ip`, 요청에 실린 Vercel 표시 값은 신뢰하지 않습니다. IPv6 축약·대소문자·IPv4 매핑 표기를 정규화하고 주소 목록·포트·zone ID는 거절합니다. IP는 DB에 직접 저장하지 않고 키 해시를 저장합니다. [Vercel 요청 헤더 명세](https://vercel.com/docs/headers/request-headers)

조건이 불충족되면 기존 공용 제한 키를 사용합니다. 자체 호스팅 서버에서 Vercel 환경 표시를 수동으로 위조 설정하지 마세요. 신뢰 경계가 깨지며 요청자가 IP 제한을 우회할 수 있습니다. 로그인은 IP별 15분 30회와 이메일별 8회를 함께 유지하고 가입은 IP별 8회입니다. 공유 네트워크의 사용자는 IP 한도를 공유합니다. IP 제한은 신원 인증·MFA·DDoS 보호의 대체 수단이 아닙니다. 기존 Sites와 로컬 Next의 IP 정책은 변경하지 않습니다.

원격 모드의 기존 파일 GET/HEAD 경로와 multipart POST는 `400 / FILE_TRANSFER_REQUIRED`로 차단합니다. 화면은 별도 전송 경로를 사용합니다. Vercel Functions의 브라우저 본문 제한을 우회하도록 기존 경로로 자동 재시도하지 않습니다.

## 독립 관리자 최초 설정

대상 DB에는 원본 업무 스키마와 별도로 `infra/standalone/migrations/0001_admin.sql`을 적용해야 합니다. **기존 Sites DB에 이 파일을 적용하지 마세요.** 이 파일은 관리자 테이블만 정의하고 계정은 만들지 않습니다. 이관 데이터의 원본 스키마·트리거 보존과 적용 순서는 별도 이관 절차에서 확인해야 하며, 운영 SQL 덤프에 원본 마이그레이션을 무조건 재실행하지 않습니다.

서버 환경을 안전하게 설정한 실제 터미널에서 다음을 사용합니다.

```sh
pnpm run admin:next:remote:check
pnpm run admin:next:remote
```

CLI는 셸에 설정된 환경을 읽으며 dotenv를 자동 로드하지 않습니다. Git에서 제외된 `.env.local`을 의도적으로 사용하는 운영자는 Node의 `--env-file=.env.local`과 `scripts/admin-next-remote.mjs`를 사용해 명시적으로 로드할 수 있습니다. 파일·터미널에 대한 접근 권한을 제한하고 값은 채팅·로그에 보내지 마세요.

- `--check`는 필요한 열과 관리자 존재 여부만 읽습니다. 스키마 전체 무결성·데이터 이관·계정 활성 상태의 종합 진단은 아닙니다.
- 최초 설정은 TTY에서 대상 서비스 주소를 정확히 입력한 뒤 비밀번호를 두 번 입력해야 합니다. 입력은 숨기며 비밀번호 인수·환경변수·파이프는 받지 않습니다.
- 지정 대표 이메일만 허용하지만 이메일 일치만으로 권한이 생기지 않습니다. 공개 가입·첫 로그인·위조 Sites 헤더로 관리자를 만들 수 없습니다.
- 이미 계정이 있으면 중단합니다. 동시 최초 설정도 기존 자격증명을 덮어쓰지 않습니다.
- 비밀번호는 scrypt, 세션은 무작위 토큰이며 DB에는 토큰 해시만 저장합니다. 관리자 1시간·파트너 12시간 정책과 HTTPS `__Host-`·Secure·HttpOnly·SameSite=Strict 쿠키를 사용합니다.
- 활성 상태·자격증명 버전·만료를 매 요청 확인합니다. 계정 전환·로그아웃은 기존 세션과 이미 발급된 파일 전송 권한의 후속 사용을 차단합니다.
- 이번 작업에서 실제 관리자 계정이나 운영 비밀번호는 생성하지 않았습니다. 아래 운영자 복구 절차를 추가했습니다. 공개 이메일 재설정·MFA·다중 관리자는 아직 제공하지 않습니다.

## 관리자 복구·비밀번호 교체

새 standalone DB에만 `0001_admin.sql` 다음 `0002_admin_recovery.sql`을 적용합니다. 기존 Sites SQL과 적용한 0001은 수정하지 않습니다. 새 파일은 변경·삭제 방지 트리거가 있는 복구 기록 테이블만 추가합니다. 계정이나 비밀번호를 자동 생성하지 않습니다.

```sh
pnpm run admin:next:remote:recovery-check
pnpm run admin:next:remote:recover
```

복구 권한은 대표 이메일을 아는 것으로 얻지 않습니다. **지정 대상의 특권 D1 서비스 접근 권한을 가진 운영자만** 실행할 수 있는 비상 절차입니다. 서비스 비밀값의 보관·접근 통제와 운영자 신원 확인은 별도 보안 경계이며 이 CLI가 사람의 신원을 자동 검증하는 것은 아닙니다. 실제 대상에서 복구하면 관리자 로그인 자격이 변경되므로 대상·사유를 확인하고 직접 실행하세요. 이번 개발 검사는 합성 계정만 사용했습니다.

- `--check`는 활성 대표 관리자 한 명, 복구 기록 테이블, 최근 복구 ID/시각을 읽습니다. 비밀번호·자격증명 버전·비밀값은 출력하지 않으며 쓰기는 없습니다.
- 복구는 TTY에서 정확한 서비스 주소, 지정 사유(`lost-password`, `credential-compromise`, `rotation`), 새 비밀번호 두 번을 숨김 입력받습니다. 비밀번호 인수·환경변수·파이프·이전 비밀번호 재사용을 허용하지 않습니다.
- CLI가 읽은 자격증명 버전과 실제 변경 시 버전이 같아야 합니다. 동시 복구·오래 열린 터미널·복구 직전 검증된 로그인 요청이 새 자격을 덮어쓰거나 이전 세션을 되살릴 수 없습니다.
- 비밀번호·버전 교체, 모든 관리자 세션 폐기, 복구 기록 저장이 하나의 D1 배치로 실행됩니다. 기록 저장 실패는 전체 롤백합니다. 계정 활성화·이메일 변경·파트너 계정 변경은 수행하지 않습니다.
- 발급된 관리자 파일 전송 권한도 다음 요청부터 거절합니다. 이미 인증 검사를 통과하여 실행 중인 요청을 소급 취소하는 기능은 아닙니다.
- 복구 기록에는 ID, 고정 관리자 ID, 지정 사유, 이전/다음 버전 해시, 시각만 저장합니다. DB 특권 관리자가 스키마를 제거하는 행위까지 막는 외부 불변 감사 서비스는 아닙니다.
- 쓰기 전에 비밀이 아닌 복구 ID를 출력합니다. 이후 통신 오류가 나면 커밋 여부가 불명확하므로 자동 재실행하지 않습니다. `--check`의 최근 ID와 대조하고 새 비밀번호의 로그인 여부를 확인합니다. 다른 복구가 뒤따른 경우 해당 ID의 감사 레코드를 권한 있는 운영자가 읽어 확인해야 합니다.

## 재현 가능한 검증

Node.js 24.19.0, 잠금 파일의 pnpm, OpenSSL이 필요합니다. Windows 검증은 Git for Windows에 포함된 OpenSSL을 사용합니다. 검증은 운영 dotenv 파일이 있으면 그 파일을 읽지 않고 중단합니다.

```sh
pnpm run test:next:remote:build
pnpm run test:next:remote
```

첫 명령은 원격 모드를 실제 프로덕션 빌드합니다. 합성 비밀값이 서버 JS에 고정되거나 공개 JS에 노출되지 않는지 검사하고, 번들 추적에서 Wrangler/Miniflare/workerd를 제외했는지 확인합니다. 이어 `next start`로 화면 3개와 API 23개×5메서드, 총 118건의 미활성화 차단 검사를 실행합니다. **활성화된 원격 Vercel 프로덕션 업무 검사는 아닙니다.**

둘째 명령은 실제 `next dev` HTTPS와 격리된 네이티브 D1/R2/Worker 세 개를 연결합니다. 일회용 테스트 인증서만 신뢰에 추가하고 TLS 검증은 유지합니다. 검사가 만든 인증서·키와 서버는 종료 시 정리합니다. 원본 마이그레이션 99개와 새 대상 관리자 스키마 2개에 합성 데이터만 넣습니다.

검증한 범위:

- 빈 관리자 스키마의 자동 생성 거절, 기존 계정 덮어쓰기 거절, 파트너/관리자 로그인과 역할·Origin·중복 쿠키 제한.
- 안전한 HTTPS 세션 쿠키, 작은 전송 권한 요청, 6MB 초과 PDF 직접 업로드/다운로드와 동일 요청 영수증 재사용.
- FLOW 파일 명령 6종, 두 슬롯의 6MiB 초과 음성 및 큰 한글 전사문, 13개 메타데이터 요청/12개 직접 업로드, 권한·늦은 재시도·비공개 다운로드.
- 기업자료/FLOW의 서버 R2 HTTPS 기반 존재·크기·SHA-256 검증 및 파트너의 관리자 보관 점검 거절.
- 로그아웃 후 두 역할 세션과 기존 파일 권한 폐기, 런타임 비활성화 시 저장소에 접속하지 않고 차단.
- 모의 Vercel 환경 표시를 사용한 네이티브 분산 요청 제한: 동시 36건 중 IP 한도 30건, 별도 IP의 독립 한도, IP가 달라도 공유되는 이메일 한도, IPv6/IPv4 매핑 정규화, 위조·누락 헤더의 공용 한도, 만료 후 재시도. 실제 Vercel의 헤더 덮어쓰기 검증은 아닙니다.
- 운영자 복구의 D1 HTTPS 원자적 교체, 이전 비밀번호·관리자 세션·파일 권한 폐기, 파트너 접근 보존, 복구 기록 수정/삭제 거절, 실제 복구 CLI의 읽기 전용 `--check`와 비밀값 비노출.

2026-09-08 보안 보완 후 전체 HTTPS 검사는 통과했습니다. 해당 실행에서 D1 요청 959건, R2 요청 3건, 파일 Worker 요청 18건, 외부 요청·유료 AI·실제 운영 쓰기·배포는 모두 0건입니다. 실행에 따른 요청 수는 구현 변경으로 달라질 수 있습니다. GitHub CI에도 별도 작업을 추가했지만 로컬 통과와 원격 CI 실행은 구분합니다.

최신 회귀검사에서 단위 테스트 885건, 원격 후보 및 기본 미연결 빌드의 프로덕션 HTTP 각각 118건, 생성된 배포 패키지의 Worker dry-run 3건·네이티브 파일 검사 40건이 통과했습니다. 운영자 복구 코드가 두 Next 서버 번들에 포함되지 않는지도 확인했습니다. TypeScript·lint·기존 Sites 빌드·번들 제한도 통과했습니다. 원본 SQL 99개와 `.openai/hosting.json`은 변경되지 않았습니다. 네이티브 D1/R2 HTTP 업무 687건과 v343 릴리스 보관본 검증은 이전 실행의 결과이며, 이번 보안 보완 후 687건 전체를 다시 실행한 것은 아닙니다. 기존 v343 보관본은 이번 이전 코드의 배포 증거가 아닙니다.
