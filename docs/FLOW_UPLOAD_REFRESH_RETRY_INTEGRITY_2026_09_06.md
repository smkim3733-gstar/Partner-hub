# 상담 FLOW 첨부 새로고침 재시도 무결성

기준일: 2026-09-06

## 확인한 문제

상담 FLOW 첨부 저장의 요청 ID는 같은 화면에서 재시도할 때만 메모리에 유지됐다. R2 기록 뒤 응답이 불확실한 상태에서 화면을 새로고침하면 브라우저가 새 요청 ID를 만들기 때문에, D1의 `pending` 예약이 보존돼 있어도 동일 파일 ID와 R2 키로 이어서 저장할 수 없었다.

## 보완

- 첨부가 있는 상담 FLOW 명령만 동일 탭의 `sessionStorage`에 진행 ID, 명령·첨부 SHA-256 재시도 키, 불투명 요청 ID를 한 건 보존한다.
- 화면을 새로고침한 뒤 같은 상담에서 동일 파일을 다시 선택하고 같은 명령을 실행하면 기존 요청 ID를 복원한다. 서버는 기존 `pending` 예약의 파일 ID와 R2 키를 재사용한다.
- 상담이 다르거나 명령·파일 바이트가 바뀌면 저장값을 사용하지 않고 새 요청 ID를 만든다.
- 성공 응답을 확인하면 진행 ID·재시도 키·요청 ID가 모두 일치하는 항목만 제거한다.
- 저장값은 최대 512자로 제한하고 형식이 손상됐거나 과대하면 제거한다. 브라우저가 임시 저장소를 차단해도 기존 화면 메모리 재시도로 안전하게 축소한다.
- 오류 안내는 새로고침 뒤 브라우저 보안상 사라진 파일을 동일 파일로 다시 선택해야 한다는 점을 명시한다.

## 개인정보·운영 경계

- 명령 원문, 파일명, 파일 바이트, 보고서 본문, 계정 정보, 인증 쿠키·토큰은 브라우저 저장소에 기록하지 않는다.
- `sessionStorage`는 같은 탭의 일시적 멱등 재시도 보조값일 뿐이며, 업무 상태와 원본의 기준은 계속 D1/R2다. 탭을 닫거나 다른 기기로 이동한 뒤의 복구를 보장하지 않는다.
- 기존 예약·원본의 자동 연결, 자동 삭제, 보관기간 변경, 관리자 권한 확대를 수행하지 않는다.
- 운영 데이터 조회·쓰기, 실제 계정 변경, 메일 발송, 유료 AI 호출은 검증에 사용하지 않았다.

## 회귀 검증

- 같은 탭 새로고침을 모의해 같은 진행·같은 지문이 정확한 요청 ID를 복원하는지 확인했다.
- 다른 진행, 다른 명령·파일 지문은 복원하지 않는지 확인했다.
- 성공한 저장은 정확히 일치하는 임시값만 제거하고 다른 요청 ID는 보존하는지 확인했다.
- 손상·과대·비활성 임시 저장소가 요청을 중단시키지 않고 안전하게 무시되는지 확인했다.
- Node 708/708, 격리 workerd+D1+R2 521/521, 타입검사, 전체 lint, 변경 파일 포맷과 프로덕션 빌드를 통과했다.
- 로컬 Worker의 `/`, `/account`, `/account/setup`은 200, 비로그인 `/api/state`, `/api/admin/file-inventory`, `/api/consulting-flow/test-case`는 401과 `private`, `no-store`, `nosniff` 경계를 반환했다.
- 격리 검증의 운영 쓰기, 메일, 유료 AI, 외부 요청은 모두 0건이다.
