### 1. 기존 자료 이전 — 기존과 같은 사용을 위한 필수 작업

현재 새 서비스에는 빈 포털 상태만 있다. 이전 Sites에서 확인했던 포털·초안·FLOW 자료가 실제로 복원된 상태가 아니다. 기존 포털 원문은 도구 출력에서 잘렸고 전체 Storage 목록도 검증하지 못했으므로, 그 출력이나 로컬 개발 DB를 운영 원본으로 사용할 수 없다.

현재 이전 CLI는 업무 테이블이 모두 0행이어야 실행된다. 이번에 확인한 `portal_state` 1행 때문에 지금 그대로 실행하면 `target-business-data-not-empty`로 중단된다. 빈 초기 상태라고 임의 삭제하거나 거절 조건을 없애서는 안 된다.

필요 작업: 잘리지 않은 원본 백업·파일 목록 확보 → 새 DB와 파일의 현재 백업 → 현재 빈 기준선의 정확한 내용과 변경 여부를 검사하는 이전 계획 보완 → 관리자·세션 보존 → 복원 후 건수·내용·파일 해시·권한 대조. 기존 CLI의 3개 업무 행 및 첨부 없는 원본에 대한 제한도 유지하거나 검증 근거에 맞게 별도 확장해야 한다.

### 3. DB와 첨부파일 백업·복구 검증 — 운영 전 확인 필요

새 Supabase 환경의 DB·파일을 함께 복원한 증거와 통합 복구 절차를 확인하지 못했다. 현재 프로젝트의 요금제·자동 백업 보관 설정은 이번 점검에서 확인하지 않았으므로, 백업 자체가 없다고 단정하지 않는다.

Supabase DB 백업에는 Storage의 실제 파일 내용이 포함되지 않는다. 파일은 별도 보존·복구 절차가 필요하다. [Supabase 공식 백업 문서](https://supabase.com/docs/guides/platform/backups)

필요 작업: 백업 주기·보관 기간·접근 권한·허용 데이터 손실 시간·목표 복구 시간을 정하고, 별도 검증 환경에서 DB와 실제 파일을 복원해 파일 원장·내용 해시·다운로드 권한을 대조한다. 이번 원본 이전 CLI는 일반적인 운영 백업·복구 도구가 아니다.

### 4. 실제 배포의 전체 업무 흐름 검증 — 테스트 증거 보완

코드 수준 핵심 기능은 구현되어 있고 이번 49개 테스트는 통과했다. 하지만 운영 Vercel의 브라우저에서 아래 흐름 전체를 완료했다는 증거는 아직 없다.

회원가입 → 대표 승인 → 로그인 → 협업신청 → 담당 배정 → 자료 업로드 → 상담 FLOW 및 보고서 확인 → 서류 보완 → 계약·입금 기록 → 사후관리 → 권한에 맞는 다운로드.

Next.js 빌드와 기존 HTTP 123개 검사는 합성 환경에서 `PARTNER_HUB_BACKEND_ENABLED=0`으로 실행된다. 실제 백엔드 연결의 전체 동작을 대신하지 않는다. 브라우저 E2E 기본 서버도 아직 Vinext다.

필요 작업: Next.js + Supabase 검증 환경에서 대표·파트너 역할별 전체 시나리오를 실행하고, 실제 배포에서의 제한적인 확인을 연결한다. 25MiB 파일의 앱 경유 제출, 중복 클릭·재시도, 동시 사용자 수정, 독립 DB 연결 경쟁, 모바일 사용도 확인한다.

기존 증거와 구분: 실제 Supabase 인증 핸들러 10단계와 실제 DB·Storage 파일 핸들러 10단계는 앞서 롤백 검사로 통과했다. 파일 핸들러의 본문은 1KiB였고, 별도 Storage 직접 전송 검사는 25MiB였다. 이는 Vercel의 전체 파일 처리 시간이나 전체 업무 시나리오 검증과 같지 않다.

### 5. Supabase 임시 업로드 정리 — 파일 운영 확대 전 보완

Supabase 업로드는 임시 경로와 `retain_until`을 기록하지만, 만료된 임시 객체를 정리하는 Supabase 전용 운영 명령·예약 실행은 저장소에서 찾지 못했다. 현재 `storage:cleanup`은 Turso/Vercel Blob용이므로 새 Supabase 운영에 사용할 수 없다.

근거: `lib/supabase-file-transfer.ts:145`, `lib/supabase-file-transfer.ts:150`, `lib/supabase-file-transfer.ts:231`, `scripts/vercel-storage.mjs:17`.

필요 작업: 보존 기한이 지난 임시 전송만 먼저 목록으로 검토하고 삭제하는 절차를 구현한다. 완료된 원본·버전·참조 중인 파일은 별도 보존 정책으로 다룬다. 삭제 중 재시도와 중단도 검증한다. 현재 운영 객체가 0건이므로 이미 용량 문제가 발생했다고 판단한 것은 아니다.
