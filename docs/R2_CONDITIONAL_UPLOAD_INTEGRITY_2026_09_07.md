# R2 조건부 업로드와 SHA-256 무결성

2026-09-07. 실제 고객자료·운영 D1/R2·외부 AI를 사용하지 않고 FLOW와 일반 기업자료 업로드의 같은 키 쓰기 경쟁을 격리 환경에서 점검했다.

## 확인된 위험

불변 업로드 예약은 정확 재시도에 같은 R2 키를 사용한다. 기존 쓰기는 최종 `head`에서 객체 교체를 찾을 수 있었지만, 라우트의 사전 확인 뒤 다른 쓰기가 먼저 완료되면 뒤따른 무조건 `put`이 그 객체를 다시 덮을 수 있었다. D1과 R2는 하나의 트랜잭션을 공유하지 않으므로 마지막 검사만으로 이 경쟁을 제거할 수 없다.

텍스트 신청자료는 원본을 검토·마스킹한 본문으로 다시 저장한다. 원본 SHA-256과 검토본 바이트 SHA-256이 다를 수 있으므로 하나의 해시를 두 용도로 사용하면 정상 검토본도 R2 체크섬 검사에서 거절된다.

## 변경

- FLOW와 일반 기업자료의 새 R2 쓰기를 사전 객체 ETag에 결속한 조건부 `put`으로 변경했다. 객체가 없을 때는 같은 키의 신규 객체가 먼저 생기지 않았을 때만 기록한다.
- 조건부 쓰기가 실패하면 최신 객체의 키·크기·MIME·SHA-256이 요청과 모두 같을 때만 안전한 동시 성공으로 인정한다. 다르면 409를 반환하고 경쟁 객체와 `pending` 예약을 보존한다.
- 업로드 바이트의 SHA-256을 R2 쓰기 옵션으로 전달하고 `put` 결과와 D1 직전 최종 `head`에서 다시 확인한다.
- 신청자료 원본 무결성 해시와 실제 검토본 저장 바이트 해시를 분리했다.
- R2 mock에 조건부 ETag 쓰기와 SHA-256 검증·보존을 추가하고 실제 workerd R2의 `checksums.sha256`도 검사했다.

## 회귀 증거

- FLOW: 사전 `head` 뒤 같은 크기 교체 객체가 먼저 저장되면 후속 쓰기는 409, FLOW D1 쓰기는 0건, 예약은 `pending`이다. 정확 재시도는 같은 파일 ID·키를 복구한다.
- 기업자료: 같은 경쟁에서 교체 객체를 덮지 않고 409를 반환한다. 정확 재시도는 최초 파일 ID·키에 원래 바이트와 SHA-256을 저장하고 `ready`로 완료한다.
- 신청자료: 검토본 저장 체크섬은 원본 해시가 아니라 실제 검토본 바이트에서 계산한다. 저장 응답 유실 전후 재시도와 원본 경쟁 오류 우선순위가 유지된다.

검증 결과는 Node 761/761, 격리 workerd+D1+R2 525/525, 타입검사, lint, 포맷, 프로덕션 빌드, 로컬 Worker 화면 200과 비인증 API 401이다. 외부 쓰기·메일·유료 AI·외부 요청은 모두 0건이다.

기능 커밋은 `66aa95462bf30470f15b8ba138682c6c62fed591`과 `cd1ecfba2b1352801c7be026554d3b6df821c4a8`이다. 로컬 배포 후보는 `outputs/release/partner-hub-v312.tar.gz`이며 생성 뒤 별도 SHA-256 검증을 수행한다. Sites 소스 전송·저장·공개 배포에는 정확히 `버전 312 Sites 소스 전송 및 공개 운영 배포 승인`이 필요하다.

## 남은 경계

새 R2 객체에는 SHA-256이 저장되지만 현재 불변 D1 원장은 ETag와 MIME만 보존한다. 후속 다운로드·미리보기·복구에서 SHA-256을 독립 권위값으로 사용하려면 additive D1 원장 확장과 기존 객체의 명시적 레거시 호환 규칙이 필요하다. 운영 원본을 자동 재해시하거나 기존 레코드를 추정 변환하지 않는다.
