# 완료 상담 FLOW 첨부 재고 가시성과 R2 확인 경계

## 결과

완료된 상담 FLOW 첨부도 대표 파일 재고의 개별 항목으로 표시한다. D1 소유·메타데이터·객체 무결성 원장과 실제 FLOW payload의 파일 항목이 정확히 한 건으로 결속돼야 `linked` 상태와 증명 유형을 인정한다. 관리자는 현재 R2 본문을 읽지 않고 객체의 존재·크기·고정 MIME·ETag·저장 시 SHA-256 객체 정보만 D1 원장과 대조할 수 있다.

기능 커밋은 `e6944bd4f10c0ac3fc06a8129e23d03b48c50282`이다.

## 재현과 수정

- 수정 전에는 완료 FLOW 첨부가 전체 증명 적용 현황에는 포함됐지만 개별 `linked` 목록 결과는 빈 배열이었다. 따라서 관리자가 해당 객체의 현재 R2 존재와 저장 원장 일치를 확인할 경로도 없었다.
- 완료 FLOW 소유 원장을 파일 재고 후보에 포함하고 `consulting-flow/{fileId}` 키, 메타데이터, 객체 무결성 원장, 선택적 업로드 예약과 실제 FLOW payload 파일 항목을 한 SQLite 읽기에서 대조한다.
- 실제 payload의 ID·키·생성시각·이름·MIME·크기·목적·신청자료 출처 필드가 정확히 한 건 일치할 때만 `linked`로 분류한다. 손상 JSON은 빈 파일 배열로 취급한다.
- 완료 소유 원장이 있는 파일은 `pending` 예약 후보에서 제외해 중복 항목을 만들지 않는다.
- 개별 확인은 완전히 검증된 FLOW와 정규 저장 키를 다시 확인한 뒤 R2 `head`만 사용한다. R2 `get`과 파일 본문 읽기는 수행하지 않는다.
- 재고의 D1 저장 증명 원장과 현재 R2 객체 정보 확인을 화면 문구·버튼·결과에서 분리했다. 현재 객체 정보 일치는 현재 파일 본문의 재해시 결과를 뜻하지 않는다.
- 파일 ID 허용 길이를 FLOW 스키마와 같은 200자로 통일하고 201자 입력은 서버와 응답 검증에서 거절한다.
- 스키마와 마이그레이션 변경은 없다.

## 검증

- 수정 전 회귀: 완료 FLOW 첨부 1건의 `linked` 목록이 빈 배열로 반환됨

- R2 `get`이 예외를 던지도록 잠근 상태에서도 `head` 한 번만 호출해 존재·크기·증명 일치 확인

- 타입검사, 전체 lint, 변경 파일 포맷, 프로덕션 빌드 통과
