# 상담 FLOW 파일 메타데이터 원장 무결성 경계

기준일: 2026-09-05

## 확인한 문제

버전 159의 소유권 원장은 파일 ID·진행·R2 키를 결속했지만, 같은 ID와 키를 유지한 채 파일명·MIME·크기·용도·생성시각 또는 원본 유입 증빙을 다른 유효값으로 바꾼 payload는 통과할 수 있었다. 파일명과 MIME을 서로 맞게 함께 변경하면 기존 형식 검사도 정상으로 판단했다.

초기 구현 후보 버전 160은 기존 `0014_consulting_flow_file_owners.sql`에 메타데이터 열을 직접 추가했다. 이 방식은 버전 159가 먼저 적용된 D1에서 `CREATE TABLE IF NOT EXISTS`가 기존 표를 확장하지 않으므로 순차 배포 호환성이 부족했다.

## 적용한 경계

- 기존 `0014`는 버전 159와 동일하게 보존하고 신규 `0015_consulting_flow_file_metadata.sql`을 추가했다.
- 새 `consulting_flow_file_metadata` 원장은 파일 ID별 최초 파일명·고정 MIME·크기·현재 용도와 선택적 원본 유입 ID·해시·검토시각·검토자를 보관한다. 생성시각은 기존 소유권 원장의 권위값을 사용한다.
- 새 파일의 FLOW CAS 저장, 진행 소유권 등록과 메타데이터 등록을 하나의 D1 batch에서 처리한다. 어느 조건이 맞지 않아도 전체를 롤백한다.
- 기존 파일은 이름·MIME·크기·키·생성시각·원본 유입 증빙을 바꿀 수 없다. 정상 업무인 `source → source_archived` 용도 전환만 FLOW와 메타데이터 원장에서 같은 batch로 진행한다.
- 상세 조회·다운로드·SQLite 대시보드 축소 전에 payload, 진행 소유권 원장과 메타데이터 원장의 모든 값을 대조한다. 원장 누락도 HTTP 503으로 실패 폐쇄한다.
- 백필은 배포 마이그레이션에서만 수행한다. 런타임 재시작이 누락된 원장을 현재 payload로 자동 재생성하지 않는다.
- 버전 159 형식의 기존 소유권 행을 넣은 뒤 `0015`를 적용하고, 전체 마이그레이션을 다시 실행해도 기존 상태와 메타데이터가 유지되는지 검증했다.
- R2 객체와 기존 FLOW payload를 자동 수정하거나 삭제하지 않았다. 인증·권한과 보관·삭제 정책도 변경하지 않았다.

## 검증

- 정상 파일의 이름+MIME, 크기, 생성시각, 용도, 원본 유입 ID를 각각 다른 유효값으로 바꿔 저장 전이와 저장 후 조회가 모두 HTTP 503으로 실패하는지 확인했다.
- 상세·대시보드·다운로드가 같은 메타데이터 변조를 차단하고 R2 객체를 보존하는지 확인했다.
- 정상 파일의 누락 원장은 런타임 읽기로 복구되지 않으며, 명시적 배포 백필만 모든 권위 필드를 복원하는지 확인했다.
- 정상 `source → source_archived` 전환은 메타데이터 원장과 FLOW에 함께 반영되는지 확인했다.
- 전체 Node 자동 테스트 597/597 통과.
- 격리 workerd+D1+R2 검사 407/407 통과. 전체 가산 마이그레이션 16개를 두 번 실행했고 v159→v161 이관을 포함했다.
- 타입검사, 전체 lint, 변경 파일 포맷 검사, `git diff --check`, 프로덕션 빌드 통과.
- 로컬 프로덕션 `/`, `/account`, `/account/setup` HTTP 200과 CSP·`DENY`·`nosniff`·`no-referrer` 확인.
- 실제 운영 쓰기, 메일 발송, 유료 AI 요청, 외부 요청 0건.
