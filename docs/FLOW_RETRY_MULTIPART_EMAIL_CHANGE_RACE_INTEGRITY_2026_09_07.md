# 상담 FLOW multipart 재시도 로그인 이메일 변경 경쟁 무결성

기준일: 2026-09-07

## 확인한 위험

파트너의 전사문·음성 2슬롯 업로드가 첫 R2 객체만 저장한 채 실패한 뒤 정확한 재시도를 시작했더라도, 큰 multipart 본문을 읽는 동안 대표가 파트너 로그인 이메일을 바꾸면 요청 시작 시점의 기존 ChatGPT 계정 결속으로 예약 조회와 남은 R2 쓰기를 이어갈 위험이 있다.

## 확인한 현재 경계

- 첫 전사문 객체 저장 성공과 두 번째 음성 저장 실패로 두 `pending` 예약이 남은 상태를 결정적으로 재현했다.
- 같은 명령 ID·본문·첨부의 multipart 재시도에서 서버가 본문을 처음 읽는 시점에 실제 관리자 상태 저장 경로로 파트너 로그인 이메일을 변경했다.
- 이메일 변경은 기존 ChatGPT 안정 사용자 ID·회원 ID 결속을 포털 상태와 함께 원자적으로 제거한다.
- 요청 시작 인증·담당 접근·업로드 권한이 성공했더라도 본문 해석 뒤 두 번째 신원 검사가 최신 회원과 결속을 다시 읽는다.
- 이전 이메일을 보낸 재시도는 HTTP 403과 활성 계정 안내로 거절되고, 예약 재사용 조회나 R2 `put`에 진입하지 않는다.
- 거절 중 FLOW 본문, 기존 전사문 객체 바이트와 두 예약의 파일 ID·R2 키·`pending` 상태는 그대로 유지된다.
- 대표가 원래 이메일로 복구해도 결속은 빈 상태로 남는다. 같은 안정 ChatGPT 사용자 ID가 복구된 이메일로 정확한 재시도를 보낼 때만 해당 회원으로 다시 결속된다.
- 재결속된 정확한 재시도는 기존 두 파일 ID와 R2 키를 이용해 완료되고 두 예약·완료 원장이 원래 명령 ID에 결속된다.
- 같은 공통 테스트 경계에서 `ownCases`, `fileUpload`, 계정 정지, 로그인 이메일 변경, 진행 중단 다섯 시나리오의 차단·보존·복구 조건을 함께 유지한다.

기존 구현이 요청 본문 전후로 인증과 접근 상태를 다시 확인하고, 관리자 이메일 변경이 결속을 원자적으로 폐기해 요구 경계를 만족한다. 런타임 코드는 바꾸지 않고 시간차 경쟁 회귀 증거를 확장했다.
