# 기업자료 원본 기본행 불변 경계

기준일: 2026-09-05

## 문제

`company_file_objects`는 기업자료 원본의 저장 키·이름·기업·종류·제목·담당 표시·업로더·MIME·크기·생성시각을 보유하는 부모 행이다. 별도 불변 원장과 모든 소비 경로의 대조가 변조를 탐지했지만, 테이블 자체는 직접 `UPDATE`를 받아들여 원본을 사용할 수 없는 손상 상태로 만들 수 있었다. 운영 애플리케이션에는 수정 경로가 없으므로 생성 뒤 변경을 허용할 이유가 없는 저장소 계약 공백이었다.

## 적용

- `app/`과 `lib/` 전체를 검사해 원본 기본행에는 신규 업로드의 `INSERT`와 검증된 명시적 삭제의 `DELETE`만 있고 `UPDATE` 경로가 없음을 확인했다.
- 모든 `company_file_objects` 직접 `UPDATE`를 거절하는 D1 트리거를 추가했다.
- 정상 삭제 API의 조건부 부모 행 `DELETE`는 유지했다. 삭제 시 저장 키·전체 메타데이터 원장을 다시 대조한 뒤 외래 키 연쇄로 자식 원장을 정리한다.
- `0024_company_file_object_immutability.sql`과 런타임 테이블 준비에 동일한 트리거를 적용했다.
- 정적 회귀검사가 애플리케이션 코드에 기본행 직접 수정 경로가 다시 들어오면 실패한다.
- 과거 손상 상태를 재현하는 테스트만 전용 도우미로 트리거를 잠시 해제하고 `finally`에서 즉시 복구한다. 운영 코드에는 우회 경로가 없다.

## 검증

- 정상 업로드 기본행의 제목 직접 변경이 `company file object is immutable` 오류로 거절된다.
- 거절 뒤 D1 원본 행과 R2 객체가 그대로 유지된다.
- 동일 파일의 검증된 삭제 API는 HTTP 204로 완료되고 부모 행·자식 원장·R2 객체를 제거한다.
- 기존 저장 키·메타데이터·크기 손상 격리 회귀검사는 명시적 레거시 fixture로 계속 통과한다.
- 25개 추가형 마이그레이션을 기존 행이 있는 격리 D1에서 두 번 적용해도 원본 사실을 교체하지 않는다.
- Node 회귀 검사 625/625 통과
- 격리 workerd/D1/R2 검사 436/436 통과
- 타입검사, 전체 lint, 변경 파일 포맷, 프로덕션 빌드 통과
- 로컬 운영 Worker `/`, `/account`, `/account/setup` HTTP 200과 CSP, `X-Frame-Options: DENY`, `nosniff`, `no-referrer` 확인
- 실제 운영 쓰기, 이메일 발송, 유료 AI 요청, 외부 요청 0건
