# 기존 서류요청 등록 화면 점검

2026-09-01. 사용자의 연속 개발 요청에 따라 상담 등록 다음 순서로 기존 `서류요청 등록` 화면을 가상 데이터로 점검했다. 실제 고객 자료·계정·연락·메일은 사용하지 않았다.

## 재현과 수정

기존 화면의 요청대상·전달 담당자·관련 서비스·관련 상담·공유범위·요청 안내문은 선택하거나 입력해도 저장되지 않았다. 화면의 요청번호는 항상 2였고, 같은 진행에서 아직 요청 중인 같은 서류를 반복 등록하면 자료 카드와 확인 업무가 중복 생성됐다.

- 실제 저장되는 요청 서류 목록과 제출기한만 입력받는다. 관련 서비스는 현재 진행 값으로 읽기 전용 표시한다.
- 요청대상은 기업대표, 전달 담당자는 현재 진행의 담당 파트너, 공유는 해당 진행 담당자 범위라는 현재 저장 동작을 화면에 명시한다. 다른 대상·안내·공개범위 기록은 기존 상담 FLOW를 이용하도록 안내한다. 새로운 공유 정책은 만들지 않았다.
- 요청번호는 해당 진행의 저장된 서류요청 기록 수에 따라 표시한다.
- 서류명의 앞뒤 공백과 중복을 정리하고 중복 항목의 필수 여부는 더 엄격한 값으로 합친다. 원본 배열은 수정하지 않는다.
- 해당 진행에서 `요청중` 또는 `보완필요`인 같은 이름의 서류는 다시 만들지 않는다. 새 항목이 섞여 있으면 새 항목만 등록하고, 모두 중복이면 저장을 차단한다. 제출완료·검토완료 기록은 신규 요청 판단을 막지 않는다.
- 존재하지 않는 날짜와 날짜 이외의 제출기한 값을 저장 전에 차단한다.

## 검증과 배포

- 실제 날짜·빈 목록, 공백·중복 정리·필수 병합, 기존 요청 일부 제외와 전부 중복 차단을 3개 회귀 검사로 추가했다.
- 전체 Node 검사 195개, 타입검사, lint, 빌드가 통과했다. 서버 API·DB 스키마를 바꾸지 않아 기존 workerd/D1/R2 저장소 검사 110개는 반복하지 않았다.
- 검사와 빌드 로그는 `outputs/validation/document-request-tests.log`, `document-request-build.log`에 남겼다.
- 운영 반영 상태는 `outputs/release/legacy-document-request-deployment.json`에 기록한다. 기존 공개 사이트, D1/R2 연결, 추가형 마이그레이션 8개를 유지한다.
- 실제 기업대표 전달·연락·메일·고객 파일 등록과 전체 키보드·모바일 검증을 수행한 것으로 해석하지 않는다.
