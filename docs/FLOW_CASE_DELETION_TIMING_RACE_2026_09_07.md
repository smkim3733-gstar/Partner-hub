# 상담 FLOW 사건 삭제 시점별 경쟁 무결성

기준일: 2026-09-07

## 확인한 위험

부분 R2 실패 뒤 정확한 전사문·음성 재시도 중 사건만 삭제되면 담당 계정은 계속 인증되므로 계정까지 삭제하는 회귀의 403만으로는 사건 접근 재검사를 증명할 수 없다. multipart 본문 처리나 R2 객체 기록 뒤에도 삭제 전 사건 권한으로 FLOW를 커밋하면 운영 목록에 없는 상담 이력과 파일 원장이 새로 생길 수 있다.

## 확인한 현재 경계

- 첫 전사문 객체 저장 성공과 두 번째 음성 저장 실패로 기존 전사문 객체와 두 `pending` 예약이 남은 상태를 각 시점별로 결정적으로 재현했다.
- 첫 multipart 본문 청크를 읽을 때 지원되는 관리자 상태 저장 API로 사건을 삭제한 경우, 본문 처리 뒤 R2 쓰기 전 사건 접근 재검사가 404로 끝난다. 재시도의 새 R2 쓰기와 FLOW·명령 영수증·파일 원장·완료 원장 D1 쓰기는 모두 0건이다.
- 재시도의 첫 전사문 객체를 기존 예약 키에 기록한 직후 같은 API로 사건을 삭제한 경우, 두 번째 음성 객체까지 원래 예약 키에 기록한 뒤 최종 사건 접근 재검사가 404로 FLOW D1 커밋을 차단한다.
- 두 시점 모두 사건 삭제는 유지되고 담당 회원과 안정 ChatGPT 사용자 ID·회원 ID 결속은 변하지 않는다. 기존 FLOW와 명령 영수증도 그대로이며 두 `pending` 예약은 원래 파일 ID·R2 키로 복구 가능하게 보존된다.
- 본문 처리 시점에는 기존 전사문 객체만 남고 음성 객체는 새로 생성되지 않는다. 첫 R2 쓰기 시점에는 전사문과 음성 객체가 모두 같은 예약 키에 남는다.
- 삭제한 사건 원본을 복구한 뒤 같은 안정 사용자 ID·명령 ID·본문·첨부로 정확히 재시도하면 같은 두 파일 ID·R2 키를 재사용해 FLOW, 명령 영수증, 두 `ready` 예약과 완료 원장을 한 번만 커밋한다.

기존 구현이 multipart 본문 처리 뒤와 모든 R2 쓰기 뒤 사건 접근을 다시 확인해 요구 조건을 만족한다. 런타임 코드는 바꾸지 않고 지원 관리자 사건 삭제의 본문 읽기·첫 R2 쓰기 경쟁 회귀 증거를 추가했다.
