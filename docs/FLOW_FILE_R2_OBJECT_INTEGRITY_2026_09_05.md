# 상담 FLOW R2 객체 무결성 경계

기준일: 2026-09-05

## 확인한 문제

버전 161은 FLOW payload와 D1 원장의 파일 크기를 R2 객체 크기와 대조했지만, 정상 객체를 같은 크기의 다른 바이트로 교체하면 다운로드가 HTTP 200으로 반환됐다. R2 객체의 `httpMetadata.contentType`을 바꿔도 저장된 파일명·고정 MIME과 별도로 대조하지 않았다. 같은 객체를 AI 근거자료로 읽는 경로도 크기만 확인했다.

## 적용한 경계

- 가산 `0016_consulting_flow_file_object_integrity.sql` 마이그레이션과 `consulting_flow_file_object_integrity` 원장을 추가했다.
- 신규 FLOW 파일은 R2 저장 결과의 키·크기·고정 MIME·ETag가 업로드 설명과 일치해야 한다. FLOW CAS 저장, 진행 소유권·파일 메타데이터·R2 객체 무결성 등록을 하나의 D1 batch로 처리한다.
- 신규 파일은 `etag` 검증 모드로 저장한다. 보관 증빙이 없거나 다른 파일의 증빙을 전달하면 FLOW 저장 전에 HTTP 503으로 실패한다.
- 기존 파일은 배포 마이그레이션에서 `metadata` 검증 모드로 명시한다. D1만으로 과거 R2 ETag를 안전하게 추정하지 않으며, 객체의 고정 MIME과 크기는 계속 확인한다.
- 다운로드는 R2 본문 반환 전 ETag·객체 MIME·키·크기를 대조한다. 권한과 FLOW를 다시 확인한 뒤 객체 원장이 바뀌지 않았는지 한 번 더 대조한다.
- AI 입력과 생성 전 사전점검도 파일 본문을 읽거나 외부 요청하기 전에 같은 객체 무결성을 확인한다.
- 객체 무결성 원장 누락·잘못된 모드·잘못된 ETag·MIME 불일치는 상세와 대시보드부터 HTTP 503으로 실패 폐쇄한다. 런타임 재시작은 누락 원장을 현재 값으로 자동 복구하지 않는다.
- 기존 R2 객체나 FLOW payload를 수정·삭제하지 않았다. 파일 권한·보관·삭제 정책도 변경하지 않았다.

## 검증

- 동일 크기의 다른 바이트로 R2 객체를 교체했을 때 다운로드가 HTTP 409로 실패하고 저장된 FLOW와 객체를 자동 변경하지 않는지 확인했다.
- 동일 바이트를 유지하면서 R2 객체 MIME만 `text/markdown`으로 바꿔도 다운로드가 실패하는지 확인했다.
- 신규 업로드의 실제 workerd R2 ETag·MIME과 D1 원장값이 일치하는지 확인했다.
- 객체 원장을 삭제하면 상세·대시보드·다운로드가 실패하고 런타임 읽기가 원장을 재생성하지 않는지 확인했다.
- AI 생성 사전점검이 같은 크기 교체를 불일치로 판정하고 외부 요청 전에 중지하는지 확인했다.
- 버전 159 상태에서 `0015`, `0016`을 순차 적용하고 전체 17개 가산 마이그레이션을 두 번 실행해도 기존 상태가 유지되는지 확인했다.
- 전체 Node 자동 테스트 599/599 통과.
- 격리 workerd+D1+R2 검사 413/413 통과. 실제 운영 쓰기, 메일 발송, 유료 AI 요청, 외부 요청 0건.
- 타입검사, 전체 lint, 변경 파일 포맷 검사, `git diff --check`, 프로덕션 빌드 통과.
- 로컬 프로덕션 `/`, `/account`, `/account/setup` HTTP 200과 CSP·`DENY`·`nosniff`·`no-referrer` 확인.

## 남은 경계

가산 마이그레이션은 기존 R2 객체의 ETag를 D1 값만으로 신뢰해 백필하지 않는다. 기존 객체는 크기와 고정 MIME을 검증하지만 과거 ETag 결속 전까지 같은 크기 바이트 교체를 식별할 수 없다. 실제 객체를 읽어 해시·소유권·백업을 확인하는 운영 이관은 별도 승인과 복구 계획이 필요한 작업이다.

다음 자동 감사는 별도 `company_file_objects` 원장을 사용하는 기업자료 원본의 같은 크기 R2 바이트 교체와 객체 MIME 변경을 다운로드·AI 입력 전에 검출하는지 확인한다.
