# 기업자료 전체 메타데이터 원장 무결성 경계

기준일: 2026-09-05

## 문제

기업자료 원본 행의 파일명·기업·종류·제목·담당 표시·업로더·MIME·크기·생성시각은 각각 정상 형식으로 바뀌면 기존 구조 검사를 통과할 수 있었다. R2 객체와 저장 키 원장이 정상이어도 유효값끼리 바뀐 D1 원본 사실이 다운로드, 상담 유입, 원본 연결, 회수와 삭제 판단에 사용될 수 있는 공백이었다.

## 적용

- `0019_company_file_metadata_integrity.sql`을 추가해 기존 원본 사실을 변경하지 않고 `company_file_metadata` 가산 원장에 정확히 백필한다.
- 신규 업로드는 원본 행·전체 메타데이터·R2 객체 무결성·저장 키·담당·진행·업로드 상태를 하나의 D1 batch에 저장한다.
- 런타임 테이블 준비는 누락 테이블만 만들고 기존 행을 자동 백필하지 않는다. 마이그레이션 누락이나 원장 손상은 추정 복구하지 않고 실패 폐쇄한다.
- 파일 조회, 다운로드, 삭제 결정과 삭제 후 정리, 상담 유입, Step 0 원본 검사, 포털 원본 연결, 관리자 회수와 보관 목록·R2 존재 확인 전에 원본 행과 전체 메타데이터 원장을 대조한다.
- 원장 누락·불일치는 R2 본문 조회나 삭제 전에 HTTP 503으로 격리하고, 관리자 보관 목록에서는 `메타데이터 확인 필요`로 분류한다.
- R2 삭제 뒤 D1 정리는 저장 키와 전체 메타데이터가 모두 결정 당시 값일 때만 단일 조건부 부모 삭제로 수행한다. 자식 원장은 외래 키 연쇄 삭제로 같은 SQLite 결정 안에서 정리한다.
- 실제 workerd D1의 SQLite 표현식 깊이 제한을 넘지 않도록 열별 연쇄 비교 대신 같은 의미의 행-튜플 비교를 사용한다.

## 검증

- 신규 업로드의 10개 메타데이터 사실이 원본 행과 원장에 정확히 일치한다.
- 정상 형식의 파일명·제목·크기 변경도 다운로드, 삭제, 회수, 상담 유입과 원본 연결 전에 차단한다.
- 손상 상태에서는 R2 `get`·`delete`·`head` 호출이 일어나지 않거나, R2 삭제 직후 경합이면 D1 원본 행·전체 원장·저장 키·객체 무결성·담당과 tombstone을 보존한다.
- 기존 원본은 마이그레이션에서 현재 사실 그대로 백필되고 마이그레이션 재실행도 기존 값을 덮어쓰지 않는다.
- Node 회귀 검사 617/617 통과
- 격리 workerd/D1/R2 검사 431/431 통과
- 타입검사, 전체 lint, 변경 파일 포맷, 프로덕션 빌드 통과
- 로컬 운영 Worker `/`, `/account`, `/account/setup` HTTP 200과 CSP, `X-Frame-Options: DENY`, `nosniff`, `no-referrer` 확인
- 실제 운영 쓰기, 이메일 발송, 유료 AI 요청, 외부 요청 0건
