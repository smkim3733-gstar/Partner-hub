# 상담 FLOW 파일 저장 키 무결성 경계

기준일: 2026-09-05

## 확인한 문제

FLOW 업로드는 새 R2 객체를 `consulting-flow/{파일 ID}` 키에 저장했지만, 저장 payload 구조 검증은 파일 ID와 키가 각각 올바른 문자열인지만 확인했다. 손상된 D1 payload가 같은 R2 버킷의 기업자료나 다른 FLOW 객체 키를 가리키면 FLOW 권한으로 그 객체에 접근을 시도할 수 있었다. 대시보드는 파일 배열을 SQLite에서 제거한 뒤 축소 구조를 검사하므로 같은 손상을 발견하지 못했다.

## 적용한 경계

- FLOW 파일 저장 키를 만드는 공용 함수와 `consulting-flow/` 네임스페이스 상수를 추가했다.
- 모든 새 업로드와 검토 완료 신청자료 가져오기는 `consulting-flow/{파일 ID}` 형식만 생성한다.
- 저장 FLOW 파일은 키가 자신의 파일 ID로 만든 값과 정확히 일치해야 한다.
- 상세 조회와 다운로드는 손상된 파일 키를 R2에서 읽기 전에 HTTP 503으로 격리한다.
- SQLite 대시보드 축소 전 검사도 파일 배열을 제거하기 전에 같은 ID·키 결속을 확인한다.
- 손상 payload가 가리킨 외부 R2 객체는 읽거나 삭제하지 않고 그대로 보존한다.
- D1 스키마, R2 원본, 인증·권한, 보관·삭제 정책은 변경하지 않았다.

## 검증

- 같은 버킷의 `company-source/...` 객체를 가리키는 FLOW 파일을 주입해 상세 조회·대시보드·다운로드가 모두 HTTP 503으로 실패하는지 확인했다.
- 실제 workerd+D1+R2에서 기존 비공개 객체 키를 참조하는 손상 payload를 주입하고 세 경로가 모두 차단되며 객체가 보존되는지 확인했다.
- Node 자동 테스트 592/592 통과.
- 격리 workerd+D1+R2 검사 394/394 통과.
- 타입검사, 전체 lint, 변경 파일 포맷 검사, 프로덕션 빌드 통과.
- 로컬 프로덕션 `/`, `/account`, `/account/setup` HTTP 200과 CSP·`DENY`·`nosniff`·`no-referrer` 확인.
- 실제 운영 쓰기, 메일 발송, 유료 AI 요청, 외부 요청 0건.
