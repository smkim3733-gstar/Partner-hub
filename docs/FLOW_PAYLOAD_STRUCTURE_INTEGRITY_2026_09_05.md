# 상담 FLOW payload 최상위 구조 무결성 경계

기준일: 2026-09-05

## 확인한 문제

D1 행과 payload의 진행·담당·revision·수정시각이 일치해도 기업명·담당자명이나 필수 배열·객체가 없거나 다른 형식일 수 있었다. 기존 서버는 이를 `ConsultingFlow`로 단언해 권한 응답과 진행단계 계산에 전달했으므로 손상 위치에 따라 일반 HTTP 500 또는 잘못된 화면 투영이 발생할 수 있었다.

대시보드는 민감 본문을 SQLite 안에서 제거하지만 `reports`·`recordings`를 축소 배열로 다시 만들기 때문에 원본 배열 형식이 손상돼도 결과만 정상 배열처럼 보일 수 있었다.

## 적용한 경계

- 공용 FLOW 구조 검증기를 만들어 서버 저장 읽기와 브라우저 응답 검증이 같은 최상위 계약을 사용한다.
- 진행·기업·담당 ID·담당자명, revision·수정시각, analysis·ai 객체와 reports·files·meetings·recordings·requests·payments·jobs·audit·commandIds 배열을 확인한다.
- 선택적 decision·contract·aftercare·commandReceipts는 존재할 때 일반 객체, executionStartedAt은 문자열이어야 한다.
- 상세 조회는 전체 payload를 JSON 파싱한 직후 검증하고 불일치를 HTTP 503 관리자 복구 상태로 격리한다.
- 대시보드는 민감 본문을 메모리에 올리지 않는다. SQLite에서 원본 전체 구조를 먼저 확인한 경우에만 보고서·녹취를 축소하고, 축소 결과에도 전용 구조 검증을 적용한다.
- 클라이언트 성공 응답도 같은 전체 구조 검증기를 사용한다. 초기 미저장 FLOW의 빈 `updatedAt` 호환은 유지하고 저장된 FLOW 시각은 서버 행 검증에서 정상 시각을 강제한다.
- 정상 FLOW 명령·권한·CAS·D1/R2 스키마와 보관·삭제 정책은 변경하지 않았다.

## 검증

- 빈 기업명, 비문자 담당자명, 잘못된 reports·files, 누락 analysis와 잘못된 AI source 구조를 상세 조회 전에 모두 거절한다.
- 원본 payload에서 `files` 배열이 누락된 경우 SQLite 축소 결과로 숨기지 않고 대시보드 투영을 거절한다.
- 격리 Worker의 실제 D1 경로에서 필수 컬렉션 누락을 상세·대시보드 모두 HTTP 503으로 차단하고 원본 복구 뒤 정상 조회가 재개된다.
- 메트릭 장애 격리 검사는 고유 SQL 별칭에만 장애를 주도록 좁혀 새 구조 검사와 독립적으로 유지한다.
- Node 자동 테스트 570/570 통과.
- 격리 workerd+D1+R2 검사 361/361 통과.
- 타입검사, 전체 lint, 프로덕션 빌드 통과.
- 로컬 프로덕션 `/`, `/account`, `/account/setup` HTTP 200과 CSP·`nosniff`·`no-referrer` 확인.
- 실제 운영 쓰기, 메일 발송, 유료 AI 요청, 외부 요청 0건.

## 다음 감사

필수 배열의 각 항목이 일반 객체인지 확인하고 보고서·파일·상담·녹취·서류요청·결제·AI 작업·감사기록의 필수 ID·시각·허용 상태·수치가 실제 서버 함수가 기대하는 형식인지 검증한다. 배열 껍데기만 정상인 손상 payload를 진행단계·합계·권한·다운로드 로직에 전달하지 않는다.
