# 한기평 파트너 허브 기획 검수

검수일: 2026-09-01
검수 방식: Codex 저장소 검토 + Duet(Claude 독립 반론)
범위: 현재 구현을 실제 파트너 파일럿에 투입하기 전의 제품·운영 기획

## 판정

현재 파트너 허브는 기술 검증이 충분히 축적된 **통제형 MVP**다. 대표 관리자와 승인된 파트너가 신청, 자료, 상담 FLOW, 보고서, 견적·계약, 후속 업무를 한곳에서 처리한다는 핵심 구조는 일관된다. 수동 처리와 자동 처리의 경계도 화면과 상태 문서에 대체로 명시돼 있다.

다만 실제 파트너 파일럿의 운영 준비가 완료된 상태는 아니다. 파일럿 성공 여부를 신뢰할 수 있게 만드는 데이터 기준선, 저장 용량·동시편집 운영 기준, 자격증명 전달·본인확인 절차가 먼저 결정돼야 한다. Vercel 또는 다른 호스팅으로 이전하는 일은 이 세 항목을 해결하지 않으므로 파일럿 준비보다 뒤에 둔다.

## 제품 역할과 책임

- **대표 관리자:** 파트너 승인·정지, 권한 부여, 전체 진행 감독, 중요 산출물 승인, 자격증명 발급과 파일럿 운영 책임을 맡는다.
- **승인 파트너:** 자신에게 배정된 기업과 진행을 기준으로 신청, 자료 제출, 상담 기록, 후속 업무를 처리한다.
- **고객 기업:** 현재 로그인 계정 역할이 아니다. 파트너가 고객을 대리해 입력하고 자료·동의를 수집하는 간접 당사자다. 파일럿 절차에는 고객 동의 근거와 대리 입력 책임을 포함해야 한다.

## 파일럿 착수 전 필수 게이트

### 1. 파일럿 데이터 기준선

현재 빈 운영 상태는 소스의 가상 파트너·기업·업무·자료·진행 데이터로 초기화될 수 있고, 대표 대시보드는 저장된 상태를 그대로 집계한다. 이 상태로 파일럿을 시작하면 실사용 지표와 가상 데이터가 섞인다.

파일럿 시작 전 다음 중 한 방식을 대표가 승인한다.

- 승인된 빈 상태에서 시작한다.
- 기존 상태를 유지하되 모든 레코드에 가상·실사용 출처를 구분하고, 대표 지표와 파일럿 지표에서 가상 레코드를 제외한다.

삭제나 정리가 필요한 경우 삭제 대상, 보존 근거, 승인자, 실행 담당자를 먼저 문서화한다. 이 검수에서는 실제 데이터를 읽거나 삭제하지 않는다.

### 2. 저장 용량과 동시편집 한계

운영 상태는 D1의 단일 `portal_state` 행에 전체 JSON으로 저장된다. 직렬화된 상태는 900,000바이트를 넘을 수 없고, 저장은 전체 이전 페이로드가 일치해야 성공하는 전역 비교·교체 방식이다. 대표와 파트너가 서로 다른 진행을 수정해도 충돌할 수 있으며 실패한 스냅샷은 열린 페이지 메모리에 남아 수동 재시도에 의존한다.

파일럿 전 다음 기준을 확정한다.

- 실제 고객 자료를 열람하지 않는 안전한 방식으로 현재 상태 크기와 진행 1건당 평균 증가량을 측정한다.
- 900KB의 70%를 1차 경보 후보로 삼되, 측정 결과에 따라 대표가 최종 임계값을 승인한다.
- 임계값 도달 전 상태 분할 또는 아카이브 설계를 시작할 시점을 정한다.
- 대표와 파트너의 동시편집 허용 범위, HTTP 409 충돌 시 최신 상태 확인, 미저장 입력 복구, 재시도 순서를 운영 수칙으로 만든다.
- 파일럿 지표에 저장 충돌 횟수, 복구 성공률, 재입력 시간을 포함한다.

### 3. 파트너 자격증명 전달과 본인확인

이메일·카카오톡 자동 발송은 연결되지 않았고 비밀번호 설정 링크는 30분 후 만료된다. 공개 자가가입은 이메일 소유권을 검증하지 않은 채 승인대기 레코드를 추가한다.

파일럿 전 다음 절차를 확정한다.

- 기존에 확인된 연락처를 사용해 파트너 본인을 확인하는 방법을 정한다.
- 설정 링크 전달 채널과 발급 기록의 보관 위치를 정한다.
- 링크 만료 시 재발급 담당자와 목표 대응 시간을 정한다.
- 파일럿 기간에 공개 자가가입을 유지할지 대표 초대 방식으로 제한할지 결정한다.
- 이메일 소유권 인증과 MFA를 파일럿 전 도입할지, 제한된 파일럿 결과를 본 뒤 도입할지 결정한다.

## 파일럿에서 측정할 지표

- [신청부터 첫 상담 FLOW까지의 완료율과 소요시간](APPLICATION_FIRST_CONSULTATION_METRICS_2026_09_01.md). 신규 서버 추적 신청과 FLOW 완료기록만 사용하고, 레거시 상담은 측정 불가로 분리하며 5건 미만 소요시간을 숨기는 관리자 전용 지표로 구현했다.
- 중복 입력·중복 요청 발생 건수
- 파트너에서 대표로 넘어가는 승인 대기시간. [1차 공동분석 확인 간격](JOINT_ANALYSIS_CONFIRMATION_METRICS_2026_09_01.md)은 독립 확인 순서·간격을 측정하고, [서류 수령 → 대표 검토 간격](DOCUMENT_REVIEW_WAIT_METRICS_2026_09_01.md)은 앞으로 서버가 기록하는 최신 추가서류 검토 주기의 완료시간과 현재 대기 연령을 측정한다. 요청별 수령 역할을 저장하지 않으므로 파트너만의 인계시간으로 분리하지는 않는다.
- 저장 충돌, 재시도, 입력 복구 성공률과 재입력 시간
- [비밀번호 링크 만료와 재발급 건수](PASSWORD_LINK_OBSERVABILITY_2026_09_01.md). 식별정보 없는 최근 7일 합계로 구현했으며 관측 한계를 함께 표시한다.
- [실제 지원 요청의 유형과 처리시간](SUPPORT_REQUEST_METRICS_2026_09_01.md). 기존 업무에 고정 지원 유형과 서버 등록·대표 인지·완료 시각을 추가하고 요청자 자가종료를 대표 처리시간에서 제외한 관리자 전용 현재 상태 지표로 구현했다.
- [가상 데이터를 제외한 진행 단계별 명시적 중단률](PIPELINE_DROPOFF_METRICS_2026_09_01.md). 신규 서버 추적 신청만 대상으로 대표의 명시적 중단을 측정하고, FLOW 확인 단계와 수동 보고 단계를 분리한 관리자 전용 현재 상태 지표로 구현했다.

## 파일럿 이후 우선순위

1. 파일럿 데이터와 충돌·병목 지표를 근거로 단일 상태 저장을 도메인별·레코드별 저장으로 분리할지 결정한다.
2. 대표 승인 병목이 실제로 확인된 단계부터 권한 위임이나 일괄 승인 방식을 검토한다.
3. 레거시 상담 입력과 상담 FLOW의 사용 빈도·중복 기록을 확인한 뒤 하나의 기준 경로로 정리한다.
4. 보관·삭제, 과거 원본 수동 배정, 이메일 소유권 인증·MFA 정책을 확정한다.
5. 그 뒤에 메시징, 캘린더, 전사, 전자서명, 입금 조회, 외부 AI 등 비용·동의·장애 대응이 필요한 연동을 검토한다.
6. 호스팅 이전은 현재 플랫폼이 필요한 기능·운영 기준을 충족하지 못한다는 근거가 확인될 때 추진한다.

## Duet 검수 결론

Duet는 중앙 계획의 방향과 저장소 인용이 타당하다고 평가했다. 독립 대안은 필요하지 않으며, 기존 계획에 누락된 세 파일럿 게이트를 추가하면 된다고 판정했다. 지적된 차단 2건과 중요 1건은 모두 저장소에서 재확인해 수용했다. 고객을 로그인 페르소나로 본 초기 표현은 현재 구현과 맞지 않아 계정 없는 간접 당사자로 바로잡았다.

네이티브 Windows에서는 Duet의 결정론적 검사 샌드박스를 사용할 수 없다. 따라서 이 문서는 기획 검수 결과이며 고위험 운영 배포에 대한 완전 승인으로 해석하지 않는다. 고위험 변경을 Duet로 검증할 때는 WSL2 환경을 권장한다.
