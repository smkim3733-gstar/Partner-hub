# 새 기업파일의 담당 계정 연결 — 2026-08-31

## 배경과 범위

선행 배포(버전 34, 소스 `767f384`)는 동명이인끼리 과거 자료를 열지 못하도록 보호했다. 다만 파일의 담당자가 이름으로만 저장되어 동명이인인 업로더가 새 파일도 다시 내려받지 못할 수 있었다. 이번 변경은 **신규 파일**의 담당 계정을 직접 저장해 이 제한을 보완한다.

## 사용 방법

- 파트너: 자료 등록 또는 협업신청에 파일을 첨부하면 로그인한 계정에 자동 연결된다. 요청에 다른 담당자 이름·ID가 있어도 서버가 본인 계정으로 저장한다.
- 대표 자료함: 담당 계정 선택 항목에서 이름과 이메일을 확인한다. 기본값인 ‘대표 전용 보관’은 파트너에게 공유하지 않는다.
- 대표 대리접수: ‘자료 공유 계정’을 선택하면 신규 진행과 첨부자료가 그 계정에 연결된다. 신청자 이름을 직접 변경하면 대표 전용 접수로 돌아간다. 이름만으로 동명이인을 추정하지 않는다.
- 표시 이름이 변경되어도 새 파일의 권한과 신청자료 검토 연결은 계정 ID를 따른다.

## 저장과 호환

추가형 마이그레이션 `0004_company_file_assignments.sql`은 기존 파일 메타데이터 구조를 보존하고 파일 ID → 담당 계정 ID 연결 테이블을 추가한다. 새 메타데이터와 담당 계정 연결을 한 D1 배치에서 저장한다. 실패하면 새 R2 객체를 정리한다. 파일 삭제 시 연결 메타데이터도 함께 정리한다.

연결 행이 없는 기존 파일과 빈 담당 계정 ID(대표 전용)를 구분한다. 과거 파일의 계정 ID를 이름이나 업로더를 근거로 자동 채우지 않는다. 서버에 남아 있는 레거시 파일의 권한 규칙과 대표 접근은 유지한다. 동명이인인 과거 자료는 대표가 개별 확인해야 하며, 이번에 재배정 도구나 일괄 이관은 추가하지 않았다. 기존 진행의 담당자를 바꾸어도 이미 저장된 원본 파일의 담당 계정이 자동으로 변경되는 기능은 아니다.

신청자료 검토는 새 연결이 있으면 기업명과 담당 계정 ID가 모두 맞는 파일만 사용한다. 연결이 없는 과거 파일은 대표 검토 화면의 기존 기업명·담당자 이름 규칙을 유지한다. 대표 전용 파일을 파트너 진행으로 자동 복사하지 않는다.

## 확인 결과

- 회귀 테스트 91개: 신규 4개는 수정 전 실패를 확인했으며 수정 후 통과했다. 동명이인, 위조된 담당 ID, 이름 변경, 잘못된/정지된 담당 계정, 대표 전용 파일, 신청자료의 교차 계정 연결을 포함한다.
- 실제 workerd + 격리 D1/R2에서 43개 확인: multipart 파일 등록, 쿠키 인증 다운로드, 타 계정 접근·삭제 차단, 대표 지정, 연결 메타데이터 정리, 5개 추가형 마이그레이션 반복 실행 후 기존 파일과 계정 연결 보존을 포함한다.
- 실제 운영 계정 생성·고객 파일 조회·기존 파일 재배정·메일 발송·유료 AI 호출은 검증에 사용하지 않았다. 브라우저 클릭 검증과 서비스 전체 보안감사는 포함하지 않는다.

선행 공개 배포의 주요 페이지는 HTTP 200, 비로그인 상태 API는 401로 확인했다. 본 변경의 최종 배포 결과는 배포 서비스 이력과 로컬의 비공개 `outputs/release/` 완료 기록으로 구분한다. 같은 날 작성한 아래의 기존 문서들은 당시 검증 단계의 기록도 포함한다.
