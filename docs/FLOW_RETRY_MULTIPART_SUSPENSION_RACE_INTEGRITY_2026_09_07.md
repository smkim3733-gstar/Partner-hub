# 상담 FLOW multipart 재시도 계정 정지 경쟁 무결성

기준일: 2026-09-07

## 확인한 위험

파트너의 전사문·음성 2슬롯 업로드가 첫 R2 객체만 저장한 채 실패한 뒤 정확한 재시도를 시작했더라도, 큰 multipart 본문을 읽는 동안 대표가 파트너 계정을 정지하면 요청 시작 시점의 활성 인증만으로 기존 예약과 남은 R2 쓰기를 이어갈 위험이 있다.

## 확인한 현재 경계

- 첫 전사문 객체 저장 성공과 두 번째 음성 저장 실패로 두 `pending` 예약이 남은 상태를 결정적으로 재현했다.
- 같은 명령 ID·본문·첨부의 multipart 재시도에서 서버가 본문을 처음 읽는 시점에 실제 관리자 상태 저장 경로로 파트너 계정을 정지했다.
- 요청 시작 시 인증·담당 접근·업로드 권한이 성공했고 안정 ChatGPT 사용자 ID·회원 ID 결속이 유지돼도, 본문 해석 뒤 두 번째 인증 검사가 최신 계정 상태를 다시 읽는다.
- 재시도는 HTTP 403과 활성 계정 안내로 거절되고 R2 `put`을 한 번도 호출하지 않는다.
- 거절 중 FLOW 본문, 기존 전사문 객체 바이트와 두 예약의 파일 ID·R2 키·`pending` 상태는 그대로 유지된다.
- 계정 정지는 안정 ChatGPT 회원 결속을 삭제하지 않지만 즉시 접근을 차단한다.
- 대표가 계정을 다시 활성화한 뒤에만 정확한 재시도가 기존 두 파일 ID와 R2 키를 이용해 완료되고 두 예약·완료 원장이 원래 명령 ID에 결속된다.
- 같은 공통 테스트 경계에서 `ownCases`, `fileUpload`, 계정 정지, 진행 중단 네 시나리오의 차단·보존·복구 조건을 함께 유지한다.

기존 구현이 요청 본문 전후로 인증과 접근 상태를 다시 확인해 요구 경계를 만족하므로 런타임 코드는 바꾸지 않고 시간차 경쟁 회귀 증거를 확장했다.
