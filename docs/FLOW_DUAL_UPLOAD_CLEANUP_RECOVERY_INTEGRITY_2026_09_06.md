# 상담 FLOW 2슬롯 정리 실패 격리·재시도 무결성

기준일: 2026-09-06

## 확인한 공백

상담 녹취의 전사문과 보조 음성을 한 요청에서 업로드한 뒤 D1 저장이 실패하면, 서버는 성공 FLOW가 참조하지 않는 R2 객체를 정리한다. 기존 구현은 두 객체를 순서대로 삭제해 첫 삭제가 실패하는 순간 나머지 삭제도 시도하지 않았다. 그 결과 한 객체의 일시적인 R2 오류가 독립적으로 정리 가능한 다른 객체까지 남기고, 어떤 키가 실제로 정리됐는지 불필요하게 모호해질 수 있었다.

## 적용한 경계

- D1 실패 뒤 권위 FLOW를 다시 읽고, 이미 성공 FLOW가 참조하는 키는 삭제 대상에서 제외한다.
- 참조되지 않은 전사문·음성 객체의 삭제를 각각 독립적으로 실행한다.
- 한 객체 삭제가 실패해도 다른 객체 삭제는 계속 시도한다.
- 삭제 실패는 원래 업무 응답을 덮어쓰지 않는다. D1의 내구성 `pending` 예약이 파일 ID·R2 키·지문을 보존한다.
- 다음 동일 첨부 재시도는 새 명령 ID에서도 원래 두 예약을 재사용하고, 누락 객체는 다시 쓰며 남은 객체는 같은 키에 정확한 바이트를 복원한다.
- 성공 FLOW에 이미 연결된 객체는 기존과 같이 보존한다.

스키마나 마이그레이션 변경은 없다. 정리 정책의 실패 격리와 복구 검사를 강화한 변경이다.

## 검증

- 첫 번째 R2 삭제만 인위적으로 실패시켜도 두 키의 삭제 시도가 모두 수행됨을 확인
- 한 객체만 남고 두 예약은 `pending`으로 유지됨을 확인
- 새 명령 ID의 동일 첨부 재시도가 원래 파일 ID·R2 키를 재사용해 전사문과 음성을 모두 완성함을 확인
- Node 자동 검사: 715/715 통과
- 격리 workerd + D1 + R2 검사: 522/522 통과
- 격리 검사는 운영 데이터 쓰기, 메일 발송, 유료 AI 요청, 외부 요청이 모두 0임을 확인
- 타입검사, lint, 변경 파일 포맷 검사, 프로덕션 빌드 통과
- 로컬 운영형 Worker에서 `/`, `/account`, `/account/setup`은 200 응답
- 인증 없는 `/api/state`, `/api/admin/file-inventory`, `/api/consulting-flow/test-case`는 401과 비공개 캐시 경계 유지
- 배포 아카이브는 Worker, 호스팅 설정, 96개 SQL 마이그레이션을 포함하고 `.wrangler` 임시 상태를 제외
