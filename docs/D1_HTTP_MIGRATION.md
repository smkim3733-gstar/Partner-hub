# Vercel 이전: 서버 전용 D1 연결 검증

## 현재 결론

우선 검증하는 구조는 **Vercel의 Next.js + 별도 Cloudflare Worker 뒤의 D1 + 비공개 파일 저장소**입니다. Vercel로 화면과 업무 API를 옮기되, SQLite JSON·트리거·트랜잭션 규칙을 보존하는 방향입니다. PostgreSQL 전환이나 운영 데이터 복사는 이번 범위가 아닙니다.

Cloudflare는 외부 앱에서 D1을 사용할 때 인증된 Worker API를 구성하는 방식을 안내하며, 관리용 REST API에는 전역 API 요청 제한이 적용된다고 설명합니다. 따라서 Cloudflare 계정 전체에 접근하는 관리 토큰을 앱의 일반 DB 연결로 사용하는 방식은 채택하지 않았습니다. [Cloudflare D1 외부 접근 안내](https://developers.cloudflare.com/d1/tutorials/build-an-api-to-access-d1/)

**실제 Cloudflare/Vercel 계정에는 연결하지 않았습니다.** 기존 Sites가 관리하는 DB/R2를 임의의 Worker에 연결할 수 있다고 가정하지 않습니다. 데이터 내보내기 권한과 사용자가 소유한 대상 자원을 확인해야 합니다. 기존 Sites의 `.openai/hosting.json`, 운영 SQL 마이그레이션 99개, 운영 계정·파일은 변경하지 않았습니다.

## 구현한 연결

후속으로 [독립 Next 원격 연결 후보](NEXT_REMOTE_BACKEND.md)를 추가하고 합성 HTTPS 환경에서 인증·업무·파일 흐름을 검증했습니다. 기존 로컬 HTTP 검증과 실제 운영 대상 연결은 구분합니다.

- `lib/d1-http-client.ts`: 현재 포털이 사용하는 `prepare`, `bind`, `first`, `all`, `run`, `batch`를 HTTP 전송에 연결합니다.
- `lib/d1-http-client.next.ts`: Next 서버 전용 진입점입니다. Client Component에서 가져오면 빌드가 거절되며, HTTP 예외나 임의 전송 함수를 받지 않습니다.
- `lib/d1-http-protocol.ts`: 버전이 있는 요청 형식, 값 검증, 바이트·쿼리 개수 제한, 안전한 오류 코드를 정의합니다.
- `infra/d1-bridge/worker.ts`: 서비스 비밀값을 검증한 뒤 단일 D1 바인딩에 요청을 전달합니다. 배포 설정·실제 자원 ID는 포함하지 않았습니다.
- `dev/next-local/d1-http.ts`: Next 개발 서버에서 실제 루프백 HTTP를 거쳐 격리된 로컬 D1에 접근하는 검증용 연결입니다. 외부 주소를 받지 않습니다.

`batch` 한 번을 하나의 HTTP 요청과 하나의 네이티브 `DB.batch`로 대응시킵니다. 순서를 바꾸거나 나눠 전송하지 않습니다. D1의 문장 오류에 대한 전체 트랜잭션 롤백과 반환된 변경 건수를 유지합니다. [D1 batch 문서](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)

현재 연결은 직접 D1 바인딩을 사용하며 읽기 복제본을 선택하는 Sessions API는 사용하지 않습니다. 인증·권한 조회에서 오래된 복제본을 읽는 경로를 추가하지 않았습니다. 추후 복제를 도입한다면 북마크 전달과 순차 일관성을 별도로 검증해야 합니다. [D1 일관성 문서](https://developers.cloudflare.com/d1/best-practices/read-replication/)

## 보안 경계

1. 서비스 연결 비밀값은 32바이트 난수의 64자리 소문자 hex 형식을 요구합니다. 검증은 일정 시간 비교를 사용합니다. 실제 값은 코드·Git·URL·로그·브라우저에 넣으면 안 됩니다.
2. Worker는 `D1_BRIDGE_ENABLED=1`과 유효한 `D1_BRIDGE_SECRET`이 둘 다 있어야 동작합니다. 미설정 상태는 `503`입니다. 이번 검사에서는 매번 메모리에서 생성한 테스트 비밀값만 사용했습니다.
3. 서비스 비밀값은 연결된 DB의 읽기·쓰기 권한과 동등한 중요도를 가집니다. 이 엔드포인트는 일반 회원 API가 아닙니다. 사용자 인증·권한 판정은 기존 업무 API에서 먼저 수행합니다. 브라우저에 이 비밀값이나 SQL 접근 권한을 제공하면 안 됩니다.
4. 일반 연결은 HTTPS만 허용합니다. 주소의 사용자정보·경로·쿼리·fragment를 거절하고, 요청이 받은 Host/Origin으로 DB 주소를 정하지 않습니다. 리다이렉트는 따라가지 않습니다. 개발용 예외는 명시적인 루프백 연결뿐입니다.
5. 브라우저 Origin이나 Cookie가 포함된 요청은 거절하며 CORS 허용 헤더를 제공하지 않습니다. Sites 신원 헤더·사용자 쿠키는 DB 인증 수단으로 인정하지 않습니다.
6. SQL·매개변수·DB 오류 원문·서비스 비밀값을 오류 메시지에 포함하지 않습니다. 요청·응답 모두 캐시하지 않습니다.
7. 요청/응답 최대 8MiB, 배치 최대 256문장, 문장 최대 100,000 UTF-8 바이트, 문장당 매개변수 최대 100개입니다. 실제 스트림 크기를 검사합니다. 현재 사용 범위는 문자열·유한 숫자·null이며, BLOB·객체·boolean 등을 임의 변환하지 않고 거절합니다.
8. `exec`, `dump`, `raw`, `withSession`은 지원한다고 가장하지 않고 명시적으로 거절합니다. 스키마 배포·내보내기는 별도 운영 절차로 관리해야 합니다.

DB 브리지는 운영 활성화 전 네트워크 접근 제한, 서비스 비밀값 회전, 요청량 제한, 로그의 민감정보 제외, 대상 DB 권한 범위와 실제 지연·최대 데이터 크기를 추가 확인해야 합니다.

## 쓰기 결과가 불확실할 때

HTTP 응답이나 D1 바인딩 응답이 끊겨도 쓰기는 이미 커밋됐을 수 있습니다. 따라서 시간초과·리다이렉트·잘못된 응답·DB 예외를 받았다고 저장이 없었다고 단정하지 않습니다.

연결 계층은 `D1_HTTP_OUTCOME_UNKNOWN`을 반환하고 **자동 재시도하지 않습니다**. 다른 DB나 로컬 저장소로 자동 우회하지도 않습니다. 기존 업무 명령의 안정 ID·영수증·현재 상태를 조회해 결과를 확인해야 합니다. 이때도 조회 응답을 받기 전 완료로 표시하지 않습니다. SQL 제약 오류로 실제 롤백되는 경우와, 커밋 후 응답만 사라지는 경우를 각각 테스트합니다.

## 로컬 실행과 검사

```sh
# 기존 로컬 저장소를 사용하되 SQL 호출만 HTTP 연결로 전환
pnpm run dev:next:local:http

# 실제 Worker 두 개와 공유된 격리 D1에서 기존 업무 시나리오 실행
pnpm run test:d1:http

# 실제 Next 서버, 관리자/파트너 로그인, 파일 저장 및 재시작 검사
pnpm run test:next:local:http
```

일반 `dev:next:local`은 기존 네이티브 D1 연결을 유지합니다. 두 모드의 저장소 이름이 같으면 같은 격리 로컬 DB를 사용하므로 동시에 실행하지 않습니다. 테스트는 별도 `test-*` 저장소를 사용합니다. 개발 모드를 바꿀 때는 서버를 재시작해야 합니다.

Next HTTP 모드에서도 원본 파일은 로컬 R2에 남습니다. **R2 외부 연결이나 대용량 직접 업로드가 구현된 것은 아닙니다.** 파일 검사에서는 SQL 메타데이터와 권한이 HTTP DB 연결을 거쳐도 유지되는지만 확인합니다.

기본/프로덕션 Next API의 `503` 차단은 유지했습니다. 브리지 또는 로컬 플래그를 설정했다고 미완성 Vercel 앱이 자동으로 운영 연결을 시작하지 않습니다. Git 자동 배포도 차단된 상태입니다.

## 검증 결과

2026-09-08 로컬 검사 결과입니다. 실제 운영 데이터와 자격증명은 사용하지 않았습니다.

- Node 테스트 821건 통과. HTTP 연결 신규 검사 18건을 포함합니다.
- 실제 Worker 간 인증된 HTTP 연결과 격리 D1/R2에서 기존 업무 검사 687건 통과. 운영 쓰기·메일·유료 AI·외부 요청은 각각 0건입니다.
- 기존 네이티브 D1 실행 경로에서도 같은 687건을 다시 통과했습니다. 두 경로의 검사 프로세스와 Next 통합검사 서버는 정상 종료했습니다.
- 실제 Next HTTP 모드에서 관리자·파트너 인증, 가입 승인대기, 권한·Origin·세션 전환, 파일 업로드/다운로드, 재시작 보존, 만료·로그아웃·로그인 시도 제한을 확인했습니다.
- Next 프로덕션 빌드, 프로덕션 HTTP 113건, TypeScript, lint를 통과했습니다. 미설정 D1 브리지와 로컬 관리자 구현이 프로덕션 번들에 포함되지 않는 것도 검사합니다.
- `.github/workflows/ci.yml`에 D1 HTTP 호환성 검사를 추가했습니다. GitHub CI 실행 또는 배포가 이루어졌다는 의미는 아닙니다.

네트워크 지연이 있는 실제 클라우드 간 성능, 운영 데이터의 최대 크기, 원격 자원 접근 권한은 아직 검증하지 않았습니다.

## 다음 단계: 비공개 파일 직접 전송

**후속 진행:** 아래 설계의 기업자료·FLOW 경로를 구현하고 네이티브 Worker에서 격리 검증했습니다. 브라우저에 R2 PUT 권한을 주는 staging 방식 대신, 별도 전송 Worker가 기존 전체 검증을 수행한 뒤 원본을 저장합니다. 개별 최대 25MiB, FLOW 두 첨부 합계 30MiB, 만료·정지·로그아웃·중복·중단 검사를 통과했습니다. 서버 측 R2 HTTP 연결도 구현해 기존 업무 687건을 D1/R2 HTTP에서 재검증했습니다. 실제 운영 연결은 남아 있습니다. [파일 직접 전송 기록](PRIVATE_FILE_TRANSFER_MIGRATION.md), [서버 R2 연결 범위](R2_HTTP_MIGRATION.md)를 참고하세요.

Vercel Functions의 요청/응답 본문 한도는 4.5MB이므로 현재 최대 25MiB 원본을 그대로 통과시킬 수 없습니다. DB 연결은 이 제한을 해결하지 않습니다. [Vercel 제한](https://vercel.com/docs/functions/limitations), [직접 전송 안내](https://vercel.com/kb/guide/how-to-bypass-vercel-body-size-limit-serverless-functions)

다음 구현에서는 파일 내용이 Vercel을 경유하지 않는 별도 전송 경로를 검증합니다.

1. Next 업무 API에서 기존 계정·진행·파일 권한과 동의를 확인하고, 파일 ID·용도·크기·MIME에 결속된 짧은 수명의 전송 권한을 발급합니다. DB 서비스 비밀값과는 완전히 별개의 권한입니다.
2. 브라우저는 제한된 임시 저장 위치에만 업로드합니다. 공개 버킷이나 영구 원본 키의 덮어쓰기 권한을 주지 않습니다.
3. 서버는 실제 파일 형식·크기·ETag·MIME·소유권과 최신 권한을 재확인한 뒤 원본 보관과 D1 완료 영수증을 확정합니다. 임시 업로드 권한이 다시 사용되어도 확정된 원본을 바꿀 수 없어야 합니다.
4. 다운로드도 짧은 수명의 전송 권한과 최신 DB/R2 검증을 거칩니다. 영구 공개 URL, 추측 가능한 저장 키, 원본을 로그에 남기는 URL 토큰을 피합니다.
5. 중단·중복 업로드·만료·정지 계정·변조 원본·실패 후 복구·큰 파일을 시험합니다. 기존 원장·멱등성·삭제 규칙을 유지합니다.

이 파일 전송 단계와 운영 인증/계정 복구, 대상 저장소 연결, 데이터 대조·롤백 검증이 끝나기 전에는 운영 전환을 진행하지 않습니다.
