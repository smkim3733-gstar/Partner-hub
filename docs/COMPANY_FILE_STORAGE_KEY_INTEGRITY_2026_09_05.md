# 기업자료 R2 저장 키 무결성 경계

기준일: 2026-09-05

## 문제

기업자료 원본 행의 `storage_key`가 파일 ID·기업·진행 원장과 함께 고정되지 않았다. D1 행이 다른 R2 비공개 객체의 키로 바뀌어도 파일명·크기·MIME·ETag 조건이 우연히 맞으면 다운로드, 상담 유입, Step 0, 원본 증빙, 회수와 보관 현황 확인이 잘못된 객체에 접근할 수 있었다.

처음에는 모든 키를 `company-source/{파일 ID}`로 강제하는 방안을 검토했다. 그러나 기존 운영 자료에는 다른 형식의 정상 키가 존재하므로 이 방식은 가산 마이그레이션 직후 레거시 원본을 차단한다. 기존 키를 추정하거나 변경하지 않고, 현재 저장된 정확한 키를 별도 원장에 결속하는 방식으로 수정했다.

## 적용

- 가산 마이그레이션 `0018_company_file_storage_key_integrity.sql`이 `company_file_storage_keys` 원장을 만든다.
- 원장은 파일 ID를 기본·외래 키로, 정확한 R2 저장 키를 고유값으로 보존한다.
- 마이그레이션은 기존 `company_file_objects.storage_key`를 그대로 백필한다. 런타임은 누락 원장을 자동 생성하지 않는다.
- 신규 업로드는 원본 행, 객체 무결성 원장, 저장 키 원장, 담당·진행 연결과 정상 상태 원장을 하나의 D1 batch로 저장한다.
- 정상 상태 판정은 같은 파일 ID의 저장 키 원장이 정확히 일치할 때만 성립한다.
- 다운로드, 상담 유입, Step 0, 원본 증빙, 회수와 업로드 재시도는 R2 접근 전에 저장 키 원장을 대조한다.
- 대표 전용 원본 보관 목록과 R2 존재 확인도 키 원장 누락·불일치를 먼저 `메타데이터 확인 필요`로 분류한다.
- 파일 삭제 시 저장 키 원장도 원본 행과 함께 명시적으로 정리한다.

## 검증

- 다른 비공개 객체 키로 바꾼 D1 행은 다운로드 전에 HTTP 503으로 격리되고 R2 `get`은 호출되지 않는다.
- 마이그레이션 전 임의 형식 키 `synthetic-private-file`은 정확한 기존 키로 백필되어 계속 접근할 수 있다.
- Node 회귀 검사 609/609 통과
- 격리 workerd/D1/R2 검사 420/420 통과
- 타입검사, 전체 lint, 프로덕션 빌드 통과
- 로컬 운영 Worker `/`, `/account`, `/account/setup` HTTP 200과 CSP, `X-Frame-Options: DENY`, `nosniff`, `no-referrer` 확인
- 실제 운영 쓰기, 이메일 발송, 유료 AI 요청, 외부 요청 0건
