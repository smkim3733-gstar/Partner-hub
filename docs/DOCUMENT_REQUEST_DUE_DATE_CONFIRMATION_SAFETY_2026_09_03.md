# 누락 요청서류 제출기한 변경 확인 안전성

## 문제

진행 화면의 `기한 일괄 저장`은 한 번 제출하면 기한이 없던 요청서류, `기한 확인` 연결 업무와 진행 타임라인을 즉시 바꾸고 상위 자동저장으로 이어졌다. 저장 전 취소할 수 없었고, 선택 뒤 진행·담당·자료상태·연결 업무나 한국 날짜 기준이 바뀌어도 이전 화면의 영향을 그대로 적용할 수 있었다.

## 변경

- 날짜 제출은 원본 자료·업무·타임라인을 바꾸지 않고 확인 초안만 만든다.
- 확인 초안마다 UUID 요청 ID를 고정하고 타임라인 ID를 결정적으로 만든다. 같은 확인의 빠른 이중 실행은 동일 결과만 계산하며 이미 저장된 ID는 중복 적용을 차단한다.
- 확인창에서 기업·진행, 대상 요청서류, 변경 후 날짜와 `예정`·`오늘 마감`·`기한 지연`, 연결 업무 수와 알림 영향을 확인해야 저장할 수 있다.
- 취소하거나 확인창을 닫으면 초안을 폐기하고 기존 상태를 유지한다.
- 저장 직전 현재 계정의 자료 권한, 진행 ID·기업·담당 계정, 기한 없는 `요청중`·`보완필요` 요청서류 전체 목록과 연결 업무를 다시 검사한다.
- 다른 반복 진행의 같은 기업 자료·업무는 포함하지 않으며, 모호한 레거시 연결이나 대상 식별자 충돌은 거절한다.
- 선택 뒤 자료명·상태·담당·기한 또는 연결 업무의 담당·상태·기한이 바뀌면 적용하지 않고 최신 화면 확인을 요구한다.
- 확인 사이 한국 날짜가 바뀌어 알림 영향이 달라지면 다시 확인해야 한다.
- 저장하면 대상 자료의 기한, 연결 업무의 기한·마감상태·우선순위와 전체 타임라인을 하나의 계산 결과로 함께 반영한다.
- 초안 생성 실패 시 입력 날짜를 지우지 않아 사용자가 바로 수정할 수 있다.

## 유지한 운영 경계

- 기존에 날짜가 있는 자료·업무는 일괄 수정하지 않는다.
- 새 외부 알림, 메일·메신저 발송, 유료 AI·외부 API 호출을 추가하지 않았다.
- 기존 진행·자료·업무 접근권한, 서버 저장 검증, revision/CAS, DB/R2 스키마·보관 정책을 변경하지 않았다.
- 과거 운영 기록을 자동 이관하거나 수정하지 않는다. 이후 사용자가 확인한 누락 기한 보정에만 적용한다.
- GitHub 푸시와 공개 Sites 배포는 사용자 승인 전까지 수행하지 않는다.
