# 상담 FLOW 파일명 무결성 경계

기준일: 2026-09-05

## 확인한 문제

FLOW 업로드는 공용 파일명 정규화로 NFC Unicode, 경로 구분자 제거, 제어문자 치환, 앞뒤 공백 제거와 180자 상한을 적용했다. 그러나 저장 payload 검증은 파일명을 공백이 아닌 제한 길이 문자열로만 확인했다. 손상된 D1 payload의 경로형 이름, 제어문자, NFD 이름과 업로드 상한보다 긴 이름이 상세 응답과 다운로드 판단에 전달될 수 있었다. 대시보드는 파일 배열을 SQLite에서 제거한 뒤 축소 구조를 검사하므로 같은 손상을 발견하지 못했다.

## 적용한 경계

- 저장 FLOW 파일명은 새 업로드와 동일한 공용 `safeFileName` 결과와 정확히 일치해야 한다.
- NFC Unicode, `\\`·`/` 치환, 제어문자·잘못 구성된 surrogate 치환, 앞뒤 공백 제거와 확장자를 보존하는 180자 상한을 하나의 규칙으로 사용한다.
- 상세 조회와 다운로드는 비정규 파일명을 R2에서 읽기 전에 HTTP 503으로 격리한다.
- 대시보드는 SQLite 축소 전에 파일명만 별도로 추출해 같은 JavaScript 정규형 검사에 통과시킨다. 보고서 본문·전사문·파일 키는 추가로 읽지 않는다.
- 손상 파일명이 연결된 R2 객체는 읽거나 삭제하지 않고 그대로 보존한다.
- D1 스키마, R2 원본, 인증·권한, 보관·삭제 정책은 변경하지 않았다.

## 검증

- 경로 구분자, 앞 공백, NFD Unicode, NUL 제어문자, 180자 초과 이름을 각각 주입해 상세 조회·대시보드·다운로드가 모두 HTTP 503으로 실패하는지 확인했다.
- 실제 workerd+D1+R2에서 `folder/report.txt` 손상 이름을 주입하고 세 경로가 모두 차단되며 객체가 보존되는지 확인했다.
- Node 자동 테스트 593/593 통과.
- 격리 workerd+D1+R2 검사 398/398 통과.
- 타입검사, 전체 lint, 변경 파일 포맷 검사, 프로덕션 빌드 통과.
- 로컬 프로덕션 `/`, `/account`, `/account/setup` HTTP 200과 CSP·`DENY`·`nosniff`·`no-referrer` 확인.
- 실제 운영 쓰기, 메일 발송, 유료 AI 요청, 외부 요청 0건.
