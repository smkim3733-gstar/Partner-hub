# 원본 보관 목록 무결성 원장 분류

기준일: 2026-09-05

## 확인한 문제

버전 164는 개별 원본 무결성 확인에서 D1 객체 원장 누락과 불일치를 정확히 표시했지만, 보관 목록의 최초 분류는 기업 원본 메타데이터 존재 여부만 확인했다. 객체 무결성 원장이 없거나 고정 MIME과 결속되지 않은 파일도 개별 확인 버튼을 누르기 전까지 `연결 확인 필요` 또는 `자료·상담 연결`로 보일 수 있었다.

## 적용한 분류

- 보관 목록 SQL이 `company_file_object_integrity`를 기업 원본 ID로 함께 확인한다.
- 객체 원장 존재, 저장 고정 MIME 일치, `metadata` 모드의 null ETag, `etag` 모드의 공백 없는 1~256자 ETag를 구조적으로 검증한다.
- 완료·레거시 기업 원본의 객체 원장이 누락되거나 구조가 일치하지 않으면 연결 여부보다 먼저 `메타데이터 확인 필요`로 분류한다.
- 업로드 확인 대기와 삭제 기록은 기존 작업 상태가 우선한다. 메타데이터 자체가 없는 완료 기록도 기존처럼 `메타데이터 확인 필요`로 유지한다.
- 목록 조회는 R2에 접근하지 않는다. 객체 존재·크기·MIME·ETag의 실제 대조는 대표가 `원본 무결성 확인`을 눌렀을 때만 수행한다.
- 저장 키·ETag·요청 지문·원문을 목록 응답에 포함하지 않고 기존 관리자 전용 권한과 25건 페이지 제한을 유지한다.

## 검증

- 객체 무결성 원장이 없는 완료 기업 원본과 저장 MIME이 다른 원장이 목록에서 `메타데이터 확인 필요`로 분류되는지 확인했다.
- 정상 원장이 있는 미연결·진행 연결·자료 연결 원본의 기존 분류가 유지되는지 확인했다.
- 업로드 대기·삭제·메타데이터 누락 상태의 기존 우선순위와 페이지네이션이 유지되는지 확인했다.
- 실제 격리 workerd/D1에서 원장 없는 기업 원본이 R2 접근 전에 불일치 목록에 나타나는지 확인했다.
- 전체 Node 자동 테스트 607/607 통과.
- 격리 workerd+D1+R2 검사 418/418 통과. 실제 운영 쓰기, 메일 발송, 유료 AI 요청, 외부 요청 0건.
- 타입검사, 전체 lint, 변경 파일 포맷 검사, `git diff --check`, 프로덕션 빌드 통과.
- 로컬 프로덕션 `/`, `/account`, `/account/setup` HTTP 200과 CSP·`DENY`·`nosniff`·`no-referrer` 확인.
