# 상담 FLOW 본문 처리 중 사건·담당 계정 삭제 경쟁 무결성

기준일: 2026-09-07

## 확인한 위험

부분 R2 실패 뒤 정확한 전사문·음성 재시도가 multipart 본문을 읽는 동안 사건과 담당 계정이 모두 삭제되면, 본문 읽기 전에 확인한 권한으로 R2 객체나 FLOW를 계속 저장할 수 있다. 삭제된 계정의 안정 ChatGPT 결속이 남거나 기존 부분 객체와 예약을 오류 정리로 없애도 접근 폐기와 안전한 재시도를 보장할 수 없다.

## 확인한 현재 경계

- 첫 전사문 객체 저장 성공과 두 번째 음성 저장 실패로 기존 전사문 객체와 두 `pending` 예약이 남은 상태를 결정적으로 재현했다.
- 같은 명령 ID·본문·첨부의 정확한 multipart 재시도가 첫 본문 청크를 읽을 때 지원되는 관리자 상태 저장 API를 두 번 실행했다. 첫 저장은 사건을 삭제하면서 담당 계정을 정지했고, 두 번째 저장은 배정 레코드가 없어진 정지 계정을 삭제했다.
- 계정 삭제 저장은 기존 안정 ChatGPT 사용자 ID·회원 ID 결속을 같은 D1 상태 변경 안에서 폐기했다.
- 본문 처리가 끝난 뒤 R2 쓰기 전 인증·신원 결속·담당 접근 검사가 삭제된 회원을 활성 파트너로 인정하지 않아 403으로 끝난다. 재시도의 새 R2 쓰기와 FLOW·명령 영수증·파일 원장·완료 원장 D1 쓰기는 모두 0건이다.
- 사건·회원 삭제와 결속 폐기는 보존된다. 기존 FLOW와 명령 영수증은 변하지 않고 기존 전사문 객체와 두 `pending` 예약은 원래 파일 ID·R2 키로 복구 가능하게 유지되며, 음성 객체는 거부 전에 새로 생성되지 않는다.
- 사건과 회원 원본을 복구해도 폐기된 결속은 되살아나지 않는다. 같은 안정 ChatGPT 사용자 ID가 같은 명령 ID·본문·첨부로 다시 요청하면 정확한 회원 ID에 재결속하고 같은 두 파일 ID·R2 키를 재사용해 FLOW, 명령 영수증, 두 `ready` 예약과 완료 원장을 한 번만 커밋한다.

기존 구현이 multipart 본문 처리 뒤 R2 쓰기 전에 인증·신원·담당 접근을 다시 확인하고 계정 삭제 시 안정 신원 결속을 폐기해 요구 조건을 만족한다. 런타임 코드는 바꾸지 않고 지원 관리자 경로의 사건·담당 계정 연속 삭제와 본문 읽기 경쟁 회귀 증거를 추가했다.
