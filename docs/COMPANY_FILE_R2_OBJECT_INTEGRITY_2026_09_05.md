# 기업자료 R2 객체 무결성 경계

기준일: 2026-09-05

## 확인한 문제

버전 162까지 기업자료 원본은 D1 원장의 저장 키와 크기를 R2 객체와 대조했지만, 정상 객체를 같은 크기의 다른 바이트로 교체하면 다운로드와 일부 내부 소비 경로가 이를 식별하지 못했다. R2 객체의 `httpMetadata.contentType`을 다른 값으로 바꿔도 저장된 고정 MIME과 별도로 대조하지 않았다.

## 적용한 경계

- 가산 `0017_company_file_object_integrity.sql` 마이그레이션과 `company_file_object_integrity` 원장을 추가했다.
- 신규 기업자료 업로드는 R2 저장 결과의 키·크기·고정 MIME·ETag를 확인한 뒤 기업 원본·객체 무결성·담당 배정·진행 연결·정상 상태 원장을 하나의 D1 batch에 저장한다.
- 신규 파일은 `etag` 검증 모드로 저장한다. ETag가 없거나 너무 길거나 R2 객체 메타데이터가 업로드 설명과 다르면 원장 확정 전에 실패한다.
- 기존 파일은 배포 마이그레이션에서 `metadata` 검증 모드로 명시한다. 과거 R2 ETag를 추정하지 않으며 저장 키·크기·고정 MIME을 계속 확인한다.
- 다운로드는 본문 반환 전에 객체 무결성을 확인하고, 권한·삭제 상태·현재 D1 행을 다시 읽은 뒤 처음 확인한 객체 원장과 정확히 같은지 대조한다.
- 상담 유입자료, Step 0 생성 전 점검, 기업자료 카드 원본 증빙, 미연결 원본 회수도 R2 본문 사용이나 외부 요청 전에 같은 객체 무결성을 확인한다.
- 정상 업로드 재시도는 기존 R2 객체와 D1 객체 원장을 다시 대조한다. 누락·잘못된 모드·ETag·MIME 불일치는 자동 복구하지 않고 실패 폐쇄한다.
- 삭제는 객체 무결성 원장을 명시적으로 제거한 뒤 기업 원본 행을 제거한다. 실제 R2 삭제와 기존 보관 정책은 바꾸지 않았다.

## 검증

- 동일 크기의 다른 바이트로 R2 객체를 교체하면 다운로드·상담 유입자료·Step 0·기업자료 증빙·회수·업로드 재시도가 실패하는지 확인했다.
- R2 객체 MIME만 다른 허용값으로 바꿔도 본문 반환과 내부 소비가 실패하는지 확인했다.
- 객체 무결성 원장을 삭제하면 모든 실제 소비 경로가 실패하고 런타임이 현재 객체값으로 원장을 재생성하지 않는지 확인했다.
- 신규 업로드의 실제 workerd R2 ETag·MIME과 D1 원장값이 일치하는지 확인했다.
- Step 0가 객체 변조를 외부 AI 요청 전에 차단하는지 확인했다.
- 이전 마이그레이션 상태에서 전체 18개 가산 마이그레이션을 적용해 기존 기업 원본이 명시적 `metadata` 모드로 보존되는지 확인했다.
- 전체 Node 자동 테스트 607/607 통과.
- 격리 workerd+D1+R2 검사 417/417 통과. 실제 운영 쓰기, 메일 발송, 유료 AI 요청, 외부 요청 0건.
- 타입검사, 전체 lint, 변경 파일 포맷 검사, `git diff --check`, 프로덕션 빌드 통과.
- 로컬 프로덕션 `/`, `/account`, `/account/setup` HTTP 200과 CSP·`DENY`·`nosniff`·`no-referrer` 확인.

## 남은 경계

가산 마이그레이션은 기존 R2 객체의 ETag를 D1 값만으로 신뢰해 백필하지 않는다. 기존 객체는 크기와 고정 MIME을 검증하지만 별도 운영 이관 전까지 같은 크기 바이트 교체를 식별할 수 없다. 실제 객체를 읽어 해시·소유권·백업을 확인하는 이관은 운영 데이터 읽기와 복구 계획이 필요한 작업이므로 자동 실행하지 않는다.

다음 자동 감사는 대표용 원본 보관 현황이 새 객체 무결성 원장의 누락·불일치를 정확히 진단하고 오해 가능한 정상 표시를 하지 않는지 확인한다.
