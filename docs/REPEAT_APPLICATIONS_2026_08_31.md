# 동일 기업 재신청·첨부자료 연결 — 2026-08-31

## 변경

같은 기업명이 이미 있으면 새 진행 생성을 생략하던 처리를 제거했다. 기업명·담당자가 같아도 새 협업신청마다 별도 진행 ID를 만들며, 타임라인과 신청 첨부자료는 같은 진행 ID를 사용한다. 진행판·상담 FLOW 선택·자료함에서 진행번호의 끝 8자리를 표시하며 상세 화면에는 전체 진행번호를 유지한다.

새 신청 파일의 진행 ID를 `company_file_case_links`에 저장한다. 기존 파일 메타데이터와 담당 계정 ID를 그대로 사용하며, 추가형 마이그레이션 `0005_company_file_case_links.sql`로 연결 테이블만 만든다. 파일 메타데이터·담당 계정·진행 연결을 한 D1 배치에서 저장하고, 파일 삭제 시 연결도 정리한다. DB 배치 저장 실패 시 새 R2 객체를 정리하는 기존 동작을 유지한다.

진행이 아직 저장되기 전에도 신청 파일 업로드는 가능하지만 진행 ID 자체는 접근 권한을 부여하지 않는다. 기존 진행을 지정한 업로드는 기업명과 담당 계정을 확인하며, 이미 시작한 상담 FLOW의 서버 저장 정보를 우선한다. 자료 검토·본문 확인·자료 반영은 기업명·담당 계정에 더해 파일에 저장된 진행 ID도 일치해야 한다.

새 요청서류에도 진행 ID와 담당 계정 ID를 연결한다. 진행 상세의 서류와 관련 업무 기한 변경은 기업명만으로 다른 신청의 기록을 함께 선택하지 않는다. 과거 서류의 연결 대상이 여러 진행으로 겹치면 상세 화면에서 추정해서 표시하지 않는다. 원본은 기업별 자료함에 남는다.

## 호환과 제한

- 과거 파일·서류·업무에 진행 ID를 일괄 채우거나 기존 데이터를 삭제하지 않는다.
- 기업별 자료함에서 일반 등록한 파일과 기존의 진행 미연결 파일은 기업·담당 계정 기준의 공통 검토 후보로 남는다. 대표는 자료의 적합성을 직접 확인해야 한다. 이번 분리는 진행 ID가 저장된 새 신청 첨부에 적용된다.
- 신청서 저장은 기존 자동 저장 흐름을 유지한다. 파일 업로드 완료와 최종 상태 저장은 구분되므로 상단 저장 완료 표시를 확인해야 한다. 네트워크 장애 시 모든 브라우저 재시도까지 하나의 접수로 합치는 서버 접수 API를 새로 만든 것은 아니다.
- 진행 담당자 변경에 따른 원본파일 재배정과 과거 연결 복구는 자동으로 수행하지 않는다.

## 검증 범위

자동 테스트 99개와 격리 workerd/D1/R2 확인 53개를 통과했다. 같은 기업·같은 계정의 두 신청에 대해 진행·타임라인·첨부를 저장 후 다시 읽고, 다른 진행의 신규 파일을 검토·가져오기 대상으로 사용할 수 없는지 확인했다. 기존 진행의 다른 계정·기업, 잘못된/중복 진행번호, 서버에 저장된 FLOW 담당자와의 불일치를 거부한다. 마이그레이션 6개 반복 적용 후 기존 파일과 새 연결을 보존했다.

브라우저 클릭 시험·실제 운영 계정 생성·고객 자료 조회·메일 전송·유료 AI 호출은 수행하지 않았다. 선행 배포는 버전 36, 소스 `ff5345b`이며, 이번 변경의 최종 배포 결과는 배포 이력과 로컬 `outputs/release/` 완료 기록에 남긴다.
