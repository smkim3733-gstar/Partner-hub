# Next.js / Vercel 이전 기반

> 2026-09-09: 새 배포 기준은 [Vercel Marketplace Turso + 비공개 Blob](VERCEL_STORAGE.md)입니다. 아래 Cloudflare HTTP 관련 내용은 이전 단계 기록이며 새 배포의 필수 조건이 아닙니다.

## 현재 범위

- 브랜치: `codex/vercel-migration`
- 기준 소스: `6f5061c4d2eb6de614ef898ca9fe9d548c021afc`
- 준비일: 2026-09-08
- 공식 Next.js `16.3.4`를 기존 vinext/Sites 실행 경로와 병행 설치했습니다.
- 기존 화면·업무 규칙·SQL 마이그레이션을 유지하고, 플랫폼 의존 부분을 분리하기 시작했습니다.
- **완성된 서비스 이전이나 Vercel 배포가 아닙니다.** 운영 DB, 파일, 도메인, 비밀값은 이동하거나 변경하지 않았습니다.

## 로컬 명령

Node.js 22.13 이상과 저장소에 지정된 pnpm 버전을 사용합니다. CI는 Node.js 24.19.0과 pnpm 11.19.0을 사용합니다.

```sh
pnpm install --frozen-lockfile
pnpm run dev:next
```

Next.js 화면 주소는 `http://127.0.0.1:3001/account`입니다. 빌드 및 독립 서버 검사는 다음과 같습니다.

```sh
pnpm run build:next
pnpm run test:next
pnpm run start:next
```

`test:next`는 빌드된 서버를 임시 로컬 포트에서 실행하고 검사 후 종료합니다. `build:next`를 먼저 실행해야 합니다.

기존 Sites 명령 `dev`, `build`, `start`, `verify`는 그대로 유지됩니다. 두 도구가 생성 파일 `next-env.d.ts` 및 `.next` 일부를 사용하므로 Next와 vinext의 개발/빌드를 동시에 실행하지 마세요. 실행 경로를 바꿀 때에는 해당 경로로 다시 빌드합니다. 생성 파일은 Git에 포함하지 않습니다.

## 런타임 경계

기존 `cloudflare:workers` 직접 참조 10곳을 `@/lib/platform-runtime`으로 모았습니다.

- Sites 기본 모듈은 기존 `env`, `waitUntil`을 그대로 내보냅니다.
- Next.js는 `next.config.ts`의 Turbopack 별칭과 `tsconfig.next.json`으로 Node 전용 모듈을 선택합니다.
- Node 전용 모듈의 `waitUntil`은 Next.js `after`에 연결합니다. 장시간 작업의 완료 보장은 별도 설계가 필요합니다.
- 기본 Node 모듈에 D1/R2 연결은 없습니다. 로컬 opt-in과 별도로, 명시적 빌드 선택·런타임 opt-in을 모두 요구하는 독립 HTTPS 연결 후보를 추가했습니다. 실제 운영 계정은 미연결입니다. [독립 운영 연결과 검증 범위](NEXT_REMOTE_BACKEND.md)를 참고하세요. `process.env.DB` 같은 문자열을 DB 바인딩으로 취급하거나 테스트 데이터를 운영 데이터로 대체하지 않습니다.
- Next 전용 환경변수의 이름과 기본 비활성화 설정은 `.env.example`에 있습니다. 실제 값은 Git에서 제외되는 `.env.local`에 보관합니다. Sites의 `.dev.vars`를 복사하거나 출력하지 마세요.

## 인증과 임시 API 차단

Sites의 `oai-authenticated-user-*` 헤더는 Sites 인증 프록시가 검증해 주는 신원입니다. 일반 Node/Vercel에서는 클라이언트가 위조할 수 있으므로 Next 경로에서는 무시합니다. 기존 ChatGPT 관리자 로그인 버튼도 숨깁니다. 독립 관리자 인증은 로컬 및 명시적 원격 연결 후보에 구현했지만, 실제 운영/Vercel 계정으로 활성화하지 않았습니다.

기본 Next 프리뷰와 프로덕션 빌드에서는 모든 `/api/*` 요청에 다음 응답을 반환합니다. 명시적 로컬 모드 또는 모든 설정을 검증한 별도 원격 빌드만 예외입니다.

```json
{
  "code": "MIGRATION_BACKEND_NOT_CONFIGURED",
  "error": "Next.js 이전 준비 중입니다. DB·파일 저장소·독립 인증 연결 전에는 업무 API를 사용할 수 없습니다. 기존 운영 사이트를 이용해 주세요."
}
```

HTTP 상태는 `503`, 캐시는 `private, no-store, max-age=0`입니다. 이는 운영 저장소 연결 전의 명시적인 임시 차단이며, 전체 서비스 이전 완료를 의미하지 않습니다. 기본/프로덕션 모드에서는 로그인·가입·자료 업로드·AI 생성을 사용할 수 없습니다. Sites 기본 런타임에서는 이 차단이 꺼져 있으며 기존 라우트 인증이 유지됩니다.

## Next.js 로컬 저장소 연결 단계

```sh
pnpm run dev:next:local
```

이 명령은 `127.0.0.1:3001`에서 Next.js 개발 서버를 실행합니다. Cloudflare의 로컬 개발 프록시를 이용해 실제 SQLite 기반 D1과 로컬 R2 에뮬레이터를 연결합니다. [Cloudflare 문서](https://developers.cloudflare.com/workers/wrangler/api/#getplatformproxy)의 개발용 연결이며 Vercel의 영구 저장소가 아닙니다.

- 원격 바인딩을 명시적으로 끄고, 운영 `.dev.vars`/`.env` 파일을 프록시에 넘기지 않습니다.
- 파일과 DB는 Git에서 제외된 `.wrangler/next-local/development/v3`에 남습니다. Sites 개발 저장소와도 구분합니다.
- 기존 SQL 마이그레이션 99개와 로컬 전용 관리자 마이그레이션 1개를 순서대로 적용하고 해시를 기록합니다. 로컬 전용 파일은 `dev/next-local/migrations`에 두고 적용 기록에 `next/` 접두사를 사용합니다. 운영 `drizzle` 파일과 스키마에는 추가하지 않습니다. 다시 시작하면 적용된 항목은 건너뛰고, 적용된 파일이 변경되었으면 중단합니다.
- 최초 로컬 DB에는 빈 운영 기준선만 만듭니다. 운영 회원·기업자료를 복사하거나 데모 계정·관리자를 자동 생성하지 않습니다.
- 새 가입은 기존 규칙대로 승인대기입니다. 운영 계정으로 즉시 로그인할 수는 없습니다. 로컬 관리자도 아래 최초 설정을 직접 실행해야 사용할 수 있습니다.
- `NODE_ENV=development`, 명시적 opt-in, Vercel 환경 표시 부재가 모두 필요합니다. `production`, `test`, Vercel 환경에서는 이 연결을 사용하지 않습니다.
- 프로덕션 빌드는 별칭으로 비활성 모듈만 선택합니다. 로컬 DB 서버를 Vercel에서 실행하려는 구성이 아닙니다.
- 로컬 연결 중에는 서버 AI 키를 제공하지 않고 외부 AI 처리를 강제로 비활성화합니다.
- Windows 경로 길이를 고려해 저장소 이름은 1~16자의 소문자·숫자·하이픈만 허용합니다. 긴 경로나 경로 이동 문자열은 받지 않습니다.
- Wrangler/Miniflare 개발 레지스트리도 각 로컬 저장소의 `registry` 아래로 지정합니다. 기본 사용자 전역 레지스트리를 공유하지 않습니다.

실제 서버의 저장소 검사는 다음 명령으로 재현합니다.

```sh
pnpm run test:next:local
```

테스트는 별도의 `test-*` 저장소에 합성 관리자·파트너 자격증명과 파일만 준비합니다. Next.js HTTP API에서 비밀번호 로그인·세션, 가입 승인대기, 상태/초안 조회, 역할별 권한, 위조 Sites 헤더 거절, 파일 업로드/다운로드, 재시작 후 보존, 로그아웃 후 세션 폐기를 확인합니다. 관리자와 파트너 간 계정 전환, 관리자 Origin 검사, 만료·중복 쿠키 거절, 로그인 시도 제한도 검사합니다. 테스트용 활성 계정은 이 검사 전용 저장소에만 존재합니다. 설정 CLI와 동일한 로컬 TypeScript 로더를 사용하며, Sites 바인딩을 테스트용 DB로 바꿔 끼우지 않습니다.

## 로컬 관리자 최초 설정

로컬 Next 서버를 중지한 상태에서 실제 터미널에 다음 명령을 실행합니다.

```sh
pnpm run admin:next:local
pnpm run dev:next:local
```

첫 명령에서 15~128자의 로컬 전용 비밀번호를 두 번 직접 입력합니다. 입력은 화면에 표시되지 않으며, 명령행 인수·파이프·환경변수로 비밀번호를 받지 않습니다. 실제 운영 비밀번호를 재사용하지 마세요. 설정 후 `http://127.0.0.1:3001/account`의 기존 이메일/비밀번호 양식으로 로그인합니다. 이메일은 기존 지정 대표 주소이며, 이메일 일치만으로 권한이 생기지는 않습니다.

- 공개 가입·첫 로그인으로 관리자를 생성하지 않습니다. 로컬 파일시스템 접근 권한이 있는 사용자가 CLI를 직접 실행해야 합니다. 이번 개발에서는 기본 `development` 저장소의 실제 관리자를 생성하지 않았습니다.
- 최초 설정만 지원하며, 이미 설정된 계정의 비밀번호를 덮어쓰지 않습니다. 재설정·복구·다중 관리자 기능은 아직 제공하지 않습니다.
- 기존 scrypt 비밀번호 해시를 사용하며 원문 비밀번호를 저장하지 않습니다. 세션에는 32바이트 난수를 쓰고 DB에는 SHA-256 해시만 저장합니다.
- 관리자 세션은 최대 1시간입니다. 기존 파트너 세션 12시간 정책은 유지합니다. `HttpOnly`, `SameSite=Strict`를 사용하고 HTTPS에서는 `__Host-` 쿠키와 `Secure`를 적용합니다.
- 관리자 조회·쓰기 시 활성 상태, 자격증명 버전, 세션 만료를 검증합니다. 쓰기는 기존 동일 Origin 검사를 통과해야 합니다.
- 로그인과 관리자/파트너 계정 전환 시 쿠키를 새로 발급하고 이전 세션을 폐기합니다. 로그아웃도 서버 DB에서 해당 세션을 삭제합니다.
- 최초 설정·로그인·로그아웃·관리자에서 파트너로 전환한 이력을 로컬 감사 테이블에 남기되 비밀번호와 세션 토큰은 남기지 않습니다.
- 로컬 관리자 모듈은 명시적으로 활성화한 `next dev`에서만 연결됩니다. Sites 기본 모듈은 비활성 동작을 유지하고, Next 프로덕션 빌드에서도 로컬 관리자 구현을 제외합니다.

이는 운영용 독립 인증의 검증 단계입니다. 실제 Vercel 인증 연결, MFA/계정 복구, 운영용 세션 저장소 및 신뢰 가능한 분산 요청 제한은 별도 구현·검증이 필요합니다. 로컬 관리자 테이블이나 테스트 비밀번호를 운영으로 복사하면 안 됩니다.

호환성 검사에서 Next.js의 로컬 URL 정규화가 `127.0.0.1`을 `localhost`로 바꿔 기존 Origin 검사와 충돌하는 문제를 확인했습니다. `skipProxyUrlNormalize`로 원래 요청 URL을 보존하며, 다른 Origin을 허용하거나 임의 전달 헤더를 신뢰하도록 변경하지 않았습니다.

Next.js가 개발 중 자동 생성하는 에이전트 지침 파일은 `agentRules: false`로 비활성화했습니다. 이번 실행에서 자동 생성된 파일만 제거했으며 기존 사용자 지침은 변경하지 않았습니다.

Next 경로의 요청 제한 식별자는 현재 보수적인 공유 키입니다. Vercel이 보장하는 프록시 환경에 맞는 신뢰 경계를 검증하기 전까지 `cf-connecting-ip` 또는 임의 `x-forwarded-for`를 신뢰하지 않습니다. 실제 사용자 서비스 전 분산 요청 제한을 설계해야 합니다.

## Vercel 설정

`vercel.json`에 공식 Next.js 프레임워크, `build:next`, `dev:next`, frozen-lockfile 설치를 지정했습니다. `git.deploymentEnabled: false`로 Git 연동 자동 배포를 차단했습니다. CLI 수동 배포까지 막는 보안 장치는 아니므로 이 단계에서 운영 배포하면 안 됩니다. Vercel 프로젝트 연결, 환경변수 등록, 도메인 변경은 하지 않았습니다.

`.github/workflows/ci.yml`에는 기존 Sites 전체 검사와 분리된 Next 빌드·HTTP 검사 작업을 추가했습니다. 로컬 검증 결과와 GitHub CI 실행 여부는 구분합니다.

## 다음 구현 순서

1. **저장소 접근과 이관 가능성 확인**: Sites가 관리하는 D1/R2의 실제 내보내기·외부 접근 권한을 확인합니다. 소스 저장소만으로 운영 데이터가 확보된 것은 아닙니다. 이 단계에서는 읽기 전용으로 접근 가능성만 조사합니다.
2. **DB 전략 결정 및 시험**: D1을 인증된 Worker API 뒤에 유지하는 후보를 구현하고 격리 검증했습니다. 99개 SQL 마이그레이션과 SQLite JSON/트리거 기반 불변식을 유지하며 실제 동시성·CAS·원장 검사를 재사용합니다. 운영 계정에는 아직 연결하지 않았습니다. [D1 HTTP 연결 범위·보안 경계·파일 전송 후속 계획](D1_HTTP_MIGRATION.md)을 참고하세요.
3. **독립 로그인·관리자 권한**: 로컬 및 원격 후보의 관리자 최초 설정·로그인·권한·세션을 구현하고 합성 HTTPS 환경에서 검증했습니다. 실제 대상 연결, MFA/계정 복구와 기존 회원 비밀번호 이관 정책은 남아 있습니다. 기존 세션을 무조건 재사용하거나 이메일 일치만으로 관리자 권한을 주지 않습니다.
4. **비공개 파일 저장소**: R2 외부 접근 또는 다른 저장소를 결정합니다. 현재 최대 25MiB 파일 경로를 Vercel Functions 요청/응답 제한 4.5MB에 그대로 통과시키지 않습니다. 직접 업로드/다운로드 및 완료 확정 흐름에서 기존 원본 무결성·소유권·멱등성을 보존합니다.
5. **AI 작업 실행**: 플랫폼 실행 시간 제한에 맞춰 내구성 있는 작업 대기열과 재시도를 검토합니다. 키만 추가했다고 기존 작업 수명주기가 이전된 것은 아닙니다.
6. **통합 프리뷰**: 독립 로그인, 관리자/파트너 접근 제어, 신청·조회·수정·파일 흐름을 연결한 뒤 임시 API 차단을 제거합니다. 사이트 URL/메타데이터, 쿠키·Origin·요청 제한, 오류 노출, 환경별 비밀값을 함께 점검합니다.
