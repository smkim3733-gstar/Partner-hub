# 기업자료 삭제 저장 키 무결성 경계

기준일: 2026-09-05

## 문제

기업자료 다운로드·AI 입력·회수·보관 진단은 정확한 R2 저장 키 원장을 확인하지만 명시적 삭제는 같은 검사를 거치지 않았다. D1 원본 행의 `storage_key`가 다른 비공개 객체 키로 바뀐 상태에서 삭제를 요청하면, 권한과 포털 연결 조건만 통과한 뒤 그 다른 R2 객체를 삭제할 수 있었다.

검사 직후 저장 키가 바뀌는 경쟁도 삭제 결정을 다시 확인하지 않으면 같은 위험을 만든다.

## 적용

- 삭제 권한과 포털 카드 연결 여부를 확인한 뒤 `company_file_storage_keys`의 파일 ID·정확한 키 결속을 검사한다.
- 키 원장 누락·불일치는 R2 `delete` 전에 HTTP 503 무결성 오류로 격리한다.
- 내구성 삭제 결정 SQL도 `company_file_storage_keys`를 조인하고 원본 행과 원장 키가 정확히 같을 때만 삭제 tombstone을 기록한다.
- 최초 키 검사 뒤 D1 행이 바뀌면 삭제 결정은 0건으로 끝나고 최신 접근 상태를 확인한 뒤 HTTP 409 충돌을 반환한다.
- 기존 연결 원본 차단, 권한 재확인, tombstone, R2 실패 시 재시도와 204 멱등 의미는 유지한다.

## 검증

- 다른 R2 객체 키를 가리키도록 손상한 D1 행의 삭제는 HTTP 503이며 R2 `delete` 호출은 0회다.
- 최초 검사 뒤 삭제 결정 직전에 저장 키를 바꾸는 경쟁은 HTTP 409이며 R2 `delete` 호출은 0회다.
- 두 경우 모두 원래 객체와 외부 객체가 보존된다.
- 실제 Worker/D1/R2 통합 시나리오에서도 손상 키 삭제 차단과 두 객체 보존을 확인했다.
- Node 회귀 검사 611/611 통과
- 격리 workerd/D1/R2 검사 424/424 통과
- 타입검사, 전체 lint, 프로덕션 빌드 통과
- 로컬 운영 Worker `/`, `/account`, `/account/setup` HTTP 200과 CSP, `X-Frame-Options: DENY`, `nosniff`, `no-referrer` 확인
- 실제 운영 쓰기, 이메일 발송, 유료 AI 요청, 외부 요청 0건
