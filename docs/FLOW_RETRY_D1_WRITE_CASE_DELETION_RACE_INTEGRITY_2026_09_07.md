# 상담 FLOW D1 쓰기 직전 사건 삭제 경쟁 무결성

기준일: 2026-09-07

## 확인한 위험

파트너의 전사문·음성 2슬롯 업로드가 첫 R2 객체만 저장한 채 실패한 뒤 정확한 재시도를 시작했을 때, 모든 R2 쓰기와 최종 접근 검사가 끝난 직후 사건 원본이 삭제되면 이미 없어진 사건에 FLOW와 파일 원장이 커밋될 수 있다. 오류 처리에서 이미 기록된 객체를 삭제하거나 예약을 새로 만들면 원래 업로드의 안전한 복구와 멱등성도 깨질 수 있다.

## 확인한 현재 경계

- 첫 전사문 객체 저장 성공과 두 번째 음성 저장 실패로 두 `pending` 예약이 남은 상태를 결정적으로 재현했다.
- 같은 명령 ID·본문·첨부의 정확한 multipart 재시도가 기존 예약 키에 전사문과 음성 객체를 모두 기록하고 최종 인증·신원 결속·담당 접근·업로드 권한 및 생명주기 검사를 통과하게 했다.
- 최종 검사에서 읽은 포털 상태 증빙을 확보한 뒤 D1 FLOW 트랜잭션 실행 직전에 실제 관리자 상태 저장 API로 사건 원본을 삭제했다.
- FLOW 조건부 쓰기는 최종 검사에서 읽은 정확한 포털 상태 payload와 현재 D1 payload를 비교한다. 사건 삭제로 값이 달라져 삭제 전 상태를 전제로 한 FLOW·명령 영수증·파일 소유권·메타데이터·객체 무결성·완료 원장 커밋을 차단하고 D1 트랜잭션 전체를 원자적으로 되돌린다.
- 사건 삭제는 보존되고 응답은 내부 D1 세부정보를 숨긴 503 재시도 안내다. 기존 FLOW와 명령 영수증은 변하지 않고 두 예약은 `pending`, 두 R2 객체는 예약된 파일 ID·키·바이트를 그대로 유지한다.
- 삭제한 사건 원본을 정확히 복구한 뒤 같은 안정 사용자 ID가 같은 명령 ID·본문·첨부로 재시도하면 같은 두 파일 ID·R2 키를 재사용해 FLOW, 명령 영수증, 두 `ready` 예약과 완료 원장을 한 번만 커밋한다.

기존 구현이 최종 상태 증빙을 D1 조건부 FLOW 쓰기에 결속해 요구 조건을 만족한다. 런타임 코드는 바꾸지 않고 실제 관리자 사건 삭제와 D1 직전 커밋 경쟁 회귀 증거를 추가했다.
