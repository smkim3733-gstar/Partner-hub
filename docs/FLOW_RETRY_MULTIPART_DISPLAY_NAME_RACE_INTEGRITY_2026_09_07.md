# 상담 FLOW multipart 재시도 표시명 변경 경쟁 무결성

기준일: 2026-09-07

## 확인한 위험

파트너의 전사문·음성 2슬롯 업로드가 첫 R2 객체만 저장한 채 실패한 뒤 정확한 재시도를 시작했더라도, 큰 multipart 본문을 읽는 동안 대표가 파트너 표시명을 바꾸면 이메일과 다른 표시 정보를 신원 키로 잘못 다루어 정상 업무를 차단하거나, 반대로 다른 계정으로 오인해 예약을 재사용할 위험이 있다.

## 확인한 현재 경계

- 첫 전사문 객체 저장 성공과 두 번째 음성 저장 실패로 두 `pending` 예약이 남은 상태를 결정적으로 재현했다.
- 같은 명령 ID·본문·첨부의 multipart 재시도에서 서버가 본문을 처음 읽는 시점에 실제 관리자 상태 저장 경로로 파트너 표시명을 변경했다.
- 표시명 변경은 ChatGPT 안정 사용자 ID·회원 ID 결속을 제거하지 않으며, 본문 해석 뒤 두 번째 신원·담당·업로드 권한 검사가 같은 안정 ID를 확인한다.
- 정확한 재시도는 중단되지 않고 기존 두 파일 ID와 R2 키를 재사용해 완료된다. 추가 R2 `put` 두 번은 두 예약의 기존 키로만 수렴한다.
- 포털 회원 표시명은 새 이름을 유지하지만, 기존 FLOW의 불변 담당자 `partnerName`은 자동 변경하지 않는다.
- 새 명령 영수증과 감사기록의 `actorKey`는 `member:<안정 회원 ID>`를 유지하고, 행위자 표시는 해당 상담 이력의 불변 담당자 이름을 유지한다.
- 대표가 표시명을 원래대로 되돌려도 완료된 FLOW·파일·명령·예약·완료 원장은 변하지 않는다.
- 같은 공통 테스트 경계에서 `ownCases`, `fileUpload`, 계정 정지, 로그인 이메일 변경, 표시명 변경, 진행 중단 여섯 시나리오의 차단 또는 연속·보존·복구 조건을 함께 유지한다.

기존 구현이 표시명을 권위 신원 키로 사용하지 않고 안정 ID로 인증·담당·예약을 결속해 요구 경계를 만족한다. 런타임 코드는 바꾸지 않고 시간차 경쟁과 명령 행위자 표시 회귀 증거를 확장했다.
