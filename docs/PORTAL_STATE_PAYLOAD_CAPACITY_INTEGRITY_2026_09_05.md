# 포털 상태 UTF-8 payload 용량 무결성 경계

기준일: 2026-09-05

## 문제

`portal_state`는 회원·진행·업무·일정·자료 연결을 포함한 전체 운영 상태를 한 JSON 객체로 보관한다. 애플리케이션 쓰기 경로는 직렬화한 payload가 900,000바이트를 넘으면 거절했지만 D1 직접 SQL에는 같은 제한이 없었다. 우회 저장된 대형 payload는 이후 정상 API 저장을 계속 용량 초과로 실패하게 만들 수 있었다.

## 적용

- 900,000바이트 상한을 `lib/storage-limits.ts`의 공용 상수로 분리해 애플리케이션과 D1 트리거 생성 코드가 같은 값을 사용한다.
- `0031_portal_state_payload_capacity.sql`에 INSERT·UPDATE 용량 트리거를 추가했다.
- SQLite의 문자 수가 아니라 `length(CAST(payload AS BLOB))`으로 UTF-8 저장 바이트를 계산한다.
- 정확히 900,000바이트는 허용하고 이를 초과하면 `portal state payload exceeds capacity`로 원자적으로 거절한다.
- ID 변경은 기존 신원 불변 트리거가 담당하도록 UPDATE 용량 검사는 기존 ID가 유지되는 경우에만 적용한다.
- 추가형 마이그레이션은 기존 payload를 읽거나 재작성하지 않고 이후 삽입·수정만 보호한다.

## 검증

- 유효한 JSON 객체를 정확히 900,000 UTF-8 바이트로 만들어 D1 직접 수정이 성공하는지 확인했다.
- 같은 객체를 900,001바이트로 늘린 직접 수정은 거절되고 기존 ID·payload·수정시각이 그대로 보존된다.
- 애플리케이션 CAS, 계정 변경, 원본 회수 저장과 JSON 객체·UTC 수정시각·고정 ID·삭제 방지 경계를 함께 회귀 검증했다.
- 32개 추가형 마이그레이션을 기존 상태가 있는 격리 D1에 두 번 적용해도 기존 상태를 교체하지 않는다.
- Node 회귀 검사 633/633 통과
- 격리 workerd/D1/R2 검사 443/443 통과
- 타입검사, 전체 lint, 변경 파일 포맷, 프로덕션 빌드 통과
- 로컬 운영 Worker `/`, `/account`, `/account/setup` HTTP 200과 CSP, `X-Frame-Options: DENY`, `nosniff`, `no-referrer` 확인
- 실제 운영 쓰기, 이메일 발송, 유료 AI 요청, 외부 요청 0건
