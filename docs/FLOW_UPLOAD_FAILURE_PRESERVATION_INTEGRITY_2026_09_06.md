# 상담 FLOW 실패 업로드 보존·동시 재시도 무결성

기준일: 2026-09-06

## 확인한 공백

상담 첨부는 같은 상담·행위자·명령/첨부 지문의 미완료 예약을 다른 탭이나 기기의 새 명령 ID에서도 재사용한다. 실패 요청이 D1 상태를 다시 읽어 아직 참조되지 않은 R2 키를 삭제하는 동안, 동일 첨부의 다른 요청이 같은 키를 다시 쓰고 성공 FLOW에 커밋할 수 있었다. 실패 요청의 재조회와 실제 R2 삭제 사이에 성공 커밋이 들어오면, 성공 응답이 반환됐는데도 그 FLOW가 참조하는 객체가 뒤늦게 사라지는 시간차 경쟁이 발생했다.

버전 258 후보의 파일별 독립 정리는 첫 삭제 실패가 다음 삭제까지 막는 문제를 줄였지만 이 더 깊은 시간차 경쟁은 해결하지 못했다. 자동 연속 감사에서 경쟁을 재현했으므로 버전 258은 공개하지 않고 버전 259로 대체했다.

## 적용한 경계

- R2 쓰기 전에 생성한 D1 예약을 실패 후 복구의 권위 기록으로 유지한다.
- 요청 종료의 오류 처리 경로에서는 예약된 R2 키를 자동 삭제하지 않는다.
- 실패·불확실 응답의 객체는 `pending` 예약과 함께 보존해 관리자 보관 현황에서 확인할 수 있게 한다.
- 같은 첨부의 새 명령 ID 재시도는 원래 파일 ID와 R2 키를 재사용하고, 같은 바이트와 고정 MIME을 다시 쓴 뒤 FLOW·파일 원장·객체 ETag·완료 원장을 하나의 D1 배치로 완성한다.
- 동시 성공 요청이 같은 예약을 완료한 뒤 실패 요청이 객체를 삭제할 경로를 제거한다.
- 자동 삭제·만료 정책은 추가하지 않는다. 보존 중인 미완료 객체는 기존 연령 관측과 명시적 운영 판단 범위에 남는다.

스키마나 마이그레이션 변경은 없다. 애플리케이션 오류 처리와 회귀 검사를 강화한 변경이다.

## 검증

- 실패 요청이 삭제 직전 대기하도록 만들고, 그 사이 동일 첨부의 새 명령 ID가 같은 예약을 성공 커밋한 뒤 삭제를 재개하는 순서로 기존 결함을 재현
- 수정 뒤 실패 요청의 R2 삭제 시도가 0건이고 성공 FLOW의 객체가 남는지 확인
- 최초 단일 첨부 D1 실패에서 객체와 `pending` 예약이 함께 보존되는지 확인
- 전사문·음성 2슬롯 D1 실패에서 두 객체와 두 `pending` 예약이 모두 보존되고 새 명령 ID 재시도가 같은 파일 ID·키를 완성하는지 확인
- 모호한 D1 결과 뒤 단일·2슬롯 교차 기기 재시도 유지 확인
- Node 자동 검사: 716/716 통과
- 격리 workerd + D1 + R2 검사: 522/522 통과
- 격리 검사는 운영 데이터 쓰기, 메일 발송, 유료 AI 요청, 외부 요청이 모두 0임을 확인
- 타입검사, lint, 변경 파일 포맷 검사, 프로덕션 빌드 통과
- 로컬 운영형 Worker에서 `/`, `/account`, `/account/setup`은 200 응답
- 인증 없는 `/api/state`, `/api/admin/file-inventory`, `/api/consulting-flow/test-case`는 401과 비공개 캐시 경계 유지
- 배포 아카이브는 Worker, 호스팅 설정, 96개 SQL 마이그레이션을 포함하고 `.wrangler` 임시 상태를 제외
