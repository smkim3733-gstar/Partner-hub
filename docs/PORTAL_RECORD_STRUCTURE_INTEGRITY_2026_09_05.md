# 포털 레코드 구조 무결성 경계

기준일: 2026-09-05

## 확인한 문제

포털 상태 검사는 타임라인·일정·업무·기업자료·진행·회원 필드가 배열인지만 확인하고 배열 항목이 일반 객체인지는 확인하지 않았다. 조작된 관리자 저장 요청에 `null` 항목을 넣으면 일정·진행·회원은 내부 예외로 HTTP 500이 됐고, 타임라인·업무·기업자료는 HTTP 200으로 실제 상태에 저장됐다. 현재 저장 상태가 이미 손상된 경우에도 파트너·관리자 조회가 500으로 중단되고, 일반 저장이 손상 상태를 초기 상태처럼 오인할 위험이 있었다.

## 적용한 경계

- 포털의 타임라인·일정·업무·기업자료·진행·회원 여섯 배열은 모든 항목이 `null`이나 배열이 아닌 일반 객체여야 한다.
- 조작된 신규 저장의 비객체 항목은 여섯 배열 모두 HTTP 403으로 거절하며 현재 상태를 변경하지 않는다.
- 파트너 인증은 손상된 저장 상태에서 회원을 추정하지 않고 HTTP 403으로 실패 폐쇄한다.
- 관리자 조회와 일반 저장은 손상된 현재 상태를 초기 상태로 간주하지 않고 HTTP 503으로 격리한다.
- 운영 상태가 아직 없는 정상 초기화의 `null` 상태는 계속 허용한다.
- 실제 운영 데이터, D1 스키마, R2, 인증수단, 공개 범위는 변경하지 않았다.

## 검증

- 수정 전: `null` 타임라인·업무·기업자료가 HTTP 200으로 저장되고, `null` 일정·진행·회원은 HTTP 500이 되는 것을 재현했다.
- 수정 후: 여섯 배열 모두 HTTP 403, 손상 저장 상태의 파트너 조회 403, 관리자 조회·일반 저장 503을 확인했다.
- 전체 Node 회귀 테스트 509/509 통과.
- 격리 workerd+D1+R2 검사 213/213 통과. 운영 쓰기·이메일·유료 AI·외부 요청은 모두 0건이다.
- 타입검사, 전체 lint, 프로덕션 빌드 통과.
- 로컬 운영 Worker의 `/`, `/account`, `/account/setup` 모두 HTTP 200.

## 저장 상태

기능 커밋 `e3a0af5c86903e48d7372957f975c6662c94652b`를 GitHub `main`과 Sites 소스 저장소에 반영했다. 같은 커밋의 검증된 빌드 산출물을 Sites 버전 128 (`appgprj_6a92514801988191b79eb9bd314e3fcd~appgver_5faf32fd3ec481918df2a83f888e02c4`)로 저장했다. 저장 산출물은 160개 파일, 4,392,960바이트, 해시 `sha256:4d891e3e7d9ebc5dd387bd8a4978954c5bf4ccdf7438186e5a3f30841e141eff`이다.

현재 공개 운영본은 버전 107이다. 버전 108~127은 버전 128로 대체하며 공개 배포하지 않는다. 버전 128도 정확한 운영 배포 승인 전까지 저장 상태로 유지한다.
