# 기업자료 원본 보관 원장 무결성 경계

기준일: 2026-09-05

## 확인한 문제

기업자료 카드의 원본 ID·파일명·크기 구조와 기존 원본 사실은 검증했지만, 일반 포털 상태 저장으로 새 원본을 연결할 때 그 ID가 실제 D1 파일 원장에 있는지 확인하지 않았다. 화면 밖 요청은 존재하지 않는 ID, 다른 기업·자료종류·담당 계정·진행의 원본, 업로드 대기·삭제 원본 또는 R2에서 사라진 원본을 완전한 카드처럼 저장할 수 있었다.

업로드 API의 정상 응답은 서버 원장값을 사용하지만, 일반 상태 저장 경계도 독립적으로 원장을 대조해야 우회 요청과 저장 직전 삭제 경쟁을 막을 수 있다.

## 적용한 경계

- 현재 상태에 없던 `storageFileId`만 새 연결로 분류한다. 기존 원본 카드는 레거시 원장 이관 없이 검토 상태와 수정시각을 계속 바꿀 수 있다.
- 새 연결은 D1 `company_file_objects`의 원본 ID·파일명·크기·기업·자료종류와 정확히 일치해야 한다.
- D1 담당 계정 ID와 진행 연결도 포털 카드의 안정 계정 ID·진행 ID와 정확히 일치해야 한다. 계정 ID가 없던 레거시 원장은 저장된 담당 표시명까지 대조한다.
- 업로드 원장 상태가 있으면 `ready`만 허용한다. `pending`과 `deleted`는 거절하며, 업로드 원장 도입 전의 레거시 파일은 실제 D1 메타데이터와 R2 원본이 온전하면 허용한다.
- R2 원본은 D1 저장 키에 실제로 존재하고 크기가 D1 원장과 같아야 한다. 본문은 읽지 않고 `head`만 사용한다.
- 사전 확인 뒤 삭제·재배정이 발생해도 포털 상태 CAS 쓰기 안의 D1 조건이 원장 사실과 상태를 다시 확인한다. 조건이 바뀌면 409 충돌로 실패하고 새 카드가 저장되지 않는다.
- D1의 업로드 자료명은 보관 당시 설명이고 포털 카드 제목은 업무용 표시값이므로 원본 권위값으로 취급하지 않는다.
- 위조·불일치·미완료·삭제·R2 누락은 익명 충돌 지표의 `원본 보관 원장 대조` 항목으로 분리한다.
- 운영 데이터 자동 수정·이동·삭제, D1/R2 스키마와 보관 정책 변경은 수행하지 않았다.

## 검증

- 수정 전 재현: 존재하지 않는 원장 ID와 D1 사실이 다른 새 원본 연결이 일반 상태 저장을 통과했다.
- 수정 후: 원장 부재, 파일명·크기·기업·자료종류·담당 계정·진행 불일치, 업로드 대기·삭제, R2 누락·크기 불일치가 모두 409로 실패하고 포털 상태를 보존한다.
- 온전한 `ready` 원본과 업로드 원장 도입 전 레거시 원본은 저장된다. 포털 표시 제목은 D1 업로드 제목과 달라도 허용한다.
- R2 확인 직후 D1 삭제 상태가 확정되는 경쟁에서도 원자적 커밋 조건이 저장을 차단한다.
- 기존 원장 없는 원본 카드의 검토 상태 변경은 계속 성공한다.
- Node 자동 테스트 556/556 통과.
- 격리 workerd+D1+R2 검사 344/344 통과.
- 타입검사, 전체 lint, 프로덕션 빌드 통과.
- 로컬 프로덕션 `/`, `/account`, `/account/setup` HTTP 200과 CSP 확인.
- 실제 운영 쓰기, 메일 발송, 유료 AI 요청, 외부 요청 0건.
