## 1. 개발 마감 요약

한기평 파트너 허브는 협업 파트너 가입과 승인, 기업 협업신청, 기업자료 관리, 상담 FLOW, 서류요청, 보고서·견적·계약, 일정·업무, 수행 및 사후관리까지 한 화면에서 관리하는 기업컨설팅 협업 포털로 개발했다.

초기 화면 중심 구현 이후 운영 데이터의 정확성, 사용자 권한, 파일 원본 무결성, 중복 요청과 응답 유실, 동시 변경 경쟁, AI 결과 증거, 상담 FLOW 명령의 의미 결속을 단계적으로 보강했다. 최종 v343은 완료 FLOW 파일의 영수증 행위자 텍스트를 감사기록과 함께 검증하여, 공백 전용·과다 길이·잘못된 Unicode 공동 변조를 파일 증명으로 인정하지 않도록 마감한 버전이다.

v343 코드는 전체 자동 검증을 통과했으며 GitHub `main` 반영, Sites 소스 전송·버전 저장·공개 운영 배포와 운영 HTTP 확인까지 완료했다.

## 2. 개발 목표와 적용 원칙

개발은 다음 원칙을 기준으로 진행했다.

1. 실제 업무 흐름을 우선한다. 협업신청부터 상담, 자료수집, 분석, 계약, 수행, 사후관리까지 연결한다.
2. 서버를 권위 기준으로 삼는다. 화면이 보낸 사용자·시각·상태·권한 값을 그대로 신뢰하지 않는다.
3. 불확실한 상태는 정상으로 완화하지 않는다. 원장이나 객체가 어긋나면 `inconsistent`로 격리하고 추가 접근을 차단한다.
4. 재시도는 중복 결과를 만들지 않는다. 요청 ID, 명령 ID, 입력 지문, 파일 예약을 이용해 같은 요청을 한 번만 완료한다.
5. 파일 본문과 메타데이터를 함께 검증한다. D1 원장과 R2 객체의 키, 크기, MIME, ETag, SHA-256을 결속한다.
6. 회귀 재현 후 수정한다. 실패 사례를 자동검사로 먼저 고정하고 운영 코드 수정 후 동일 검사를 통과시킨다.
7. 실제 운영 데이터와 외부 서비스를 개발 검증에 사용하지 않는다.

## 3. 주요 구현 결과

### 3.1 파트너 계정과 인증

- 파트너 신규 가입, 대표 승인, 정지, 조건부 삭제를 구현했다.
- 이메일·사이트 전용 비밀번호 로그인과 30분 유효 일회용 비밀번호 설정 링크를 구현했다.
- 관리자와 일반 파트너의 역할·권한을 서버에서 재검증한다.
- 계정 정지, 담당 변경, 권한 회수, 계정 삭제가 요청 처리 중 발생해도 최종 저장 전에 다시 확인한다.
- 세션·쿠키·로그인 응답과 개인정보 오류 로그의 노출 경계를 보강했다.

### 3.2 협업신청과 기업자료

- 협업신청 작성, 임시저장, 재접속 복구, 제출, 대표 검토 흐름을 구현했다.
- 사업자등록증, 크레탑, 기타 기업자료와 녹취자료 첨부를 지원한다.
- 파일명 정규화, 형식·MIME·파일 시그니처·크기 제한, 실제 바이트 기준 중복 판정을 적용했다.
- 업로드 응답 유실과 재시도에서 동일 파일 ID와 저장 키를 재사용한다.
- 기업자료의 저장 키, 전체 메타데이터, 담당·진행 연결, 객체 무결성 원장을 D1에 불변 증거로 보존한다.
- 연결된 원본의 임의 삭제와 검증 직후 저장 키 변경 같은 경쟁 상태를 차단한다.

### 3.3 상담 FLOW

- 반복 상담, 녹취, 근거자료, AI 작업, 보고서, 일정, 서류요청, 계약, 입금, 수행, 사후관리 흐름을 구현했다.
- 지원 명령을 실제 업무 상태 변화와 결속하고 허용되지 않은 필드·대상·순서 변경을 차단한다.
- 동일 요청 재시도, 부분 R2 저장, 응답 유실, 여러 파일 중 일부 실패를 안전하게 복구한다.
- 사건 삭제, 담당 변경, 계정 정지, 권한 회수 등 동시 변경이 발생하면 최종 D1 저장 전 현재 상태를 재검증한다.
- 신청자료 불러오기는 원본 ID, SHA-256, 검토시각, 검토자를 보존하고 원본 교체나 삭제를 감지한다.

### 3.4 파일 재고와 증명

- 대표 전용 파일 재고 화면에서 기업자료와 완료 FLOW 첨부를 통합 조회한다.
- 동일 원시 파일 ID가 서로 다른 출처에 존재하면 충돌 항목을 모두 보존하고 격리한다.
- 소유 원장, 메타데이터 원장, 객체 무결성 원장, 체크섬 원장, 업로드 예약, 완료 영수증, FLOW payload를 교차 검증한다.
- 원장 누락, 고아 원장, 한쪽 완료 영수증, 비정상 `pending`, payload 누락·복제·대상 불일치를 정상 파일로 표시하지 않는다.
- 현재 R2 확인은 본문을 읽지 않고 `head` 정보만 대조하며, 증명 불일치 시 R2 접근 전에 차단한다.
- v343에서 현대 영수증의 `actor`를 정상 Unicode 1~200자로 제한하고 감사기록 행위자와의 정확한 문자열 일치를 검증한다.

### 3.5 업무 운영 기능

- 대표·파트너 대시보드, 전체 진행 검색, 모바일 검색과 내비게이션을 구현했다.
- 일정, 업무, 기한, 서류요청 상태, 반복 상담 이력을 관리한다.
- 보고서·PPT·견적서·경영자문 계약서·서명본을 상담 단계에 연결한다.
- 신청→FLOW 전환, 문서 검토 대기, 공동분석 확인, 저장 충돌, 지원요청 등 운영 지표를 대표 전용으로 제공한다.
- 실제 기록과 가상 예시를 구분하고 작은 표본이나 식별 가능한 상세값을 과도하게 노출하지 않는다.

## 4. 기술 구성

- 화면: React 19, TypeScript, Tailwind CSS, shadcn 기반 구성요소
- 애플리케이션·빌드: Vinext, Vite
- 실행 환경: Cloudflare Workers
- 관계형 상태·불변 원장: Cloudflare D1(SQLite)
- 비공개 파일 객체: Cloudflare R2
- 품질 도구: Node 테스트 러너, TypeScript 타입검사, oxlint, oxfmt

화면과 서버 API는 `app/`, 공통 업무 화면은 `components/`, 인증·권한·상담 FLOW·파일·AI 처리는 `lib/`, D1 스키마와 마이그레이션은 `db/` 및 `drizzle/`에 분리했다.

## 5. 보안 및 데이터 무결성 강화

v343까지 다음 위험을 집중적으로 점검하고 회귀검사로 고정했다.

- 권한 없는 계정의 조회·저장·다운로드
- 요청 처리 중 계정 정지, 권한 회수, 담당 변경, 사건 삭제
- 오래된 화면과 여러 창에서 발생하는 저장 경쟁
- 동일 요청의 중복 실행과 응답 유실 후 재시도
- 부분 파일 저장과 모호한 R2 성공·실패
- 파일명, MIME, 크기, 저장 키, ETag, SHA-256 불일치
- D1 원장 누락·변조·고아 기록과 R2 객체 교체
- 상담 FLOW payload와 파일 소유·예약·완료 영수증 불일치
- AI 요청·응답·토큰·Message ID·실패 이력의 증거 변조
- 명령 행위자 텍스트 봉투, 대상, 동작, 시각과 감사기록 결속의 변조
- 비정상 Unicode, 과도한 문자열, 허용되지 않은 JSON 필드

검증 실패는 가능한 한 저장이나 R2 본문 접근 전에 차단한다. 손상 상태는 추정 복구하지 않고 관리자가 확인할 수 있는 격리 상태로 유지한다.

## 8. 현재 의도적으로 자동화하지 않은 범위

다음 기능은 연결 완료로 표시하지 않고 수동 절차 또는 별도 프로젝트 범위로 남겼다.

- Google Calendar 자동 쓰기 및 양방향 동기화
- 음성 자동전사 서비스
- 카카오톡·이메일 자동 발송
- 자동 PPT 생성
- 전자서명
- 은행 입금 자동 확인
- 실제 외부 AI 모델·잔액·비용·기업별 전송 승인

또한 v343 파일 재고 SQL은 영수증·감사기록 `actor`의 형식과 상호 일치를 검증하지만, 두 값을 형식상 정상인 다른 문자열로 함께 바꾼 경우 권위 있는 관리자·담당 표시명과 독립적으로 대조하지 않는다. 정상 명령 생성은 서버 전이 검증과 D1 트리거가 보호하지만, 저장된 payload를 직접 공동 변조한 상태는 재고 검증에서 탐지되지 않을 수 있다. 이번 기능 마감 결정에 따라 이 항목은 수용한 잔여 위험으로 기록한다.

이 범위는 API 계약, 비용, 개인정보 처리, 외부 서비스 계정, 운영 책임을 별도로 결정한 뒤 진행해야 한다.

## 9. 마감 판정

v343을 이번 개발의 기능 마감 버전으로 확정한다. 30분 간격 연속 개발 자동화는 중지하며 v344 이상의 신규 감사 버전을 만들지 않는다.

개발·검증·운영 마감은 다음 세 단계까지 모두 완료했다.

1. v343 마감 문서와 기능 커밋을 GitHub `main`에 반영했다.
2. v343 소스를 Sites에 전송하고 버전 310으로 저장·공개 배포했다.
3. 운영 URL의 핵심 화면, 비인증 API 차단, 보안 헤더를 확인해 기록했다.

이후 작업은 신규 개발이 아니라 운영 장애 대응, 법·정책 변경, 외부 서비스 연결, 사용자 요청에 따른 유지보수로 분류한다.

## 10. 이후 운영 원칙

v343 기능 개발과 공개 운영 반영은 완료했다. 이후에는 신규 버전을 자동 생성하지 않고 운영 장애 대응, 법·정책 변경, 외부 서비스 연결 또는 사용자가 요청한 유지보수만 진행한다.
