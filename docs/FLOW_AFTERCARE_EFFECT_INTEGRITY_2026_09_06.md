# 상담 FLOW 사후관리 효과 무결성

기준일: 2026-09-06

## 문제

`start_aftercare` 명령은 수행 완료 확인 뒤 사후관리 요약·다음 점검일·담당자를 저장했지만, 기존 저장 경계는 `aftercare` 영역이 바뀌었다는 사실만 확인했다. 따라서 기록시각을 과거의 정상 시각으로 바꾸거나 요약·담당자에 비정규 앞뒤 공백을 넣고 감사문구를 다른 정상 문자열로 바꿔도 저장될 수 있었다. 실패 우선 검사로 기록시각 위조가 애플리케이션 저장 경계를 통과하는 것을 재현한 뒤 앱과 D1에 같은 사후관리 효과 계약을 추가했다.

## 적용한 경계

- 사후관리 등록·업데이트는 계약이 있고 약정 계약금이 모두 확인돼 컨설팅 수행이 시작된 상태에서 안정 관리자 신원 `admin:primary`만 수행한다.
- 새 사후관리 객체는 `at`, `summary`, `nextDate`, `owner` 네 필드만 허용한다.
- 기록시각은 해당 revision의 서버 수정시각과 정확히 같아야 한다.
- 요약과 담당자는 앞뒤 공백 없는 비어 있지 않은 정규 문자열이며 각각 Unicode 코드포인트 3,000자·100자 이하로 제한한다.
- 다음 점검일은 `YYYY-MM-DD` 형식의 실제 달력 날짜만 허용한다.
- 감사기록은 같은 명령 ID·서버시각·`start_aftercare` 동작과 `컨설팅 수행 결과 확인 · 사후관리 일정 등록` 문구에 정확히 결속한다.
- 이미 사후관리 일정이 있어도 새 수행 결과와 다음 계획으로 업데이트하는 기존 제품 동작은 유지한다. 업데이트도 같은 정규형·서버시각·감사 규칙을 다시 적용한다.

애플리케이션 커밋 검사와 추가형 `0091_consulting_flow_start_aftercare_effect.sql` D1 트리거가 같은 효과를 독립적으로 강제한다. 기존 사후관리 기록은 변경하지 않고 이후 revision의 새 `start_aftercare` 명령만 검사한다.
