# 로그인 세션·설정 링크 발급 커밋 무결성 경계

2026-09-05 기준. 계정 상태를 확인한 뒤 로그인 세션이나 일회용 비밀번호 설정 링크를 D1에 기록하기 직전, 대표의 계정 정지·삭제·이메일 변경 또는 비밀번호 변경이 먼저 끝나는 동시 요청을 점검했다.

## 확인한 문제

- 로그인은 비밀번호와 활성 명단을 먼저 확인했지만 세션 삽입 시점에는 최신 비밀번호 계정과 명단 상태를 다시 확인하지 않았다. 정지 또는 비밀번호 변경이 먼저 완료된 뒤 늦은 로그인 요청이 사용할 수 없는 세션을 남기고 성공을 응답할 수 있었다.
- 설정 링크 발급은 대상 명단을 먼저 확인했지만 기존 링크 삭제와 새 링크 삽입 시점에는 최신 이메일·상태를 다시 확인하지 않았다. 이메일 변경이 먼저 끝나고 새 이메일용 링크가 발급된 뒤 늦은 과거 요청이 최신 링크를 삭제하고 오래된 이메일용 링크를 만들 수 있었다.

두 경우 모두 이후 포털 접근이나 링크 사용 단계에서 현재 명단을 다시 확인해 타인 접근으로 이어지지는 않았다. 다만 이미 폐기된 인증수단이 다시 저장되고 정상 요청에 실패 응답이 늦게 나타나는 데이터 무결성·가용성 문제가 있었다.

## 적용한 경계

- 로그인 세션은 한 D1 트랜잭션에서 현재 비밀번호 계정의 회원 ID·이메일·자격 버전과 현재 명단의 동일 회원 ID·이메일·`활성` 상태가 모두 일치할 때만 삽입한다.
- 비밀번호 변경이 먼저 끝나면 이전 자격 버전으로 세션을 만들지 않는다. 로그인이 먼저 끝나면 기존 비밀번호 설정 트랜잭션이 해당 세션을 폐기한다.
- 설정 링크의 기존 행 삭제와 새 행 삽입은 현재 명단의 대상 회원 ID·이메일·비정지 상태가 모두 일치할 때만 실행한다.
- 대상 이메일이나 상태가 먼저 변경되면 늦은 요청은 HTTP 409로 최신 명단 확인을 안내하며, 변경 뒤 만들어진 새 링크를 삭제하지 않는다.
- 실제 운영 계정·세션·링크·회원 명단은 이 개발 과정에서 읽거나 변경하지 않았다. DB 스키마·보관 기간·메일 발송 방식도 바꾸지 않았다.

## 검증

- 결정적 경합 검사: 정지가 세션 삽입보다 먼저 끝난 경우 HTTP 403과 세션 0건 확인
- 결정적 경합 검사: 이메일 변경과 새 링크 저장이 먼저 끝난 경우 늦은 요청 HTTP 409, 최신 링크 보존 확인
- 전체 Node 자동 검사 472개 통과
- 실제 workerd와 격리 D1/R2 검사 147개 통과
- 타입검사, 전체 lint, 프로덕션 빌드 통과
- 로컬 운영 화면 3곳 HTTP 200과 화면 보안 헤더 확인
- 보호 API 3곳 익명 HTTP 401과 비공개 캐시·참조정보·MIME 보호 확인
- 실제 운영 쓰기·메일 발송·유료 AI·외부 요청 0건
