# 상담 FLOW 신청자료 최종 커밋 원본 무결성

## 결론

신청자료 원본을 마지막으로 확인한 직후 삭제 tombstone이 기록되면, 기존 구현은 이미 준비한 원본 사실로 최종 FLOW D1 배치를 성공시킬 수 있었다. `import_intake_source` FLOW 효과와 기업자료 원본의 현재 유효성을 같은 D1 트랜잭션에 결속해 이 간격을 닫았다.

기능 커밋은 `b38f22b82d5d44964b2af3a7e1e52760a02753ad`이다. GitHub `main`과 Sites 소스 `main`에 반영했고 Sites 버전 308 (`appgprj_6a92514801988191b79eb9bd314e3fcd~appgver_e2daae659618819194b4f288394ff459`)로 저장했다. 공개 운영본은 버전 107이며 버전 108–307은 버전 308로 대체해 공개하지 않는다.

## 재현한 결함

신청자료 가져오기가 목적지 R2 복사와 마지막 FLOW 접근 검사를 마친 뒤, 최종 `db.batch` 직전에 원본 삭제 tombstone을 삽입했다.

- 수정 전: HTTP 200, 오래된 신청자료 검토본을 포함한 FLOW와 파일 효과가 저장됐다.
- 기대 결과: 현재 원본 부재 404, FLOW 관련 D1 효과 전체 롤백.

이 회귀는 애플리케이션 재검사와 D1 커밋 사이의 원본 사실이 동일 트랜잭션에 포함되지 않았음을 증명했다.

## 적용한 보호

`consulting_flows_import_intake_source_effect_guard`가 `import_intake_source` 효과를 저장하는 같은 D1 트랜잭션에서 다음 사실을 다시 확인한다.

- `company_file_objects` 원본과 불변 기업·사건·담당 결속
- 기업자료 삭제 tombstone 부재
- FLOW 사건과 현재 파트너 ID·표시명 일치
- 원본 저장 키 원장 일치
- 파일명·MIME·크기·SHA-256·생성시각을 포함한 전체 메타데이터 원장 일치
- 유효한 객체 무결성 원장과 신청자료 초안 가시성 규칙

런타임 스키마와 추가형 마이그레이션 `0096_consulting_flow_intake_source_origin.sql`에 같은 트리거 SQL을 설치했다. 신선한 D1에서도 참조 테이블이 먼저 존재하도록 FLOW 데이터베이스 초기화가 기업자료 스키마 준비를 선행한다.

최종 FLOW 커밋이 트리거에 의해 거절되고 요청이 신청자료 가져오기라면 라우트는 롤백 뒤 원본을 다시 확인한다. 삭제는 404, 원본 사실 불일치는 409로 반환하며 일반 저장 오류로 가리지 않는다.

## 실패 원자성

삭제 경쟁이 발생하면 다음 결과를 강제한다.

- FLOW, 명령 영수증, 파일 원장, 완료 원장, 준비 상태 전이: 0건
- 이미 복사된 목적지 R2 객체: 1개 보존
- 불변 파일 ID·키 예약: `pending` 보존
- 기업자료 삭제 tombstone: 보존

R2 객체와 D1은 단일 트랜잭션을 공유하지 않으므로 목적지 객체를 즉시 삭제하지 않는다. 정확한 재시도와 운영 복구가 같은 예약 키를 사용할 수 있게 보존한다.
