# 상담 FLOW 파일 확장자·MIME·목적 무결성 경계

기준일: 2026-09-05

## 확인한 문제

FLOW 업로드는 작업·차수별 허용 확장자를 확인하고 공용 등록표의 고정 MIME을 저장했지만, 저장 payload 구조 검증은 파일명·MIME·목적을 각각 비어 있지 않은 문자열로만 확인했다. 손상된 D1 payload에서 허용되지 않은 확장자, 파일명과 다른 MIME, 목적과 맞지 않는 형식이 상세 응답과 다운로드 판단에 전달될 수 있었다. 대시보드는 파일 배열을 SQLite에서 제거한 뒤 축소 구조를 검사하므로 같은 손상을 발견하지 못했다.

## 적용한 경계

- 저장 목적별 허용 확장자를 업로드 정책과 같은 목록에서 파생한다.
- `source`·`source_archived`, 보고서, 녹취·전사문, 요청서류, 서명 계약서가 각 목적의 허용 형식만 사용하도록 한다.
- 보고서 저장 목적은 일반 보고서 형식과 3차 발표자료 형식의 합집합을 허용해 차수 정보가 없는 기존 저장 구조와 일치시킨다.
- 파일명의 대소문자 확장자를 공용 파서로 읽고 공용 등록표의 고정 MIME과 정확히 대조한다.
- 저장 FLOW 상세 조회와 SQLite 대시보드 축소 전 검사가 같은 목적·확장자 규칙과 MIME 등록표를 사용한다.
- 네이티브 D1의 SQL 표현식 깊이 한계를 넘지 않도록 규칙을 JSON 테이블로 평탄화했다.
- 기존 업로드 내용 서명 검사, 목적별 크기 상한, 다운로드의 R2 객체 크기 재대조는 유지한다.
- D1 스키마, R2 원본, 인증·권한, 보관·삭제 정책은 변경하지 않았다.

## 검증

- 서명 계약서 TXT, 보고서 MIME 위장, 미등록 EXE, AI 보관 근거 DOCX를 상세 조회와 대시보드가 모두 거절한다.
- 실제 workerd+D1에서 목적 밖 확장자와 파일명에 맞지 않는 고정 MIME을 상세 조회와 SQLite 축소 대시보드가 동일하게 HTTP 503으로 격리한다.
- Node 자동 테스트 591/591 통과.
- 격리 workerd+D1+R2 검사 390/390 통과.
- 타입검사, 전체 lint, 변경 파일 포맷 검사, 프로덕션 빌드 통과.
- 로컬 프로덕션 `/`, `/account`, `/account/setup` HTTP 200과 CSP·`DENY`·`nosniff`·`no-referrer` 확인.
- 실제 운영 쓰기, 메일 발송, 유료 AI 요청, 외부 요청 0건.
