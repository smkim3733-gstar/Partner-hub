# 상담 FLOW R2 쓰기 중 업로드 권한 회수 경쟁 무결성

기준일: 2026-09-07

## 확인한 위험

파트너의 전사문·음성 2슬롯 업로드가 첫 R2 객체만 저장한 채 실패한 뒤 정확한 재시도를 시작했더라도, 재시도의 R2 객체 쓰기 사이에 대표가 `fileUpload` 권한을 회수하면 권한이 없는 계정의 새 첨부와 업무 변경을 커밋할 위험이 있다. 반대로 실패 객체를 즉시 삭제하면 같은 예약을 완료하는 정확한 재시도나 동시 요청의 객체를 지울 수 있다.

## 확인한 현재 경계

- 첫 전사문 객체 저장 성공과 두 번째 음성 저장 실패로 두 `pending` 예약이 남은 상태를 결정적으로 재현했다.
- 같은 명령 ID·본문·첨부의 정확한 multipart 재시도에서 첫 전사문 R2 쓰기가 완료된 직후 실제 관리자 상태 저장 경로로 `fileUpload` 권한을 회수했다.
- 이미 인증된 요청은 두 번째 음성 객체까지 기존 예약 키에 기록하지만, 모든 R2 쓰기 뒤 최종 인증·담당·업로드 권한 및 생명주기 재검사가 권한 회수를 403으로 거절한다.
- 거절된 요청은 FLOW와 명령 영수증을 변경하지 않고 두 예약을 `pending`으로 유지한다. 첫 전사문과 두 번째 음성 객체는 각각 예약된 파일 ID·R2 키와 바이트를 보존한다.
- 오류 경로는 객체를 삭제하지 않는다. 다른 정확한 재시도나 동시 커밋과 경쟁해 공유 예약 객체를 지우지 않기 위한 경계다.
- 대표가 `fileUpload` 권한을 복구한 뒤 같은 명령 ID·본문·첨부로 재시도하면 기존 두 파일 ID·R2 키를 재사용해 FLOW, 명령 영수증, 두 `ready` 예약과 완료 원장을 한 번만 커밋한다.
- 완료된 명령의 `actorKey`는 안정 회원 ID를 유지하고 FLOW 불변 담당자·감사 행위자 표시는 기존 상담 이력을 보존한다.

기존 구현이 R2 객체 쓰기 뒤 최종 접근·업로드 권한·생명주기 재검사와 영속 예약 복구 경계를 갖춰 요구 조건을 만족한다. 런타임 코드는 바꾸지 않고 R2 쓰기 도중 실제 업로드 권한 회수 경쟁 회귀 증거를 추가했다.
