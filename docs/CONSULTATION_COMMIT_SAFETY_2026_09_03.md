# 새 상담 원자적 저장 안전성

## 문제

새 상담 등록은 타임라인, 허브 일정, 후속 업무, 진행단계와 상담번호를 각각 별도 화면 상태 변경으로 만들었다. 일정·업무 ID가 현재 시각에 의존해 빠른 반복 실행과 재시도에서 충돌할 수 있었고, 타임라인은 진행·날짜·제목만으로 병합해 같은 상담번호의 별도 기록이 사라질 수 있었다. 폼을 연 뒤 권한·담당 진행·FLOW 관리·중단 상태나 단계가 바뀌어도 전체 상태를 저장 직전에 다시 대조하지 않았으며, 이미 계약 이후인 진행이 상담 단계로 되돌아갈 수 있었다.

## 변경

- 상담 폼마다 UUID 요청 ID를 한 번 만들고 같은 제출 이벤트의 재실행에 재사용한다.
- 타임라인·일정·후속 업무 ID를 요청 ID에서 결정적으로 만들며, 어느 파생 ID라도 이미 저장됐으면 같은 상담의 중복 적용을 차단한다.
- 타임라인의 새 ID를 진행 ID와 함께 병합 키로 사용한다. 같은 날짜·제목의 별도 상담은 보존하고, 다른 진행의 같은 ID로 기존 기록을 덮어쓸 수 없다.
- 기존 ID 없는 타임라인은 진행·날짜·제목 병합 규칙을 유지해 과거 기록을 강제 이관하지 않는다.
- 상담번호는 화면 표시값으로만 사용하고 저장 식별자로 사용하지 않는다. 폼을 연 뒤 번호가 바뀌면 최신 화면에서 재확인하도록 차단한다.
- 저장 전 현재 계정의 진행 관리 권한, 진행 ID·기업·서비스·담당 계정·FLOW 관리·중단 상태·단계·상담횟수와 폼을 열 때의 진행 연결을 다시 검사한다.
- 상담 입력을 공용 검증으로 다시 정규화하고, 폼에서 확인한 내용과 실제 저장 영향이 달라지면 전체 저장을 중단한다.
- 타임라인·일정·후속 업무·진행 변경과 상담번호 증가를 하나의 순수 계산 결과로 만든 뒤 한 화면 갱신에서 함께 반영한다.
- 상담으로 진행단계가 앞으로 갈 수는 있지만 계약·컨설팅수행·사후관리 등 뒤 단계가 상담예약·상담진행으로 되돌아가지 않는다. 취소 상담은 진행 상태를 바꾸지 않는다.
- 원본 상태 배열은 직접 변경하지 않으며 같은 기업의 다른 반복 진행은 변경하지 않는다.

## 유지한 운영 경계

- 새 상담의 명시적 저장 동작, 허브 일정 공개범위와 후속 업무 의미는 유지한다.
- Google Calendar나 외부 일정에는 자동 등록하지 않는다.
- 이미 저장된 타임라인·일정·업무 ID나 상담번호를 일괄 변경하지 않는다.
- 서버 API, 인증·권한 규칙, revision/CAS, DB/R2 스키마·보관 정책을 변경하지 않았다.
- 메일·메신저·외부 알림·유료 AI·외부 API 호출을 추가하지 않았다.
- GitHub 푸시와 공개 Sites 배포는 사용자 승인 전까지 수행하지 않는다.
