# 상담 FLOW 담당 재배정 시점별 경쟁 무결성

기준일: 2026-09-07

## 확인한 위험

정상 관리자 경로는 FLOW가 관리하는 사건의 담당 계정을 직접 바꾸지 못하지만, 레거시·복구 writer가 multipart 재시도 중 포털 사건의 담당 회원 ID를 바꾸면 기존 FLOW의 불변 담당 ID와 어긋날 수 있다. 표시명이 같은 다른 계정이면 이름 비교만으로 변경을 놓쳐 이전 담당자의 첨부와 명령을 새 담당 사건에 커밋할 위험이 있다.

## 확인한 현재 경계

- 첫 전사문 객체 저장 성공과 두 번째 음성 저장 실패로 기존 전사문 객체와 두 `pending` 예약이 남은 상태를 각 시점별로 결정적으로 재현했다.
- 레거시·복구 writer는 사건 표시명을 그대로 둔 채 담당 회원 ID만 동일 표시명의 다른 안정 계정 ID로 바꿨다.
- 첫 multipart 본문 청크를 읽을 때 재배정한 경우, 본문 처리 뒤 접근 재검사가 포털 담당 회원 ID와 FLOW 불변 담당 ID 불일치를 409로 차단한다. 재시도의 새 R2 쓰기와 FLOW·명령 영수증·파일 원장·완료 원장 D1 쓰기는 모두 0건이다.
- 재시도의 첫 전사문 객체를 기존 예약 키에 기록한 직후 재배정한 경우, 두 번째 음성 객체까지 원래 예약 키에 기록한 뒤 최종 접근 재검사가 같은 불일치를 409로 차단해 FLOW D1 커밋을 시작하지 않는다.
- 두 시점 모두 변경된 포털 담당 회원 ID는 유지되지만 기존 담당 계정과 안정 ChatGPT 사용자 ID·회원 ID 결속, 기존 FLOW의 불변 담당 ID·표시명, 명령 영수증은 변하지 않는다. 두 `pending` 예약도 원래 파일 ID·R2 키로 복구 가능하게 보존된다.
- 포털 담당 회원 ID를 FLOW 불변 담당 ID로 복구한 뒤 같은 안정 사용자 ID·명령 ID·본문·첨부로 정확히 재시도하면 같은 두 파일 ID·R2 키를 재사용해 FLOW, 명령 영수증, 두 `ready` 예약과 완료 원장을 한 번만 커밋한다.

기존 구현이 표시명이 아니라 안정 담당 계정 ID를 본문 처리 뒤와 모든 R2 쓰기 뒤 다시 대조해 요구 조건을 만족한다. 런타임 코드는 바꾸지 않고 레거시·복구 담당 재배정의 본문 읽기·첫 R2 쓰기 경쟁 회귀 증거를 추가했다.
