# 기업자료 저장 키·객체 무결성 원장 불변 경계

기준일: 2026-09-05

## 문제

기업자료의 정확한 R2 저장 키와 객체 ETag·MIME 검증 범위는 별도 가산 원장으로 결속되어 소비·삭제 전에 대조된다. 그러나 두 원장 테이블 자체는 직접 `UPDATE`와 부모 원본이 남은 상태의 직접 `DELETE`를 받아들일 수 있었다. 운영 애플리케이션에는 해당 변경 경로가 없었지만, 잘못된 유지보수 SQL이 교차 객체 키나 새 ETag를 권위값처럼 다시 쓰거나 증거 행을 먼저 제거할 수 있는 저장소 계약 공백이었다.

## 적용

- `app/`과 `lib/` 전체를 검사해 `company_file_object_integrity`, `company_file_storage_keys`, `company_file_metadata`에는 신규 파일의 `INSERT`만 있고 직접 수정·삭제 경로가 없음을 확인했다.
- `0021_company_file_integrity_ledger_immutability.sql`에 저장 키·객체 무결성 원장별 `BEFORE UPDATE` 트리거를 추가해 유효한 값으로의 변경도 모두 거절한다.
- 부모 원본이 존재하는 두 원장 행의 직접 `DELETE`도 각각 거절한다.
- 정상 파일 삭제는 검증된 `company_file_objects` 부모 행을 조건부 삭제하고 세 원장을 외래 키 `ON DELETE CASCADE`로 같은 SQLite 결정에서 정리한다.
- 런타임 테이블 준비에도 같은 트리거를 `IF NOT EXISTS`로 포함해 신규·격리 저장소와 마이그레이션 적용 저장소의 계약을 맞춘다.
- 정적 회귀검사가 이후 애플리케이션 코드에 세 불변 원장의 직접 `UPDATE`·`DELETE`가 다시 들어오면 실패한다.
- 기존 손상 탐지 검사는 트리거 적용 뒤 원장을 임의로 훼손하지 않고, 원장 누락·불일치가 처음부터 존재하는 레거시 장애 자료로 구성한다.

## 검증

- 객체 무결성 원장의 직접 MIME 변경과 직접 삭제가 각각 불변·부모 삭제 요구 오류로 거절된다.
- 저장 키 원장의 직접 키 변경과 직접 삭제도 같은 방식으로 거절된다.
- 정상 삭제 API는 HTTP 204를 반환하고 R2 객체와 저장 키·객체 무결성·전체 메타데이터 원장을 함께 제거한다.
- 22개 추가형 마이그레이션을 기존 행이 있는 격리 D1에서 두 번 적용해도 원장값을 교체하지 않는다.
- Node 회귀 검사 620/620 통과
- 격리 workerd/D1/R2 검사 433/433 통과
- 타입검사, 전체 lint, 변경 파일 포맷, 프로덕션 빌드 통과
- 로컬 운영 Worker `/`, `/account`, `/account/setup` HTTP 200과 CSP, `X-Frame-Options: DENY`, `nosniff`, `no-referrer` 확인
- 실제 운영 쓰기, 이메일 발송, 유료 AI 요청, 외부 요청 0건
