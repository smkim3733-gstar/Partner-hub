# 상담 FLOW 다중 R2 쓰기 사이 접근변경 경쟁 무결성

기준일: 2026-09-07

## 확인한 위험

상담 FLOW의 전사문·음성파일 동시 저장은 두 개의 R2 `put`을 순서대로 실행한다. 기존 구현은 두 객체를 모두 쓴 뒤 최종 접근을 다시 확인했기 때문에, 첫 객체 쓰기 중 권한·신원·담당·사건 상태가 바뀌어도 두 번째 객체까지 기록한 다음 요청을 거절했다. FLOW D1 커밋은 차단됐지만 이미 취소된 접근으로 불필요한 두 번째 객체를 쓸 수 있었다.

## 발견·수정한 문제

- 공용 경쟁 회귀 도우미로 첫 R2 객체 쓰기 중 계정 정지, 사건 중단, `fileUpload`·`ownCases` 권한 회수, 로그인 이메일 변경, 담당 변경, 사건 삭제, 사건·담당 계정 삭제를 실행했다. 표시명 변경은 권한을 잃지 않는 대조군으로 유지했다.
- 수정 전 업로드 권한 회수 회귀는 차단 상황에서도 R2 쓰기 2회가 발생해 기대한 1회와 다른 `2 !== 1` 실패를 재현했다.
- 첫 객체가 실제 저장된 다중 슬롯 요청은 두 번째 R2 쓰기 전에 인증·안정 신원·FLOW 담당 ID·업로드 권한·사건 생명주기를 다시 확인하도록 라우트를 보강했다.
- 차단되는 8개 상태변경은 403·404·409 중 해당 오류로 끝나며, 전사문 객체 1개만 기존 예약 키에 보존하고 음성 객체는 쓰지 않는다. 두 업로드 예약은 모두 `pending`으로 남고 FLOW·명령 영수증·파일 원장·완료 원장 D1 쓰기는 발생하지 않는다.
- 상태·권한·담당·사건을 복구하고 필요한 경우 같은 안정 ChatGPT 사용자 ID를 다시 결속한 정확한 재시도는 같은 파일 ID와 R2 키를 재사용해 한 번만 완료된다.
- 표시명만 바뀐 경우 안정 신원·권한·담당 결속이 유지되므로 중간 재검사를 통과한다. 두 R2 객체와 단일 FLOW 커밋이 정상 완료되고 현재 프로필 변경도 유지된다.
