# R2 객체와 D1 SHA-256 원장 무결성

## 결과

새 기업자료와 상담 FLOW 첨부파일은 R2가 확인한 SHA-256을 별도 D1 불변 원장에 함께 기록한다. 이후 다운로드, 신청자료 미리보기·가져오기, 파일 복구, 재고 점검, AI 입력 준비는 기존 ETag·MIME·크기뿐 아니라 D1 SHA-256과 현재 R2 체크섬도 대조한다. 같은 키의 객체가 바뀌거나 D1 체크섬 증명이 달라지면 원문을 반환하거나 후속 처리를 시작하지 않고 무결성 오류로 중단한다.

기능 커밋은 `67484fe7a34aadab83f0b46112ee11389ea5b020`이다.

## 구현

- `company_file_object_checksums`와 `consulting_flow_file_object_checksums`에 파일 ID별 64자리 소문자 SHA-256을 저장한다.
- 체크섬 행의 직접 수정·삭제를 D1 트리거로 차단한다. 기업자료는 검증된 부모 파일 삭제에서만 연쇄 제거되며, FLOW 체크섬은 기존 FLOW 파일 원장과 같이 보존된다.
- 새 업로드는 R2 조건부 `put`, R2 응답 체크섬 확인, D1 ETag/MIME 원장, D1 SHA-256 원장을 하나의 완료 조건으로 사용한다.
- FLOW 업로드 예약은 체크섬 원장이 존재하지 않으면 `ready`로 전환할 수 없다.
- 추가형 마이그레이션 `0097_r2_sha256_integrity.sql`은 새 원장과 트리거를 만들고 FLOW 완료 가드를 최신 정의로 교체한다.

## 레거시 호환

기존 객체의 SHA-256을 추정하거나 운영 R2 본문을 대량으로 다시 읽지 않는다. 체크섬 행이 없는 기존 ETag 객체는 ETag·MIME·크기 검증을 유지하고, 더 오래된 메타데이터 모드 객체는 기존 메타데이터 경계를 유지한다. 마이그레이션을 두 번 적용해도 기존 상태와 레거시 검증 모드는 바뀌지 않는다.

## 검증

- Node 회귀 테스트 763/763
- 격리 workerd·D1·R2 전체 검사 통과
- 98개 추가형 마이그레이션 2회 적용 통과
- D1 체크섬 저장값과 R2 SHA-256 일치, 체크섬 수정·삭제 거절, 의도적으로 다른 D1 SHA-256에서 다운로드 거절 확인
- 레거시 파일에 가짜 SHA-256을 백필하지 않음을 확인
- 타입검사, 전체 lint, 변경 파일 포맷, 프로덕션 빌드 통과
- 로컬 Worker `/`, `/account`, `/account/setup` 200, 비인증 보호 API 3곳 401과 `private, no-store`, `nosniff`, `no-referrer` 확인
- 검증 중 운영 데이터 쓰기, 메일 발송, 유료 AI 요청, 외부 업무 요청 0건

## 운영 경계와 다음 감사

GitHub `main`에는 반영했다. Sites 소스 전송과 공개 운영 배포는 별도 외부 변경이므로 버전 313 명시 승인 전에는 수행하지 않는다. 다음 감사는 관리자 파일 재고 화면에서 SHA-256 원장 적용 여부를 신규·레거시로 구분해 운영자가 무결성 증명 보급률을 안전하게 확인할 수 있는지 점검한다. 이 감사도 운영 R2 본문을 읽거나 레거시 체크섬을 추정하지 않는다.
