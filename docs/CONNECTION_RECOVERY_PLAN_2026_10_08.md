1. 사용자 **기존 Supabase 계정 로그인은 완료**했다. 다시 요구하지 않는다. 새 계정·새 프로젝트·유료 플랜을 만들지 않는다. 아직 DB 비밀번호를 변경하지 않는다.
2. 로그인 후 프로젝트 ID, 프로젝트 접근 권한, Connect의 실제 pooler 호스트·사용자·포트를 확인한다. 기존 문서의 호스트를 추정하거나 다른 프로젝트의 값을 사용하지 않는다. 앱은 transaction pooler 6543, 백업은 같은 호스트의 session pooler 5432를 사용한다.
3. Supabase의 정식 API Keys 화면에서 기존 서버 Secret key를 조회할 수 있는지 확인한다. 조회할 수 있으면 기존 키를 유지한다. 조회 불가 시 새 서버 키 최대 1개 생성의 범위와 권한을 별도 확인한다. 기존 키는 자동 폐기하지 않는다. `anon`, publishable 키나 JWT 비밀로 대체하지 않는다.
4. OneDrive 밖 비공개 폴더와 Windows 현재 사용자·SYSTEM 접근 제한은 위 경로에 준비했다. 실제 비밀값 보관은 승인 후 수행한다. 기존 파일이 있으면 덮어쓰지 않는다. 비밀번호·키는 채팅·Git·스크린샷·로그에 넣지 않는다.
5. 새 연결값을 반영할 기존 Vercel Secret은 **`SUPABASE_DATABASE_URL` 1개**다. 서버 키 Secret은 유지한다. 현재 운영 소스·재배포 확인 창은 검토 후 취소했다. Production 외 Preview/Development로 운영 DB 값을 복제하지 않는다. DB 비밀번호 변경 전에 새 값 보관·URI 생성·반영 절차를 준비한다.

## 중요한 결정과 실행 순서

비밀번호 사본이 없으므로 기존 DB 비밀번호를 사용하는 현재 구성으로 로컬 연결을 복구하려면 DB 비밀번호 재설정이 필요하다. **DB 비밀번호 변경은 기존 DB 연결과 동일 DB를 사용하는 다른 구성요소에 영향을 줄 수 있다.** 기존 앱의 연결을 새 값으로 바꾸고 새 배포가 반영될 때까지 접속 장애가 발생할 수 있으며 시간을 보장하지 않는다. 이 영향과 실행 범위를 구체적으로 승인받기 전에는 변경하지 않는다.

승인 후에도 **비밀번호 입력·확인·재설정 제출은 사용자가 Supabase 화면에서 직접 수행**한다. 계정 로그인 비밀번호가 아니라 이 프로젝트의 DB 접속 비밀번호다. 사용자 직접 입력 단계에서 에이전트가 대신 입력·제출하지 않는다. 새 키 생성이 필요할 경우에는 해당 작업 직전에 별도 권한 확인을 한다.

1. 기존 서버 키를 정식 조회로 확보한다. 기존 키 생성·삭제·폐기 0건을 유지한다. 조회 가능성이 확인됐으므로 새 키를 만들지 않는다.
2. 새 DB 비밀번호를 안전하게 보관하고, 변경 직후 반영할 DB URI와 기존 Vercel 변경 절차를 준비한다. 비밀번호의 URI 예약 문자는 정확히 인코딩한다.
3. 사용자가 DB 비밀번호 재설정을 완료하면 새 연결로 `SELECT 1` 등 고객 자료를 읽지 않는 최소 연결 검사와 비공개 버킷 설정 검사만 수행한다. 키·전체 DB URI·원격 오류 본문을 출력하지 않는다.
4. 승인된 새 DB 연결값만 기존 Vercel Production의 `SUPABASE_DATABASE_URL`에 반영하고, 동일 운영 소스를 재배포한다. 기존 서버 키·도메인·DB·버킷·외부 AI 비활성·권한 정책을 유지한다. 고객 자료 수정, 관리자 생성, 스키마 변경은 하지 않는다.
5. 새 배포의 Ready·도메인 할당과 비인증 HTTP 7건, 새 연결의 최소 검사 결과를 확인한다. 이 검사만으로 관리자 로그인·전체 업무·실제 파일 복원까지 통과했다고 보고하지 않는다.
6. 이후 실제 백업 생성·보관·복원은 실데이터 처리 범위와 별도 보관 위치를 확인하고 진행한다. 연결 복구만으로 B2 전체를 완료 처리하지 않는다.

## 중단·복구 원칙

- DB 비밀번호를 바꾸기 전 계정 권한·Vercel 접근·새 값 보관·배포 경로 중 하나라도 준비되지 않으면 변경하지 않는다.
- 변경 후 배포나 접속 검사가 실패하면 추가 데이터 작업을 멈춘다. 저장한 새 값과 URI 인코딩·정확한 프로젝트/호스트를 확인한다. 비밀번호를 연속해서 재설정하지 않는다.
- **이전 배포로 되돌리는 것만으로 이전 DB 비밀번호가 복원되지는 않는다.** 이전 값은 없으므로 단순 배포 롤백을 완전한 복구책으로 제시하지 않는다. 검증된 새 연결정보를 사용하도록 동일 운영 코드를 다시 반영하는 경로를 준비한다.
- 기존 API 키 폐기, RLS/인증/SSL 해제, 공개 버킷 전환, 프로젝트 재생성, 고객 자료 삭제는 이 계획에 포함하지 않는다.
