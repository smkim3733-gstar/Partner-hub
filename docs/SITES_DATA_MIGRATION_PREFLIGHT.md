# Sites 데이터 이전: 읽기 전용 사전 검사

2026-09-10. 대상은 기존 Sites의 D1 `DB`와 R2 `AI_SOURCE_FILES`, 이전 대상은 Vercel Next.js + Supabase다. 이 문서와 검사 도구는 **운영 백업·PostgreSQL 복원·운영 전환의 완료 증거가 아니다.**

## 운영 원본에서 확인한 범위

- `.openai/hosting.json`의 프로젝트 `appgprj_6a92514801988191b79eb9bd314e3fcd`를 그대로 사용했다. 새 Site를 만들거나 배포하지 않았다.
- Sites의 읽기 전용 DB 목록은 사용자 테이블 30개를 반환했고 식별자 생략·잘림은 없었다. 저장소의 원본 SQL 99개를 빈 SQLite에 적용한 테이블 목록과 일치한다.
- `portal_state` 한 행을 조회했지만 `model_projection.truncated=true`, `truncated_values=1`이었다. `has_more=false`와 `next_offset=null`이어도 셀 본문이 완전하다는 뜻이 아니다. 이 조회 결과로 백업 파일을 만들지 않았다.
- 기존 `portal_chatgpt_member_bindings`도 실제 원본에 남아 있다. 새 `portal_chatgpt_identity_bindings`가 존재한다는 이유로 구형 테이블을 백업에서 제외하면 안 된다.
- 기업 파일 테이블의 한 번의 빈 조회는 모든 R2/FLOW 파일이 없다는 증거가 아니다. 파일 원장과 실제 객체 바이트는 별도 전수 대조가 필요하다.

현재 연결 도구에는 D1의 일관된 전체 DB 내보내기나 R2 전체 원본 다운로드 기능이 확인되지 않았다. 잘린 조회를 이어 붙이거나, 비공개 관리용 API를 임의로 공개 배포하는 우회 방법은 사용하지 않는다. 플랫폼의 정식 내보내기 기능/지원 경로로 확보한 완전한 사본이 필요하다.

## 검사 도구

Node 24에서 실행한다. 자격증명, 네트워크 연결 또는 앱 활성화가 필요하지 않다.

```powershell
node scripts/check-sites-snapshot.mjs --help
node scripts/check-sites-snapshot.mjs inspect backups/sites-source.sqlite
node scripts/check-sites-snapshot.mjs compare backups/sites-source.sqlite backups/sites-restored.sqlite
```

위 파일명은 사용 예시다. 실제 운영 사본이 아직 저장됐다는 뜻이 아니다. `inspect`는 로컬 사본을 검사하고, `compare`는 두 **실제 SQLite 파일을 다시 읽어** 논리 내용을 비교한다. 사용자 편집이 가능한 JSON 보고서를 복원 증거로 신뢰하지 않는다. 명령에는 import/export/cleanup/force 기능이 없다.

입력 조건:

- 정식 내보내기 또는 SQLite의 일관된 백업 방식으로 만든 동결된 독립 SQLite 파일이어야 한다. 실행 중 DB의 본체만 파일 복사하면 안 된다.
- SQL 덤프, JSON 조회 결과, UTF-16 DB, WAL 형식 및 `-wal`/`-shm`/`-journal` 동반 사본은 거절한다. 거절된 보조 파일을 삭제해서 검사를 강제로 통과시키지 않는다. 올바른 새 사본을 확보한다.
- 파일 최대 2GiB, 전체 행 최대 100,000개, 셀 최대 64MiB, 읽은 논리 셀 합계 최대 1GiB다. 한도 초과는 오류이며 일부만 검사한 성공 보고서를 내보내지 않는다. 더 큰 실제 원본은 별도 스트리밍 방식과 자원 검토가 필요하다. 이 한도는 네이티브 SQLite 전체 메모리/CPU의 절대 상한을 보장하지 않는다.
- 입력 경로는 `readOnly`로 열고 확장 로딩을 허용하지 않는다. `trusted_schema=OFF`, `query_only=ON`과 단일 읽기 트랜잭션을 사용한다. 전후 파일 식별자·크기·수정 시각 변경도 거절한다. 원본 SQL 덤프는 실행하지 않으며, 기준 스키마 구성 시에만 신뢰하는 저장소의 `drizzle/*.sql`을 메모리 DB에서 실행한다.

## 검사 내용과 판정

- 원본 30개 테이블을 모두 정책에 등록한다. 빠진 테이블, 추가 테이블, 변경된 열/생성 열, view/virtual table 대체, 인덱스·트리거·스키마 차이를 자동 수리하지 않는다. 알 수 없는 이름이나 SQL은 출력하지 않는다.
- `quick_check(20)`와 외래 키 검사는 신뢰하는 기준 스키마와 정확히 일치할 때만 실행한다. 입력 스키마의 임의 CHECK 표현식을 검사 목적으로 평가하지 않는다. 스키마가 다르면 완전한 검사로 판정하지 않는다. `quick_check`는 모든 인덱스/UNIQUE 검증이나 업무 규칙 검증을 대신하지 않는다.
- 각 셀을 타입·길이·바이트와 열 이름에 결속해 SHA-256을 계산한다. TEXT는 원시 UTF-8 바이트, INTEGER는 BigInt 십진 문자열, REAL은 8바이트 부동소수 표현, BLOB은 원시 바이트, NULL은 독립 타입으로 처리한다. JSON을 다시 직렬화하지 않으므로 공백·키 순서·큰 정수·중복 키를 없애지 않는다.
- 행 해시를 정렬한 다중집합으로 테이블 해시를 만든다. 삽입 순서/rowid와 무관하지만 중복 행·삭제·셀 변경은 다르게 판정한다. 스키마 해시와 데이터 해시는 별도다. 물리 DB 파일이 바이트 단위로 동일하다고 주장하지 않는다.
- 잘못된 UTF-8, PostgreSQL TEXT에서 허용하지 않는 NUL, 스토리지 타입 불일치, JSON 오류·중복 키, 비표준 UTC 시각/통계 날짜, `company-source/<id>` 또는 `consulting-flow/<file_id>`와 다른 원장 경로를 집계한다. 값·개인 식별자·이메일·본문·비밀번호/세션·행별 해시는 출력하지 않는다.
- `complete=true`는 알려진 전체 테이블과 정확한 기준 스키마를 읽고 SQLite 기본 검사를 끝냈다는 뜻이다. **PostgreSQL 도메인·모든 참조·원장 간 결속·실제 파일 바이트 검증 완료가 아니다.** 외래 키나 데이터 호환성 문제는 `issues`를 함께 확인한다.
- `sqliteLogicalMatch=true`는 두 사본의 알려진 스키마와 논리 데이터가 같다는 뜻이다. 원본 출처나 내보내기 시각이 올바르다는 뜻도, Supabase에 복원됐다는 뜻도 아니다. 같은 잘못된 자료 두 개도 서로 일치할 수 있다.
- `migrationReady`는 항상 `false`다. 원본 출처/쓰기 동결, 전체 파일 바이트 대조, PostgreSQL 역사 이관/복원, 독립 인증 결속, Vercel 전환/롤백을 미검증 항목으로 남긴다.

## 데이터 종류별 이전 원칙

분류는 `scripts/sites-snapshot-policy.mjs`의 테이블별 목록으로 관리한다. **모든 표는 원본 백업에 보존한다.** 분류는 삭제나 운영 데이터 변경 권한이 아니다.

| 종류                                      | 대상 처리 원칙                                                                                                                                             |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 명단·초안·AI 이력·운영 통계               | 원본 값과 안정 ID를 보존하고 PostgreSQL 도메인·참조·시각 조건을 별도 검사한다.                                                                             |
| 기업/FLOW 파일·예약·완료·해시 원장        | 삭제 영수증·미완료 예약도 보존한다. DB 목록만으로 파일 바이트의 존재/해시를 증명하지 않는다.                                                               |
| `consulting_flows`                        | 이미 진행된 revision/명령/감사/파일 이력을 보존하는 별도 역사 이관 경로가 필요하다. 신규 FLOW API는 복원 API가 아니다. 보호 트리거를 자동 해제하지 않는다. |
| 비밀번호 계정                             | 해시를 원본 백업에 보존하되 현재 회원 ID·이메일·자격 버전과 별도 검증한다. 신규 관리자 자격은 운영자 절차로 구성한다.                                      |
| ChatGPT 구/신 결속                        | Sites 복구용으로 보존한다. Vercel의 독립 관리자/회원 로그인 권한으로 자동 전환하지 않는다.                                                                 |
| 기존 세션·재설정 링크·인증 제한·충돌 토큰 | 원본 사본에 보존하고 새 운영 도메인에서 활성화하지 않는 계획이다. 실제 이관 정책 확정과 통제된 새 로그인 절차가 필요하다.                                  |

새 PostgreSQL 전용 명령 키·독립 인증·Storage 버전/포인터·직접 전송 테이블은 원본 표를 이름만 맞춰 복사하는 대상이 아니다. 원본 업무/파일 증거에 근거한 파생 값 검증과 대상 원자성이 별도 필요하다.

## 실제 이전과 복구의 남은 관문

1. 정식 경로로 전체 D1 사본과 R2 객체 원본/목록을 확보한다. 생성 시각·원본 프로젝트·내보내기 방식과 쓰기 동결 구간을 기록한다. 현재 조회 도구의 잘린 결과는 이 관문을 통과하지 못한다.
2. 이 도구로 동결 사본을 검사한다. 스키마 차이와 비표준 키/날짜는 원본을 보존한 상태로 별도 이관 명세에 남긴다.
3. 파일별 실제 길이·SHA-256, 소유권·원장·업무 참조·예약·삭제 이력을 대조한다. R2 ETag와 Supabase의 새 ETag가 같다고 가정하지 않는다. 최종 객체/버전 포인터 생성은 Storage API와 기존 원장 규칙을 통해 처리한다.
4. 격리된 Supabase 대상에서 역사 FLOW 포함 이관/복원 경로를 시험한다. 건수와 변환 전후 불변식, 실패 후 재실행·부분 쓰기 롤백을 검증한다. 이 SQLite 비교 도구로 PostgreSQL 복원 완료를 대체하지 않는다.
5. 자격증명·비공개 버킷·권한을 설정하고 실제 Supavisor 독립 세션, Storage 전송, Vercel Preview를 검증한다. 2026-09-10 비공개 버킷 생성과 25MiB 제한은 실제 확인했다. 아직 앱용 Secret key·DB 비밀번호 포함 풀러 URL·Vercel 주소가 로컬에 없으며 실제 연결 검증은 미완료다.
6. 검증을 통과한 후 쓰기 동결·최종 증분/재내보내기·절체를 수행한다. 절체 뒤 새 데이터가 생겼다면 이전 DB로 되돌리는 것만으로 롤백이 되지 않는다. 역방향 증분/새 데이터 보존 방안을 확정하기 전 자동 전환하지 않는다.

사본과 보고서는 개인 정보 및 인증 해시를 포함하거나 그 지문을 가진다. `.gitignore`의 `backups/` 또는 별도 접근 제한 저장소를 사용하고 Git·공개 첨부·공개 CI 로그에 넣지 않는다. Git 제외는 암호화나 접근 통제를 대신하지 않는다.

## 검증 근거

`tests/sites-snapshot.test.ts`의 합성 로컬 DB 15개 검사가 통과했다. 전체 원본 스키마, 긴 본문, 정확한 64비트 정수/인접 실수, 삽입 순서와 JSON 바이트, NULL/빈 값/행 삭제, UTF-8/NUL, 중복 JSON 키, 레거시 시각/파일 키, 인증/역사 분류, 스키마 드리프트/외래 키, 악성 CHECK/view 비실행, WAL/SQL 거절, 행 상한과 CLI 종료 코드를 검사했다. 입력 사본의 전후 해시도 대조했다. 실제 운영 백업·원격 Supabase 복원 시험이 아니다.
