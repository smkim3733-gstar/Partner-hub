# 기업자료 삭제 후 D1 정리 무결성 경계

기준일: 2026-09-05

## 문제

기업자료 삭제는 R2 객체를 지운 뒤 파일 ID만으로 객체 무결성·저장 키·진행·담당 원장과 원본 행을 일괄 삭제했다. 내구성 삭제 결정 뒤 R2 삭제가 끝나는 사이 D1 원본 행의 저장 키가 바뀌면, 원래 키의 객체는 이미 삭제됐는데 바뀐 행과 복구 증거까지 무조건 제거될 수 있었다. 다른 R2 객체를 추가로 삭제하지는 않지만 손상 상태를 숨기고 외부 객체를 원장 없는 고아로 남기는 문제다.

## 적용

- R2 삭제 뒤 D1 정리 batch의 각 자식 원장 삭제에 파일 ID·원본 행 저장 키·저장 키 원장 일치 조건을 추가했다.
- 저장 키 원장 삭제도 원본 행이 삭제 결정 당시 키를 그대로 유지할 때만 수행한다.
- 최종 원본 행 삭제는 파일 ID와 결정 당시 저장 키가 모두 같아야 한다.
- D1 batch는 하나의 트랜잭션으로 실행되므로 조건이 맞으면 전체 정리가 완료되고, 키가 바뀌면 원본 행과 모든 자식 원장을 보존한다.
- 최종 원본 행 삭제가 0건이면 이미 다른 동시 삭제가 완료된 경우 204 멱등 성공을 유지한다. 행이 남아 있으면 HTTP 409 무결성 충돌로 격리한다.
- 삭제 tombstone은 그대로 남아 다운로드·재업로드를 차단하고 수동 복구 근거를 보존한다.

## 검증

- R2 삭제 직후 D1 키를 바꾸는 경합에서 HTTP 409를 반환한다.
- 원래 R2 객체는 삭제됐지만 외부 객체는 보존되고, 바뀐 원본 행·정확한 기존 키 원장·객체 무결성·담당 원장이 모두 남는다.
- 정상 삭제와 두 요청의 동시 삭제는 기존 204 멱등 의미를 유지한다.
- 실제 Worker/D1/R2 정상 삭제에서 저장 키·객체 무결성·담당 원장이 조건에 맞게 정리된다.
- Node 회귀 검사 612/612 통과
- 격리 workerd/D1/R2 검사 425/425 통과
- 타입검사, 전체 lint, 프로덕션 빌드 통과
- 로컬 운영 Worker `/`, `/account`, `/account/setup` HTTP 200과 CSP, `X-Frame-Options: DENY`, `nosniff`, `no-referrer` 확인
- 실제 운영 쓰기, 이메일 발송, 유료 AI 요청, 외부 요청 0건
