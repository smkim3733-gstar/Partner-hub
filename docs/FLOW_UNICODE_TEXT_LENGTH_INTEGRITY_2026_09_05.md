# 상담 FLOW Unicode 문자열 길이 무결성 경계

기준일: 2026-09-05

## 확인한 문제

SQLite `length(TEXT)`는 Unicode 코드 포인트 수를 세지만 JavaScript `String.length`는 UTF-16 코드 단위 수를 센다. 이모지처럼 기본 다국어 평면 밖의 문자 하나는 SQLite에서 1자, JavaScript에서 2자로 계산된다. 같은 저장 행이 축소 대시보드에서는 정상인데 상세 FLOW 조회에서는 손상으로 거절될 수 있었고, 명령 입력·AI 생성 결과·사전점검도 서로 다른 길이 판정을 사용할 수 있었다.

## 적용한 경계

- FLOW 문자열 길이를 Unicode 코드 포인트 수로 세는 공용 함수를 만들었다. 이 기준은 SQLite `length(TEXT)`와 일치한다.
- 저장 구조의 이름·본문·식별값 상한, 수동 명령 입력, AI 근거자료와 생성 보고서, AI 작업 결과와 감사기록, 1차 보고서 사전점검이 같은 공용 길이 함수를 사용한다.
- 20자·80자·200자 최소 조건도 같은 기준으로 계산해 화면 안내와 서버 판정을 일치시킨다.
- 한국어 등 기본 다국어 평면 문자의 기존 한도는 바뀌지 않는다.
- 진행 전체 JSON은 별도의 UTF-8 1,800,000바이트 상한을 계속 적용한다. 코드 포인트 상한을 맞추면서도 보조 평면 문자로 저장 자원 한도를 키울 수 없다.
- D1 스키마, R2 파일, 인증·권한, 보관·삭제 정책은 변경하지 않았다.

## 검증

- 이모지 1개와 한국어 1개가 각각 1자로 계산되는지 확인했다.
- 보고서 본문은 이모지 80,000개를 허용하고 80,001개를 거절한다.
- 숨김 감사 상세는 이모지 2,000개일 때 상세 조회와 SQLite 축소 대시보드가 모두 허용하고 2,001개일 때 모두 HTTP 503으로 격리한다.
- Node 자동 테스트 587/587 통과.
- 격리 workerd+D1+R2 검사 375/375 통과.
- 타입검사, 전체 lint, 변경 파일 포맷 검사, 프로덕션 빌드 통과.
- 로컬 프로덕션 `/`, `/account`, `/account/setup` HTTP 200과 CSP·`DENY`·`nosniff`·`no-referrer` 확인.
- 실제 운영 쓰기, 메일 발송, 유료 AI 요청, 외부 요청 0건.

## 다음 감사

JavaScript 문자열이 가질 수 있는 짝이 없는 UTF-16 surrogate가 JSON 직렬화와 SQLite `json_extract()` 사이에서 같은 값과 길이로 유지되는지 확인한다. 잘못 구성된 Unicode가 상세 조회·축소 대시보드·명령 입력 중 한 경로에서만 통과하지 않도록 저장 전 계약을 마련한다.
