# 순차 점검 1 — 회수 저장 잠금·응답 유실·재시도

## 점검 결과

원본 회수 요청이 서버에 저장된 뒤 응답만 유실된 경우, 기존 화면은 오류 처리에서 전체 자료 편집 잠금을 풀었다. 이 상태에서 다른 자료를 수정하면 오래된 운영 화면 저장이 서버에서 거부되고, 오류 상태 때문에 회수 재시도 버튼도 비활성화될 수 있었다. 서버의 버전·회수 증빙 보호는 유지되지만 화면에서 결과 확인을 이어가기 어려운 경로였다.

기존 오류 시 잠금 해제 동작을 제출 제어 코드로 분리해 가상 응답 유실로 재현했다. 해당 잠금 유지 회귀 검증은 수정 전 실패했고 수정 후 통과했다. 실제 브라우저 클릭이나 운영 고객 회수로 재현하지 않았다.

## 수정한 동작

- 실제 회수 요청을 보낸 뒤에는 응답 성공·통신 실패·서버 거부·읽을 수 없는 응답 모두에서 다른 자료 편집과 메뉴 이동 잠금을 유지한다.
- 잠금을 가진 해당 원본의 재시도만 허용한다. 다른 원본의 회수와 자료 목록 재조회·필터 이동은 잠긴 상태를 유지한다.
- 재시도는 첫 요청의 계정 ID·요청 ID·확인 사유·진행번호·버전 값을 그대로 보낸다. 전체 운영 상태를 다시 저장하거나 바뀐 로그인 계정으로 요청 내용을 바꾸지 않는다.
- 저장 전 확인 실패나 오래된 미리보기는 회수 요청을 보내지 않고, 획득한 잠금만 해제한다.
- 응답 오류 뒤에도 `최신 운영 화면에서 결과 확인`으로 명시적으로 새로고침할 수 있다. 이 작업은 회수 취소가 아니며 이미 저장된 결과를 되돌리지 않는다.
- 이미 완료된 확인과 연속 클릭은 추가 회수 요청을 보내지 않는다. 성공 후에도 최신 운영 화면을 읽기 전까지 편집을 재개하지 않는다.
- 자료 등록 창이 열린 동안에는 회수를 시작할 수 없게 해 미제출 자료 입력과 회수 새로고침이 겹치지 않도록 했다.

기존 전역 저장 큐의 먼저 저장·버전 확인, 서버의 동일 요청 재시도, 회수 증빙 보호, 창을 닫을 때 경고하는 경로도 대조했다. 서버의 원본 연결 규칙·계정 권한·DB 스키마와 원본 저장·삭제 정책은 변경하지 않았다.

## 검증 범위

자동 테스트 160개와 격리 workerd/D1/R2 검증 93개를 통과했다. 새 검증 6개는 잠금 유지, 사전 확인 실패, 중복 클릭, 오류 응답·손상 응답, 계정 변경 후 동일 요청 유지, 실제 회수 API가 저장한 뒤 응답을 잃었을 때 원본 요청으로 복구하는 흐름을 다룬다. 마지막 검증은 실제 저장 큐와 가상 DB를 연결해 오래된 운영 상태 저장 0회, 회수 자료·이력 각 1건을 확인한다.

브라우저 클릭·시각 QA·실제 고객 파일 조회·실제 계정 생성·운영 자료 쓰기·메일·유료 AI 요청은 수행하지 않았다. 원본 업로드·다운로드·삭제의 동시 요청과 상담 FLOW 권한 점검은 다음 두 항목으로 남긴다.

선행 운영 버전은 44, 소스는 `6be0011`이다. 최종 lint·타입검사·빌드·배포와 공개 경로 확인 결과는 `outputs/release/recovery-lock-deployment.json`에 기록한다.
