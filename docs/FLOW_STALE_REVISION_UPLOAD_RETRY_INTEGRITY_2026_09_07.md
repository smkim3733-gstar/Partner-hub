# 상담 FLOW 낡은 revision 업로드 재시도 무결성

기준일: 2026-09-07

## 확인한 위험

2슬롯 업로드가 첫 객체만 저장한 채 실패한 뒤 다른 요청이 FLOW를 갱신하면, 이전 revision의 재시도가 기존 예약을 사용해 R2 객체를 먼저 쓰거나 동시 변경을 덮어쓸 위험이 있다.

## 확인한 현재 경계

- 첫 전사문 객체 저장 성공과 두 번째 음성 저장 실패를 결정적으로 재현했다.
- 별도 실제 API 명령으로 FLOW revision과 AI 정책을 갱신한 뒤, 원래 명령 ID·첨부와 낡은 revision으로 재시도했다.
- 서버는 예약 조회·R2 쓰기 전에 낡은 revision을 409로 거절하고 R2 `put`을 한 번도 호출하지 않는다.
- 거절된 요청은 동시 FLOW 변경, 기존 전사문 객체 바이트와 두 `pending` 예약의 파일 ID·R2 키·상태를 그대로 보존한다.
- 새 FLOW revision으로 원래 명령 ID·본문·첨부를 다시 보내면 같은 두 파일 ID·R2 키로 정상 완료되고 두 예약과 완료 원장이 원래 명령 ID에 결속된다.

기존 구현이 요구 경계를 만족해 런타임 코드는 바꾸지 않고 동시 변경 덮어쓰기 방지 회귀 증거를 추가했다.
