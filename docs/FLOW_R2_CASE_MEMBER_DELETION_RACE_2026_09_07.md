# 상담 FLOW R2 쓰기 중 사건·담당 계정 삭제 경쟁 무결성

기준일: 2026-09-07

## 확인한 위험

부분 R2 실패 뒤 정확한 전사문·음성 재시도가 첫 객체를 기존 예약 키에 기록한 순간 사건과 담당 계정이 모두 삭제되면, 남은 객체 쓰기나 FLOW 커밋이 삭제 전 권한으로 계속될 수 있다. 삭제된 계정의 안정 ChatGPT 결속이 남거나 이미 기록한 객체를 오류 정리로 없애도 접근 폐기와 안전한 재시도를 보장할 수 없다.

## 확인한 현재 경계

- 첫 전사문 객체 저장 성공과 두 번째 음성 저장 실패로 두 `pending` 예약이 남은 상태를 결정적으로 재현했다.
- 같은 명령 ID·본문·첨부의 정확한 multipart 재시도가 첫 전사문 객체를 기존 예약 키에 다시 기록한 직후 지원되는 관리자 상태 저장 API를 두 번 실행했다. 첫 저장은 사건을 삭제하면서 담당 계정을 정지했고, 두 번째 저장은 배정 레코드가 없어진 정지 계정을 삭제했다.
- 계정 삭제 저장은 기존 안정 ChatGPT 사용자 ID·회원 ID 결속을 같은 D1 상태 변경 안에서 폐기했다.
- 재시도는 두 번째 음성 객체까지 원래 예약 키에 기록한 뒤 최종 인증·신원 결속·담당 접근 검사를 다시 수행한다. 삭제된 회원은 활성 파트너로 인증되지 않아 403으로 끝나며 FLOW·명령 영수증·파일 원장·완료 원장 D1 쓰기는 시작하지 않는다.
- 사건·회원 삭제와 결속 폐기는 보존된다. 기존 FLOW와 명령 영수증은 변하지 않고 두 예약은 `pending`, 두 R2 객체는 예약된 파일 ID·키·바이트를 그대로 유지한다.
- 사건과 회원 원본을 복구해도 폐기된 결속은 되살아나지 않는다. 같은 안정 ChatGPT 사용자 ID가 같은 명령 ID·본문·첨부로 다시 요청하면 정확한 회원 ID에 재결속하고 같은 두 파일 ID·R2 키를 재사용해 FLOW, 명령 영수증, 두 `ready` 예약과 완료 원장을 한 번만 커밋한다.

기존 구현이 모든 R2 쓰기 뒤 인증·신원·담당 접근을 다시 확인하고 계정 삭제 시 안정 신원 결속을 폐기해 요구 조건을 만족한다. 런타임 코드는 바꾸지 않고 지원 관리자 경로의 사건·담당 계정 연속 삭제와 첫 R2 쓰기 경쟁 회귀 증거를 추가했다.
