# 기업자료 담당 계정·진행 연결 원장 불변 경계

기준일: 2026-09-05

## 문제

기업자료의 담당 계정과 상담 진행 연결은 파일 접근 권한과 원본 출처를 결정하는 별도 원장이다. 운영 코드는 두 원장에 신규 파일의 최초 `INSERT`만 수행했지만, 테이블 자체는 직접 `UPDATE`와 부모 원본이 남은 상태의 직접 `DELETE`를 허용했다. 잘못된 유지보수 SQL이 최초 소유권이나 진행 귀속을 새 값으로 덮어쓰거나 증거 행을 먼저 지울 수 있는 저장소 계약 공백이었다.

## 적용

- `app/`과 `lib/` 전체를 검사해 `company_file_assignments`, `company_file_case_links`에는 신규 파일의 `INSERT`만 있고 운영 중 직접 수정·삭제 경로가 없음을 확인했다.
- `0022_company_file_ownership_ledger_immutability.sql`에 두 원장별 `BEFORE UPDATE` 트리거를 추가해 유효한 값으로의 변경도 모두 거절한다.
- 부모 원본이 존재하는 원장 행의 직접 `DELETE`도 각각 거절한다.
- 정상 파일 삭제는 검증된 `company_file_objects` 부모 행을 조건부 삭제하고 두 소유권 원장을 외래 키 `ON DELETE CASCADE`로 같은 SQLite 결정에서 정리한다.
- 런타임 테이블 준비에도 같은 네 트리거를 `IF NOT EXISTS`로 포함해 신규·격리 저장소와 마이그레이션 적용 저장소의 계약을 맞춘다.
- 정적 회귀검사가 이후 애플리케이션 코드에 다섯 불변 원장의 직접 `UPDATE`·`DELETE`가 다시 들어오면 실패한다.
- 담당 계정이나 진행을 실제로 바꿔야 할 미래 업무는 기존 증거를 덮어쓰지 않고 별도 감사·버전 원장을 추가하는 명시적 재배정 기능으로 설계해야 한다.

## 검증

- 담당 계정 원장의 직접 계정 변경과 직접 삭제가 각각 불변·부모 삭제 요구 오류로 거절된다.
- 진행 연결 원장의 직접 진행 변경과 직접 삭제도 같은 방식으로 거절된다.
- 정상 삭제 API는 HTTP 204를 반환하고 R2 객체와 담당 계정·진행 연결 원장을 함께 제거한다.
- 23개 추가형 마이그레이션을 기존 행이 있는 격리 D1에서 두 번 적용해도 최초 결속을 교체하지 않는다.
- Node 회귀 검사 621/621 통과
- 격리 workerd/D1/R2 검사 434/434 통과
- 타입검사, 전체 lint, 변경 파일 포맷, 프로덕션 빌드 통과
- 로컬 운영 Worker `/`, `/account`, `/account/setup` HTTP 200과 CSP, `X-Frame-Options: DENY`, `nosniff`, `no-referrer` 확인
- 실제 운영 쓰기, 이메일 발송, 유료 AI 요청, 외부 요청 0건
