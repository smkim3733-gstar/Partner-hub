# 기업자료 업로드 응답 검증 안전성

## 문제

기업자료 업로드 클라이언트는 성공 응답에서 파일 ID 존재만 확인하고 나머지 메타데이터를 화면 자료 카드에 적용했다. 손상된 성공 응답은 다른 파일명·크기·담당 계정·진행 ID·자료종류를 현재 신청이나 자료 목록에 연결할 수 있었고, 비-JSON 오류는 기술 오류 문구로 노출될 수 있었다.

## 변경

- 성공 응답의 파일 ID·안전한 파일명·크기·MIME·생성시각·담당자·담당 계정·진행 ID·자료종류·자료명을 검증한다.
- 파일명·크기·MIME·담당 계정·진행 ID·자료종류·자료명은 현재 업로드 요청과 정확히 일치해야 한다.
- 서버와 클라이언트가 같은 안전한 파일명 변환 함수를 사용한다.
- 검증된 공개 메타데이터만 새 객체로 반환하고 알 수 없는 서버 필드는 제거한다.
- 비-JSON·손상된 성공 응답은 같은 파일과 자료정보로 재시도하도록 안내하며 앞서 저장됐을 수 있는 원본은 자동 삭제하지 않는다.

## 유지한 운영 경계

- `/api/files` 서버 저장·인증·권한·멱등 요청·D1/R2 동작을 변경하지 않았다.
- 응답 불확실성에서 원본을 추정 삭제하거나 새 파일 ID를 만들지 않는다.
- 기존 원본·자료 카드·운영 데이터·DB/R2 스키마·보관 정책을 변경하지 않았다.
- 외부 발송·유료 AI·GitHub 푸시·공개 Sites 배포를 수행하지 않았다.

## 검증

- 자동 테스트: 361개 통과
- 격리 workerd/D1/R2 스모크: 129개 통과
- TypeScript `--noEmit`, 전체 lint, 프로덕션 빌드 통과
- 기존 개발 서버 `/` 응답: HTTP 200
- 검증 중 운영 쓰기·메일 발송·유료 AI·외부 요청: 각 0건
