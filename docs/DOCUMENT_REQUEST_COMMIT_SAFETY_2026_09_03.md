# 새 서류요청 원자적 저장 안전성

## 문제

새 서류요청 등록은 자료 여러 건, 연결 업무, 타임라인과 진행 다음 행동을 각각 별도 화면 상태 변경으로 만들었다. 자료·업무 ID도 현재 시각을 사용해 같은 순간의 재실행이나 저장 재시도에서 충돌·중복 가능성이 있었다. 폼을 연 뒤 담당 진행·권한·기존 요청이나 한국 날짜 기준이 바뀌어도 저장 직전 전체 상태를 다시 대조하지 않았다.

## 변경

- 서류요청 폼마다 UUID 요청 ID를 한 번 만들고 같은 제출 이벤트의 재실행에 재사용한다.
- 자료와 업무 ID를 요청 ID에서 결정적으로 만들어 같은 화면 상태에서 같은 제출이 반복돼도 동일한 한 묶음만 계산한다.
- 요청 ID가 이미 자료나 업무에 저장돼 있으면 중복 등록하지 않고 기존 진행 기록 확인을 요구한다.
- 저장 전 현재 계정의 서류요청 권한, 진행 ID·기업·담당 계정·FLOW 관리·중단 상태와 폼을 열 때의 진행 연결을 다시 검사한다.
- 서류명·중복·제출기한과 한국 날짜 기준 마감상태를 공용 검증으로 다시 확인한다.
- 폼 작성 중 같은 진행에 동일 서류가 새로 요청되면 일부만 조용히 저장하지 않고 전체 재확인을 요구한다.
- 같은 기업의 다른 반복 진행에 있는 자료는 현재 요청의 중복으로 추정하지 않는다.
- 자료·업무·타임라인·진행 변경을 하나의 순수 계산 결과로 만든 뒤 한 화면 갱신에서 함께 반영한다.
- 원본 상태 배열은 직접 변경하지 않으며 기존 기록과 새 기록의 ID 충돌을 차단한다.

## 유지한 운영 경계

- 새 서류요청의 명시적 등록 동작, 담당 계정·기한·알림 의미는 유지한다.
- 이미 저장된 자료·업무 ID를 일괄 변경하거나 과거 기록을 이관하지 않는다.
- 서버 API, 인증·권한 규칙, revision/CAS, DB/R2 스키마·보관 정책을 변경하지 않았다.
- 메일·메신저·외부 알림·유료 AI·외부 API 호출을 추가하지 않았다.
- GitHub 푸시와 공개 Sites 배포는 사용자 승인 전까지 수행하지 않는다.
