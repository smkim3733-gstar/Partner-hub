# 상담 FLOW 첨부 예약·불확실 저장 복구 무결성

기준일: 2026-09-06

## 확인한 문제

상담 FLOW 첨부를 R2에 기록한 뒤 D1 배치와 후속 FLOW 재조회가 함께 실패하면, 안전상 R2 객체를 보존해야 하지만 어느 요청·진행·파일에 속한 객체인지 운영 화면에서 확인할 내구성 기록이 없었다. 같은 요청을 다시 보내도 새 파일 ID와 키를 만들 수 있어 미참조 객체가 누적될 수 있었다.

## 보완

- R2 쓰기 전에 진행 ID·안정 행위자·명령 ID·명령 지문·첨부 슬롯·파일 ID·정확한 R2 키·공개 가능한 파일 메타데이터를 `consulting_flow_upload_requests`에 `pending`으로 먼저 예약한다.
- 같은 명령과 첨부의 정확한 재시도는 예약된 파일 ID와 R2 키를 재사용한다. 다른 명령 내용·파일·첨부 구성은 업로드 전에 409로 거절한다.
- FLOW 루트, 파일 소유권·메타데이터·R2 ETag 원장과 예약의 `ready` 전이를 하나의 D1 배치에 묶는다.
- D1 배치 실패 뒤 FLOW를 읽을 수 있으면 미참조 R2 객체만 제거한다. 재조회도 실패하면 객체와 `pending` 예약을 함께 보존해 관리자 인벤토리에서 찾고 동일 요청으로 복구할 수 있게 한다.
- 예약은 생성 뒤 신원·키·파일 사실을 바꿀 수 없고 삭제할 수 없다. `ready`는 정확한 FLOW 참조와 세 파일 원장이 모두 존재할 때만 허용한다.
- 예약 생성시각은 감사·인벤토리 기준으로 고정한다. 재시도의 FLOW 파일 생성시각은 새 명령 전이시각을 사용해 최초 FLOW 기준시각과 충돌하지 않게 한다.
- 대표 전용 원본 보관 현황은 미완료 FLOW 첨부의 파일명·크기·용도·진행·담당자만 표시하고 저장 키·명령 지문·명령 ID는 반환하지 않는다. 원본 확인은 본문을 읽지 않는 R2 `head`와 예상 크기만 사용한다.

## 회귀 검증

- 서로 다른 파일로 동일 첫 명령을 동시에 실행해 200 한 건·409 한 건, R2 쓰기 한 번, FLOW 파일 한 건으로 수렴하는지 확인했다.
- D1 배치 실패와 FLOW 재조회 2회 실패를 연속 주입해 503, `pending` 예약과 R2 객체 보존을 확인했다.
- 같은 명령·같은 파일 재시도가 동일 파일 ID·키로 성공하고 예약이 `ready`가 되는지 확인했다.
- 파일 원장 없는 강제 `ready`, 예약 키 변경과 삭제를 앱 모의 D1과 실제 workerd D1에서 거절하는지 확인했다.
- 스키마 상수와 추가형 `0093` 마이그레이션의 테이블·인덱스·트리거가 정확히 일치하는지 자동 대조했다.
- Node 704/704, 격리 workerd+D1+R2 521/521, 타입검사, 전체 lint, 변경 파일 포맷과 프로덕션 빌드를 통과했다.
- 로컬 Worker의 `/`, `/account`, `/account/setup`은 200, 비로그인 `/api/state`와 `/api/admin/file-inventory`는 401과 비공개 무저장 헤더를 반환했다.
- 실제 운영 데이터 쓰기, 메일 발송, 유료 AI 호출, 외부 업무 API 호출은 0건이다.
