# 직접 업무 원자적 등록 안전성

## 문제

직접 업무 등록은 제출할 때마다 새 UUID를 만들었다. 같은 버튼 동작이 빠르게 반복되거나 동일 폼 제출이 재실행되면 내용이 같은 별도 업무 두 건이 생길 수 있었다. 입력 검증과 담당 계정 선택도 화면 함수 안에서 바로 새 상태를 만들었기 때문에 결정적 결과와 중복 차단을 독립적으로 검증하기 어려웠다.

## 변경

- 업무 폼마다 UUID 요청 ID를 한 번 만들고 검증 실패 후 수정·재시도와 같은 제출 이벤트에 재사용한다.
- 업무 ID를 요청 ID에서 결정적으로 만들며 이미 같은 ID가 있으면 중복 등록을 차단한다.
- 업무 입력을 공용 검증으로 정규화하고 검증을 통과한 업무명·기업명·유형·지원분류·마감 정보만 저장한다.
- 파트너는 현재 로그인 계정 ID와 제출 담당 ID가 정확히 일치해야 하며, 현재 명단에서 해당 계정이 한 건의 활성 계정인지 다시 확인한다.
- 대표가 선택한 담당자도 현재 명단에서 한 건의 활성 계정인지 다시 확인한다. 대표 전용 업무의 빈 담당 ID 의미는 유지한다.
- 생성 업무와 전체 업무 목록을 하나의 순수 계산 결과로 만들며 원본 업무·명단 배열을 변경하지 않는다.
- 같은 화면 상태의 같은 제출은 같은 결과를 계산하고, 저장된 결과에 다시 적용하면 기존 업무 확인을 요구한다.

## 유지한 운영 경계

- 직접 업무 등록의 유형·지원분류·담당자·마감·알림 의미는 유지한다.
- 지원 요청의 등록시각·처리주기 등 서버 소유 추적 정보는 기존 저장 경계에서 계속 부여한다.
- 기존 업무 ID를 일괄 변경하거나 내용 기반으로 별도 업무를 자동 병합하지 않는다.
- 서버 API, 인증·권한 규칙, revision/CAS, DB/R2 스키마·보관 정책을 변경하지 않았다.
- 메일·메신저·외부 알림·유료 AI·외부 API 호출을 추가하지 않았다.
- GitHub 푸시와 공개 Sites 배포는 사용자 승인 전까지 수행하지 않는다.
